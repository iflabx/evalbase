## 实现

- 新增 `src/assistant/feedback.ts`，会话读取和最终回复共同投影持久状态。具体业务冲突优先，区分未保存修改、同修订保存回执、总结失败、处理中、确认、完成和实际停止原因。确认阶段使用中性文案，不推测保存目标。
- 模型澄清仍受事实和技术文案边界约束，不能把“已生成/已保存”口头声明变为回执；机器标识形式的工具名/字段留在诊断。保留“已有原始资料进行扩充”的正常补充提示。
- 前端消费 OPT-44 的 action/reason/revision/validUntil/canExecutePlan，区分重试本轮、继续规划及继续执行未完成步骤。过期或409后刷新能力，保留未发送输入；迟到的旧修订读取不回滚当前状态。
- 现有 retry 路由兼容空体，并可携带展示时的修订和动作供服务端锁内核对；不新增公开路由、表、框架或导航。旧确认、候选、诊断入口保留。
- `configuredModel` 的内部 Symbol 身份绑定实际项目/session/turn 或 processing run，供有界验收隔离记账。身份不进入模型 HTTP 请求头或正文。无此身份的普通连接测试不受影响。

## 首次失败与自动纠正

- CU-1：第二条提示后，模型自行要求覆盖3类却只生成2条，`assistant_plan_count_conflict`；随后纠错试图改变原交付语义，被保护拒绝，本轮失败。按票第三条正常业务提示明确只查物流后成功。历史失败仍可展开，成功后当前失败提示清除。
- CU-2：一次 `assistant_background_reference_invalid`，同一轮自动纠正后保存方案成功；没有隐藏此失败来宣称首次无错。
- CU-3：一次 `assistant_tool_input_invalid`（只存语义要求但未给非空可执行步骤），同轮纠正后保存2＋2方案；零生成断言与刷新均通过。
- CU-4：`deliveries[0]` 不是对象；普通继续继承原纠错额度后出现 `assistant_tool_repair_exhausted`；业务修改后 `deliveries[1].scenarios` 少于合同要求3项。三个回合仍无完整方案，未生成。原始错误、已完成的背景读取、未生效变更均保留。
- CU-5：第二主题替换未被现有变更/分类规则同步接受，`assistant_requirement_conflict`：“本轮未更改对应分类约束，不能删除类别、定义或缩减配额”；随后 `assistant_no_progress`。未生成已撤销的地址主题，也未生成退款。不能把保护性拒绝算作替换交付成功。

没有真实提供方超时或连接失败。当前未通过点集中在模型规划合同遵循和业务主题变更的合同衔接，不是 Worker 已生成但页面没刷新。后续修复应使用本次原始失败夹具，检查结构纠错的有效范围、基于合法事实恢复非空方案，以及显式主题替换与对应分类约束的原子更新。不能删除分类/依据保护、放宽场景合同或重置纠错额度来凑通过。新真实补测须另有明确额度，本轮已封存，不自动重跑。
