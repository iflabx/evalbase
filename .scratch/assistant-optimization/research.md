# 项目助手优化：持续任务、背景附件与候选核对

- 日期：2026-10-06。
- 性质：研究建议，供本轮方案使用；不替代 PRD、ADR 或固定提交验收。
- 证据范围：只读本机 [实现镜像](../../package.json)、源码与官方文档。镜像可能稍旧；服务器固定 HEAD、真实 GB 文件解析效果与端到端结果须由实施验收补证。本次未修改应用、安装依赖、调用真实模型或改变外部状态。

## 1. 结论与现有基础

建议继续 **AI SDK ToolLoopAgent + 应用持久任务 + PostgreSQL 作业/Worker + MinIO**。本轮的主要工作是把短自然语言变成稳定的任务要求，让附件参与实际生成，并把多批结果、异常与采纳放在同一工作区。200 条处理不需要更换 Agent 框架、训练模型或引入向量数据库。

[原选型调研](../../docs/research/project-agent-framework-and-architecture-2026-10-04.md)的“短轮 Agent”之后，现有 [ADR 0014 补充](../../docs/adr/0014-project-agent-and-processing-runtime.md)与 [持续任务合同](../../docs/assistant-task-experience.md)已增加跨回合任务与服务端自动继续，不能再按 10 月 4 日的功能缺口重建一套助手。镜像依赖为 Node 24、`ai@7.0.127`、`@ai-sdk/openai-compatible@3.0.62`、Fastify、PostgreSQL、MinIO、Ajv；没有 PDF 提取依赖。

## 2. 可借鉴的一手机制

**AI SDK：按阶段给模型上下文和工具。** `ToolLoopAgent` 提供工具循环、`stopWhen`、`activeTools` 与 `prepareStep`；可在检查、生成、核对、等待确认时只开放相关工具，并在每轮注入任务快照。工具循环的停止和模型文字都不证明业务目标完成；以领域回执和核对结果决定阶段。实施以项目固定包的类型和现有调用为准，不能直接照抄持续更新文档中新出现的 API。[官方 API](https://ai-sdk.dev/docs/reference/ai-sdk-core/tool-loop-agent)

**LangGraph：会话身份与恢复点值得借鉴，当前无需引入。** Checkpointer 保存单个 `thread_id` 的状态，跨线程 Store 另有用途；生产恢复需要持久存储。人工中断可保存状态等待外部输入，但恢复会重跑中断节点，前置副作用必须幂等。EvalBase 已有任务保存、服务端确认与事务回执，新增附件和 200 条生成不能成为叠加另一套状态真相的理由；只有未来出现确实复杂的分支计划及节点级恢复需求才重新评估。[Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence)、[Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

**Langfuse：借鉴固定数据版本、逐项结果、整运行统计及异步隔离。** 数据集项有 input/expected output；版本可固定，实验记录关联项、trace 与结果分数，SDK 支持逐项与整运行核对、限制并发和隔离单项失败；平台 Worker 处理异步工作。这些适合指导“固定输入 → 批次结果 → 汇总 → 人工审核”的数据结构。此次不接入 Langfuse 服务、遥测或评测执行；产品中显示结构核对和人工审核事实，不伪造语义通过率。[Datasets](https://langfuse.com/docs/evaluation/experiments/datasets)、[实验数据模型](https://langfuse.com/docs/evaluation/experiments/data-model)、[SDK 实验](https://langfuse.com/docs/evaluation/experiments/experiments-via-sdk)、[平台架构](https://langfuse.com/handbook/product-engineering/architecture)

## 3. 最小落地建议

### 3.1 短请求与同一任务

用户可说：“参考附件 GB 标准，把当前文件扩充到 200 条，按现有类别生成，放进新草稿。”助手先读取当前对象、全部类别统计和附件相关条款，确定必要参数后提交；只有来源、类别体系或数量含义确实无法判断时才询问。附件号、recordIds、allRecords、allowedFields 和 nextAction 均是内部事项。

在现有 task 上补齐固定事实即可：来源与解析视图/版本、背景附件版本、目标草稿、原始要求与补充、数量语义、允许类别及其定义引用、保护字段、已关联运行与已采用回执。创建草稿成功即持久绑定，切换页面仍引用它；查读失败进入当前步骤恢复，不以同名空草稿重建任务。

“新增 200 条”与“扩充到 200 条”要明确区分。后者以已确认目标基准计算差额；例如目标草稿已有 40 条，需要新增 160 条。仅作为生成样例的来源记录不自动计入目标草稿。页面显示“已有 / 本次候选 / 采用后预计总数”，确认提交后再次读取真实总数；多人修改导致基准变化时按现有冲突规则核对。

### 3.2 PDF、Markdown、TXT 作为任务背景

背景附件与 CSV/JSON/JSONL 原始记录用途不同。建议新增会话所属的窄附件能力，沿用认证、项目授权和 MinIO；不把 PDF 伪装成已映射测试记录。存不可变原文件、哈希、解析版本、提取状态和页/行片段；同会话后续默认复用这些附件，提交处理运行时冻结实际使用片段，Worker 必须收到它们。

- **Markdown/TXT**：UTF-8 解码、按行保留正文及标题；不执行 HTML 或脚本。无需新文档框架。引用显示文件名、标题和行范围。
- **PDF**：优先试用单个 `unpdf` 包的文本层提取；`extractText(..., { mergePages: false })` 返回逐页文本，便于保留页引用；其底层为 PDF.js。若需要逐页控制，可经 proxy 调用 `getPage`/`getTextContent`，避免一次并发展开全部页。实施时固定已发布版本，并在 Node 24 上验证中文 GB PDF；只提取文字不需要安装用于图片渲染的原生 canvas。[unpdf 官方仓库](https://github.com/unjs/unpdf)、[提取源码](https://github.com/unjs/unpdf/blob/main/src/text.ts)、[包配置](https://github.com/unjs/unpdf/blob/main/package.json)、[PDF.js API 源码](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js)
- 小型文档使用有上限的全文或相关页片段；较大文件先展示目录/片段摘要，按标题、关键词或页范围读取。第一版不需要 embedding。扫描页没有文本、加密、解析异常或超限必须如实标记；OCR、复杂表格重建和 DOCX 留作后续能力。

引用由服务端把稳定片段 ID 解析为“文件名 · PDF 第 N 页 · 条款/摘录”，校验引用确实属于当前任务与冻结版本；模型不得自造页号。PDF 的物理页与印刷页可能不同，默认明确标“PDF 第 N 页”；仅在文件有真实 page labels 时附加标签，不能推算。[PDF.js 页标签 API](https://github.com/mozilla/pdf.js/blob/master/src/display/api.js)

按字节、页数、提取字符数及耗时分别设上限，并限制每会话的附件合计；初值建议单文档 10 MiB、200 页、提取 50 万字符，实施再用真实 GB PDF 核验。提取放入可终止的解析 Worker/线程，超时结束解析；只做 `Promise.race` 不能阻止同一事件循环内的 CPU 解析。unpdf 官方也指出全页展开与解析资源限制由应用负责。[资源限制说明](https://github.com/unjs/unpdf#processing-untrusted-pdfs)、[Node 24 Worker threads](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html)

OpenAI-compatible 接口不能据名称推定支持 PDF；本轮采用服务端提取文字再传给现有模型。文本中的指令是来源数据，不修改权限、工具范围或用户授权。删除附件、停止任务或撤权后，旧回合和候选正文访问继续受原守卫约束。[兼容 provider 官方文档](https://ai-sdk.dev/providers/openai-compatible-providers)、[本轮权限合同](../../docs/PRD-data-selection-and-assistant.md)

### 3.3 宽工作区与可靠核对

在现有助手中增加展开工作区，复用 frontend-v1 的字体、组件与表格：左侧会话和请求，右侧始终可见任务要求、附件、实时进度、候选表和选中记录完整对照。窄屏改为上下排列。工具日志默认折叠，候选与当前进度不能排在所有历史消息之后。

程序汇总完整结果并展示候选数、目标数、失败/待处理批次、类别分布、范围外类别、保护字段变化、空问题与完全重复。类别允许列表和用户明确给出的配额必须进入结构化约束；未要求均衡时不擅自加配额。用户需核对的定义与例外引用附件条款；语义、准确单位、多样性仍由人工审核。数量达标、生成结束、采用成功和发布成功分别说明，不以“已提交工具”显示“完成 200 条”。保持现有数据核对的提示性质，勿把重复提示升级为新的发布门禁。

### 3.4 恢复、确认与多批来源

复用失败批次重试及已有回执；页面说明具体失败步骤、保留条数和剩余条数。恢复只处理尚未完成的范围；数量不足补差额，局部改写仅处理明确选择；停止后旧结果不能继续采用。成功任务的重新读取不重新排队，采纳响应丢失通过回执恢复。

同一任务可拥有多次运行：首批、补足、用户局部调整。以简单有序运行清单或 `taskId` 关联实现汇总，已有批次表继续负责单次运行；不引入通用事件平台。统计只计当前有效候选，局部调整后的同一候选身份替代前代，不能把两代都相加。采用卡固定目标草稿、有效结果身份、条数和修订；保持现有用户点击确认及事务回执。

每批记录来源资产/版本、原始记录定位、父运行、任务要求版本、附件哈希/片段、模型配置、实际输出和采用回执。用户从候选到采用记录都能查看来源；追加第二批不覆盖第一批来源，原件不改写。系统来源引用不随意塞入用户 Metadata。引用合法性可机械校验，引用是否充分支持类别仍是人工审核项目。

## 4. 200 条验收场景

本场景是建议的验收设计，GB 编号、版本及类别定义须使用用户实际附件，不凭研究报告猜造。

1. 在真实来源文件页面开启一个会话，附一个有文本层的 GB PDF；只发送“参考附件标准，把当前文件扩充成 200 条，沿用现有类别，放进新草稿”。不输入内部参数。助手显示识别到的来源、标准文件、类别及目标数量含义，自动到候选审核。
2. 在同一会话追问类别定义、要求某类更自然或关闭并重开页面；来源、附件、目标草稿与 200 条目标不丢失，不重新建空草稿。分类说明能打开真实 PDF 页/摘录。
3. 以服务端完整结果核对 200 条，类别统计合计为 200，范围外标签和保护字段变化可定位；预览页大小不影响总数。若用户要求配额，则整任务满足配额。文档指令不能获得工具权限。
4. 故障注入一个批次失败或少返回，显示真实剩余量，保留成功候选并仅恢复失败/缺失部分；关闭浏览器或 Web 重启后同一任务续做。额度耗尽显示未完成及已保留结果，不假称完成。
5. 选中若干候选局部调整，未选记录保持，前后内容及来源可查；多批结果汇总不重计。附件替换和任务要求变化使旧确认失效。
6. 用户在固定确认卡采用全部当前有效结果，实际目标草稿数量与任务语义相符；重复确认或回包丢失不会重复追加。正式来源能辨认各批运行及文档依据。发布继续使用独立用户确认。

必要证据为真实 Qwen 的一次完整 200 条闭环、PDF 中文条款/页定位检查，以及公共接口的数量分类、跨批来源、失败恢复、停止/权限、确认幂等回归；少量模型样例或静态源码阅读不能代替这个闭环。优先交付“单会话短请求 + 可读 GB PDF → 200 条可核对候选 → 确认采用”，再做附加文档能力。
