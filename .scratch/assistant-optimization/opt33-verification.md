## 2. 已实现

1. 在已有提取片段上建立有界章节/行索引，支持父章节加字母子项、十进制及中文编号、Markdown 标题、可证的简单表格。编号、名称及组合别名映射到同一真实定义；同级边界截止，跨片段保留定位。歧义/错位不靠 contains 放行。
2. 读取返回绑定账号、会话、文档哈希、提取版本及原文位置的定义引用；规划和执行沿同一证据校验。已知查询优先给对应章节的定义，避免前置无关目录占满额度；普通自然段不强造分类。
3. 区分逐题自然期望行为和固定标签。不能将“写具体安全行为”变成一个值的枚举，也不能自报 basis:user 绕过实际用户指令。
4. 新文档的规划阶段只向模型提供紧凑的现有生成参数，固定核对/采用确认步骤由服务端补齐；保存前核对非空步骤、独立交付、实际数量及每类依据。只给方案在执行入口也禁止业务写入。
5. 单一、已验证的背景 Metadata 分类，将完整定义作为场景的实际测试目标，模型原场景仅作背景包装，不能用包装中的中立目标替代本类目标；原指令与数量保留。多类别、期望输出分类和用户自定义依据不套此组合。组合后仍走原 200 字场景及工具容量校验，超限拒绝、不截断定义。具体题目是否满足定义仍由 OPT-31 验证。
6. 明确要求记录时，只有真实 plan_task 保存语义要求才可声称已记录；仅文本、仅标题、空输入均不能充当回执。在原有限预算内触发原生保存纠正；两次仍未保存则明确未完成，输入和事实保留。纯解释和核对历史事实不制造新保存。
7. 数量修改保留原语义要求；不能通过空数组误删未被撤销要求。首次明确且无歧义的数量作为执行字段保存，不重复保留“做3条”文字。否定/多数量更正不猜数。无分类步骤的空分类数组不再误清文档依据。
8. 修正场景字符串的 JSON Schema pattern 与模型兼容解码器全匹配解释不一致：原模型只输出单字。相同请求的受控对照，旧 pattern 返回三个单字，新 pattern 返回三个完整场景。参数修复仅增加一层可往返验证的 JSON 容器包装恢复，不猜括号、不替换业务文字、不增加重试额度。
