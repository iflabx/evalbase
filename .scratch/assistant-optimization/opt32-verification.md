## 代码与范围

分支 codex/assistant-optimization，基线 d7dc9dafd3a0ec28425fa354d32486834b0b1834；实现及运行版本 5b0322a8f562b0d75065d5d6b506bdc04982e886。

- 使用已安装 AI SDK 的正式 repairToolCall。直接调用与计划嵌套步骤复用原工具 Schema；修复请求没有业务执行器，只返回当前允许的原工具参数。执行前重走原参数、权限、对象、修订及业务校验。
- 保守比较含义，只允许无损类型、单项/数组、完整 JSON 外壳及已知拼写修正。不能猜引用、改数量/范围/保护字段或丢弃未知要求。修复 Schema 从原合同派生，仅展示已提供字段与对应动作。
- 校验回调不再提前改变终态。修复失败或自身异常进入失败边界；修复成功不留失败卡。同一未解决工具/目标/步骤最多两次实际修复 HTTP 请求，网络重试也占额度；发送前持久化，普通重试/自动续做不重置，共享原请求、时间及取消预算。
- 不新增公开 API、表、依赖、配置页或前端布局。沿用原有 frontend-v1 风格组件。OPT-33、OPT-31 未实施。

## 真实模型：参数修好与整轮完成分别统计

使用现有 qwen3.8-27b-un、模型配置修订 1，修复温度 0；仅写入一次性隔离数据库/存储。Owner 模型配置只读，凭据不进入记录。最终验证源文件与上述提交一致；隔离进程未设置 GIT_SHA，原诊断 codeVersion 为 unknown，部署身份另由下节验证。

注入样本首次合法率 0/6、修复后合法率 6/6；平均额外修复请求约 1.69 秒，整轮完成 5/6。这不是自然请求的首次成功率。

**保留失败：**“记录要求：做3条，保留事实，不添加新信息。先不要执行”已正确保存数量和要求，随后普通规划重复请求至原十次预算边界，最终 assistant_result_incomplete。已有要求保留，零处理/发布写入；该整轮不记为通过，后续工作流仍需跟踪，不能以增加参数修复次数解决。

普通短提示固定为“查询当前项目”“请先给创建一个名为短提示草稿的空测试集的方案，暂不执行”“现在新建一个名为短提示执行草稿的空测试集”，每条两次。全部 6/6 完成；有工具的 5 轮首次调用无参数错误，另 1 轮依据项目上下文直接回答，不纳入工具参数分母。共 7 次业务工具调用无格式失败，修复 0 次、额外修复耗时 0；只给方案没有创建草稿，两个执行请求各新建一个草稿，无版本/处理任务。各轮耗时 1.97、1.48、3.03、4.03、34.55、4.18 秒，其中一次仍较慢，未宣称延迟问题全部消失。

首轮真实修复曾为 4/6，收窄 Schema 后为 5/6；修复嵌套序列化异常后最终参数 6/6。诊断中“回调未发生、普通后续回合成功”的样本未计为修复成功。各轮成功/失败摘要、最终回执及预算见 [脱敏证据](opt32-evidence.json)，服务器 opt32 目录保留原始失败和命令日志。

strict 探测显式发送 strict:true 和互相矛盾的 const/enum；端点 HTTP 200 仍返回不满足完整约束的参数，仅证明可传输标记，不能确认受约束生成。没有启用未经证实的 strict 保障或新增模型配置项，不宣称验证了其他端点的严格模式。
