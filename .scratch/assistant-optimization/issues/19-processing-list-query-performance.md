# OPT-19 数据处理任务列表查询与加载性能优化

Status: ready-for-agent
Implementation: completed
Blocked by: none

优先级：P1（数据处理列表明显慢于原始数据、测试集）。2026-10-13 Owner 授权编写 Ticket，后续明确授权完成 OPT-19 开发。依赖现有 OPT-14/17/18 和列表性能补修，不等待旧 Ticket 的最终人工验收，不改写历史验收状态。

## 目标与依据

让数据处理列表在任务没有变化时快速返回；有变化时准确同步当前成果。采用“批量读取摘要、按变化同步、合并保存统计”的最小方案，复用现有表和查询能力。

继承 [助手 PRD §6](../../../docs/PRD-data-selection-and-assistant.md#6-ai-03-清洗改写扩充)、[CONTEXT](../../../CONTEXT.md)、[处理架构](../../../docs/architecture/data-selection-and-assistant.md)、[ADR 0014](../../../docs/adr/0014-project-agent-and-processing-runtime.md)、[OPT-14](14-loading-performance-and-transitions.md) 和 [OPT-17](17-processing-task-rounds.md)。公开接口、最近 100 项范围、来源权限、处理轮次、采用身份及修订约束保持现有合同。

| 页面 | 列表 API 耗时，两轮 | 导航至数据显示，两轮 |

| 原始数据 | 20 / 12 ms | 484 / 193 ms |
| 测试集 | 62 / 29 ms | 393 / 263 ms |
| 数据处理 | 1021 / 888 ms | 1229 / 1097 ms |

- 当前服务分析中，首屏 20 项约 851 次 SQL、34 次对象读取；改为仅返回 1 项仍约 831 次 SQL、34 次对象读取。大部分工作发生在分页前，与当前页显示几项关系不大。计数不含测量入口的账号查询。
- 59 项各有一次任务事务、任务行锁及历史轮次查询；同一请求还有约 165 次项目权限 SQL、105 次运行详情 SQL。当前页保存统计仍有 23 次回执查询，旧回执兼容读取造成 34 次对象读取。没有观察到锁等待，不能把锁争用写成本次已证实的主因。
- 批量读取摘要并核对已有同步标记的只读探针约 39 ms，59 项均无需同步；这只是变化检查，不含完整权限、来源校验和响应组装，不能作为完整接口已达标的证据。
- 既有补修 `b799214` 已将更早约 13.8 秒的问题降至约 1 秒，见 [既有加载验证](../loading-verification.md)。本次没有复现 20 秒，不把此前已完成的改进重复记为本张成果。

## 实施范围

### 1. 批量读取任务摘要与访问依据

- 入口复用现有身份与项目权限校验，批量读取任务、必要轮次、来源可用性、发起人和执行状态等列表字段；避免逐项调用完整 `getProcessingRun`。
- 完整任务涉及的历史来源、个人背景所属用户及删除状态仍须校验，不能只检查首轮或最新一轮。不可见项不得泄露名称、数量、状态或影响可见项分页统计；沿用现有跨项目和角色边界。
- 尽量只读所需字段；结果正文、整份输入快照和无关历史大字段不进入摘要查询。当前成果引用和保存统计所需数据尽量延后到当前页读取。
- 保留既有最近范围、排序、搜索、五类状态映射、总数、`hasActive` 和响应字段语义，不扩展公开 API。

### 2. 仅同步确有变化的任务

- 批量读取最新运行/批次事实，复用 `processing_task.applied_run_id`、`applied_hash` 及现有哈希规则判断是否需要同步；不另建缓存版本协议。
- 已同步且未变化的稳定任务不进入逐项 `FOR UPDATE` 事务、不读取处理结果正文。需要同步或尚未建立成果的任务沿用现有成果汇总逻辑，仅在必要范围读取对象。
- 变化预判不能替代事务内校验。实际同步时在已有锁内重读最新事实，保留修订、并发保存/新增轮次保护，防止用过期摘要覆盖新成果。
- 执行中继续显示既有当前成果；部分完成、失败、取消、补齐、重试及同一运行内批次更新均沿用现有规则，不能只凭运行 ID 或“已完成”状态判断不变。

### 3. 合并当前页的保存状态查询

- 回执只在当前页需要计算保存状态时按现有授权范围批量查询，同一请求复用一次查询结果；按稳定候选身份计算已保存/未保存，不逐任务或逐轮重复查询相同回执。
- 保留历史回执缺少 `candidateOrigins` 时的兼容路径；仅对不能由现有回执判定的必要运行回读，并在同一请求内复用结果。不得以省查询为由漏算、重复算或将不确定状态显示为已保存。
- 不批量改写历史回执或用户数据，不添加跨用户全局缓存。正常新回执路径与旧回执兼容路径分别记录耗时及读取量。

## 边界与代码落点

- 主要落点：`src/processing/tasks.ts`、`task-state.ts`、`adoption.ts`，以及必要的权限/来源批量查询复用；实施前核对实际调用方。
- 复用 PostgreSQL 现有表、同步标记和索引；不新增 Redis、队列、数据表、通用列表框架或后台预热服务。只有查询计划证明现有索引不足时才增加针对性索引。
- 不改变模型执行、重试预算、助手规划流程、原件和正式版本；共享读取入口的助手结果仍须一致。
- 页面 UI 继续严格对齐 frontend-v1；保留现有加载过渡、按需刷新和错误反馈，不以延长动画、隐藏加载或只命中前端缓存冒充接口优化。
- 不顺带重构原始数据/测试集列表，不清理用户任务或删除历史数据。本张后续实施沿用当前分支和同一 4217，保留资料与会话；本次写 Ticket 不切换环境。

## 验收与最小验证

先用现有公开列表入口建立能复现逐项查询的定向回归；测试记录 SQL 类别/次数、任务写锁与对象读取，不只依赖易波动的计时断言。复用现有隔离数据、数据库和对象存储测试设施。

| 编号 | 验收内容 |
| --- | --- |
| R19-1 稳定列表 | 已同步、来源有效、使用新格式回执的任务，列表不逐项进入任务写锁或读取处理结果正文；SQL 往返不再随每条任务/每个历史轮次增加一组查询，保存回执每请求最多查询一次。扩大隔离样本后仍满足该约束。 |
| R19-2 变化与并发 | 新任务、执行中至终态、部分完成、失败、取消及同运行补齐后能同步；并发继续处理或保存期间，列表不覆盖新修订、不丢成功结果，刷新后与详情一致。使用可控批次，不调用真实模型批量造数。 |
| R19-3 权限与分页 | 超过 100 项且夹有不可见项的隔离样本中，完整任务可见性、最近范围、搜索/空态、五类状态、分页总数和 `hasActive` 与旧合同一致；覆盖查看角色、其他项目、私人背景、历史来源失效。 |
| R19-4 保存兼容 | 未保存、部分保存、全部保存、跨轮稳定身份以及旧回执缺少来源身份的统计准确；必要旧运行同请求最多回读一次。不能要求旧数据迁移后才可使用。 |
| R19-5 性能 | 在同一 59 项稳定数据及同等服务环境，首屏 20 项 API 的连续 5 次请求中位数目标 ≤300 ms；记录首次请求、每次耗时、SQL 和对象读取量，与约 0.9–1.0 秒基线对照。禁用浏览器响应缓存；需要同步的首次请求和旧回执兼容耗时另列，不删掉较慢样本。未达标须说明剩余开销，不宣称已达标。 |
| R19-6 页面与交付 | 定向检查首次进入、刷新、搜索/筛选、返回列表及读取失败恢复，状态和保存计数与详情一致；原始数据/测试集正常。UI 无样式漂移。记录实际应用版本及未重建服务，不进行 5/10 人压测、长时间稳定性试验或服务器重启测试。 |

实施完成时在本规格关联验证记录，按实际接口/查询变化最小更新架构和测试文档；产品行为未变时不复制或重写 PRD。类型检查、相关集成回归及受影响前端检查按变更选择，不重复跑无关全量流程。实施完成与 Owner 验收分开记录，不授权合并、推送、tag 或正式部署。
