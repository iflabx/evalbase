## 保存目标修改漏执行：审查后补强方案（2026-10-30）

状态：方案已按 Owner 要求更新，尚未实施或复测。本节是本次修复的唯一详细方案；上述失败记录和已通过部分保持原结论。适用合同见[总 Spec](../spec.md)、[重建架构](../../../docs/architecture/assistant-rebuild.md)。

### 1. 根因与修复范围

首次明确要求“只把保存名称改成…先不要继续”后，模型返回文字，未调用 update_requirements；工具当时可见，请求 HTTP 200，没有触发参数错误。现有 assertResolved 仅核对已发生工具错误的 pending，暂停分支只补遗漏的继续命令，没有核对修改是否真正提交。普通“继续”的名称检查只读取当前消息，未保存上一轮遗漏修改，因此无法完整阻止沿旧目标恢复。

现有 feedback 同时承载工具纠错，restoreSuspended 又会从旧暂停快照恢复该字段；直接把新修改意图塞进 feedback 会引入覆盖风险。此次补齐“明确请求 → 持久待完成修改 → 业务提交 → 事实核对 → 恢复/确认”的合同，不再仅增加提示词。

范围限定为当前已开放的保存目标名称修改。复用既有交付绑定、update_requirements、修订校验、受保护提交、预算及恢复入口；允许必要结构调整，不新增通用意图模型、第二套编排或纠错引擎，不扩展生成、多交付或已保存草稿改名功能。已有草稿自身名称修改属于原业务命令，不能与尚未采用的 saveTarget 混同。

### 2. 指令与状态合同

- 将命令判断和名称提取分开；requestedSaveName 仅能作为提取辅助，不能凭匹配片段创建写授权。核对整条用户指令、当前会话对象与控制语义，覆盖有/无引号的普通明确改名表达。
- “不要改成X”“是不是已保存为X”、引用示例、文档正文和纯查询不产生修改义务。混合指令或对象歧义无法可靠绑定时明确澄清，不静默新增交付、不猜测目标。只改名保持暂停；改名并继续须分别满足修改完成和继续授权。
- 使用已有持久存储承载独立的待完成修改事实，不能依靠模型历史、临时变量、参数纠错 feedback 或旧暂停快照。实施时选择最小兼容存储方式，不要求另建表或任务平台。
- 该事实至少能关联原用户消息/修改身份、项目/会话/任务及交付身份、目标字段与目标名称、基础要求修订、保持暂停或明确继续的授权、处理结果和已消耗的恢复尝试。凭据不进入记录；重复消息沿用原身份。
- 生命周期区分待完成、已完成、明确撤销、被新指令替代；冲突及额度不足保留待完成原因。只读查询、普通“继续”、断线、重启、检查点重放、工具纠错成功和旧暂停快照恢复均不能擅自清除它。
- 连续修改名称时，新指令替代同一目标的旧待修改要求，保留历史；迟到旧响应不得清除或完成新的要求。用户明确撤销的只是本项未完成修改，不回滚已提交业务、不等于取消交付，也不自动授权继续。

### 3. 提交、完成与恢复

1. 在模型执行前，将可靠识别且完成对象绑定的修改要求持久化；未能绑定的明确歧义进入现有澄清流程，不按旧目标推进。
2. 通过原 update_requirements 及授权/修订/幂等保护修改，不由宿主直接写业务表。原来源、记录范围、数量、加工规则及处理成果不因单独改名失效，不重复处理。
3. 每轮结束和恢复前，以同一交付的实际 saveTarget 名称核对完成；模型承诺、工具调用次数、display name 或修订号增长都不是完成证据。名称已是目标值时允许幂等成功，无需强制增加修订。
4. 基础修订冲突时不自动换最新修订覆盖。业务提交、完成标记及确认失效需具备一致性；若不能同事务落地，重启必须先查原业务回执和当前目标对账，不换键重写。已提交但回执传输丢失与真正未修改须区分。
5. 模型未调用所需工具时，复用宿主 required-tool 机制发起最多一次补调用恢复，仍走同一 Schema、业务校验和受保护提交。参数仍错误时沿原纠错链处理，不能重新套一轮新修复预算；其他错误或无进展不能通过不断重启补调用循环。
6. 普通继续、服务端恢复入口、检查点/后台自动续步、准备采用确认和确认消费共用待修改检查。只阻止受影响目标的后续写入，查询、查看已有成果及明确撤销仍可用；不扩大为全项目禁用。
7. 待修改期间旧确认卡不可消费，界面同步呈现不可用原因；修改提交后旧修订确认必须失效。“只改名、不继续”完成后仍暂停，明确继续后才准备匹配当前目标的新确认卡。撤销未完成修改后重新核对原目标，不复活已失效卡片。
8. 修改与确认并发以事务顺序确定：修改先受理则旧目标确认被拒；保存已先提交则保留真实成果并说明已保存，不能假称改了原保存结果或偷偷再建一份。

### 4. 预算、消息与状态

- 漏调用恢复、参数纠错和传输重试共用原任务/活动实际请求账本，分别记录原因；补调用次数持久化，刷新、普通继续及重启不重置。下一次显式新修改可有自己的修改身份，但不能增加任务总余额。
- 达到请求、时间或无进展上限即停止额外调用，保留待完成修改及原成果；后续查询仍诚实说明原因。用户“继续”不等于追加额度。
- 修改成功且要求保持暂停：简短展示实际目标名称，并明确仍暂停、未保存成果。修改未完成：明确“保存名称尚未修改，任务保持暂停”，不以整轮成功文案掩盖失败。
- 当前消息处理结束与用户业务要求完成分开投影；补调用仍失败不能记为修改成功。保存已经成功时也不能被后续解释失败改写为业务保存失败。历史消息、旧失败事件和回执不回填。
- UI 复用既有暂停/提示/确认状态，严格沿用 frontend-v1，不新增配置页或要求普通用户填写内部参数。
