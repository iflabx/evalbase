## 1. 目标与复杂度边界

用户在一个会话中，以简短要求完成“选资料 → 理解要求 → 处理 → 核对 → 局部调整 → 确认保存”，无需了解内部工具、运行编号、批次及修订号。独立页面为这个连续过程提供足够空间。

本轮优先让执行可解释、可继续、结果可核对。模型或服务仍可能失败；不承诺零错误，也不把隐藏报错、延长等待、增加重试次数当作稳定性提升。是否改善以同一批真实短请求及可控故障测试为准。

| 保留并复用 | 本轮补齐 | 暂不纳入 |
| --- | --- | --- |
| AI SDK、现有兼容模型连接、Fastify、PostgreSQL、MinIO、Worker | 对话层错误分类、有界恢复、统一诊断与固定测试基线 | 更换 Agent 框架、微服务拆分、Redis、新队列 |
| 个人会话、当前 task、步骤、固定输入、processing run、proposal、业务回执 | 简化模型参数，稳定要求身份，按阶段提供工具 | 多智能体、通用 DAG、可视化流程编排器、插件市场 |
| PDF/MD/TXT 背景与已有来源读取 | 有界事实摘要、已验证背景引用 | 向量库、跨会话记忆平台、OCR、任意网页读取 |
| 原始数据、测试集、数据处理及候选表组件 | 独立助手页面、整任务结果审核、准确恢复入口 | 自由拖拽工作台、第二套任务/候选数据库、供应商风格 UI |

不新增常驻服务或独立数据表。优先使用现有 task/turn 的 JSON、诊断和引用字段；新增可选字段须有兼容读取。若实施发现必须改变核心存储或扩大权限，先列出具体必要性及设计差异，不默认升级成本轮基础设施改造。

## 2. 当前问题与改进对应

| 已确认事实或风险 | 对用户的影响 | 对应改进 |
| --- | --- | --- |
| 对话模型异常归类较粗，普通临时请求错误直接结束 | 用户难分辨该重试、改要求还是找管理员 | OPT-20 分类与诊断；OPT-21 有界恢复 |
| `plan_task` 参数多，普通步骤通常暴露整套 14 个工具 | 明确的需求仍可能生成互相冲突的参数 | OPT-22 只补充当前动作所需意图，服务端绑定既有事实 |
| 相同独立要求仅重排就可能重置已完成读取步骤，已通过实际规范化路径复现 | 无意义的重新读取和恢复成本 | OPT-22 稳定要求比较，保留真实回执 |
| 最近 6 回合和粗粒度工具内容截断；背景定义反复抄写 | 长会话引用丢失、参数过长的风险；尚未证明是全部故障原因 | OPT-23 结构化事实、可再读取引用、背景定义复用 |
| 抽屉分列挤压；会话没有独立地址；候选预览常以运行批次为入口 | 用户难持续工作，也难分清当前完整成果 | OPT-24 独立页面；OPT-25 整任务审核 |
| 已有真实模型脚本，但没有统一、可重复的任务级比较口径 | 不知道代码修复实际改善了多少 | OPT-20 建基线，后续各张只重跑受影响案例 |

旧会话错误次数不作为当前版本失败率；研究报告中已区分已复现问题、静态事实和待验证风险。

## 3. 推荐执行架构

沿用现有链路：用户消息进入会话，由模型理解目标；服务端规范化要求、绑定对象并检查权限；现有步骤执行器调用业务服务；耗时处理交给 Worker；完整结果经服务端核对后进入人工审核与确认。

### 3.1 职责分工

| 位置 | 负责 | 不承担 |
| --- | --- | --- |
| 模型 | 理解自然语言、提出业务步骤、语义改写/生成、解释真实结果 | 自行计算权威数量、发明对象 ID、判定写入已成功、授予权限 |
| 当前任务和约束入口 | 当前目标、来源范围、字段保护、数量规则、背景依据、步骤及修订 | 从历史聊天拼凑另一份权威任务 |
| 现有执行器 | 固定范围、顺序推进、权限和停止检查、操作幂等、真实回执对账 | 无限自循环、通过重规划解除未知写入绑定 |
| Processing Worker | 已冻结输入的分批处理、有效产物保留、现有失败/补齐预算 | 接受聊天临时改写正在运行的输入 |
| 项目助手页面 | 展示当前事实、选取/审核、明确确认和恢复动作 | 独立推算完成状态、客户端批准写入 |

不是每个问题都必须先生成计划。查询可以直接回答；简单处理直接提交已有业务能力；复杂要求才保留有序步骤。“先设计方案”不执行写操作；“按方案执行”沿当前方案继续。已明确要求执行的请求不再重复询问开工。

### 3.2 轻量工具与要求合同

1. 保留现有业务工具和步骤执行器，不新增一套同义工具平台。模型侧采用薄的动作参数投影，随后进入同一规范化和业务校验入口。
2. 来源、已固定的记录选择、当前草稿、步骤、操作键和已完成数量由服务端从 task/回执解析。模型只在用户改变它们或尚未明确时提出新意图，不能静默改范围。
3. “未提供字段”保留旧值；“明确替换/撤销”更新或清除。使用当前能力表达此区别，不要求模型重填整个任务。接口简化时退出被替代的模型侧分支及提示词补丁，旧持久记录保留兼容读取。
4. 独立要求清单比较采用精确文本规范化、去完全相同项及稳定排序；有序处理步骤仍保序。自由文本实质变化不能被忽略，不做自动语义等价判定。展示顺序不承担步骤身份。
5. 约束变化只使确实受影响的步骤、核对或待确认操作重新核对。无法证明可复用时保留成果并撤销其执行/采用资格，不自动全量重跑，也不删除历史产物。
6. 模型可用工具集合由已持久化的任务状态和权限决定，不按用户消息关键词猜阶段。只对当前有意义的工具开放；服务端校验仍是最终边界。

| 当前阶段 | 可用能力 | 关键限制 |
| --- | --- | --- |
| 查询/理解 | 查询授权对象、读资料/背景、整理要求、必要澄清 | 不提供未经授权的后台提交或确认 |
| 规划 | 补读、更新目标/步骤、检查规则 | 仅要求方案时禁止产生业务写入 |
| 执行 | 补读、修正合法参数、提交当前允许步骤、读取真实回执 | 不绕过前序条件或转换未授权来源 |
| 后台等待 | 由已有调度器等终态并推进 | 不启动模型循环反复查状态 |
| 核对/局部调整 | 汇总有效成果、检查缺口、按明确选择调整、生成固定提案 | 不把局部调整变成全量重做 |
| 待确认 | 解释当前结果、必要查询；用户更正则更新任务并作废旧卡 | 模型不能确认采用/发布；没有新事件不空转 |

补读和纠错通道必须保留，避免阶段收窄后无法修复缺失参数。功能受限通过明确错误返回，不把禁用工具伪装成成功。

## 4. 失败如何恢复

### 4.1 同一错误合同

模型请求、工具校验和业务提交返回统一可解释的信息：失败层、类别、当前步骤、是否已发生副作用、已保留成果、可用恢复动作、关联诊断编号。普通用户看到简短原因和操作；HTTP 状态、模型配置修订、契约版本、耗时及尝试次数写入现有受控诊断，不展示密钥、系统提示或完整业务正文。

| 情况 | 自动处理 | 用户看到 |
| --- | --- | --- |
| 429、明确临时 5xx、连接短暂中断 | 总预算内重试同一次模型请求 | “模型服务暂时繁忙，正在重试”；失败后保留成果 |
| 模型参数/结构不合法，已证实未执行 | 给字段级反馈，允许预算内纠正；沿用连续同错停止规则 | 不能恢复时显示缺少/冲突的字段和下一动作 |
| 401/403、端点/模型不兼容、确定性配置错误 | 不自动重试 | 提示管理员检查配置；无原始错误正文泄露 |
| 权限变化、来源失效、草稿修订冲突 | 停止受影响的操作 | 恢复权限、重选来源或核对草稿；不自动覆盖 |
| 操作已提交但响应丢失或结果未知 | 以原操作键先查询真实回执 | “正在核对已执行操作”；无证据不显示失败重做 |
| 输出缺失、重复或部分失败 | 复用现有处理/去重/补齐机制和批次预算 | 有效数量、剩余缺口、继续或审核已有结果 |
| 总预算耗尽、反复无进展 | 保存检查点和已有成果，停止自动续做 | 暂停位置、具体原因及有效恢复入口 |
| 数据处理成功但最后说明生成失败 | 直接按回执显示成果和下一步 | 结果仍可查看；不要求重新处理 |

### 4.2 明确预算，避免重试叠加

- 对话传输层每个请求最多 2 次额外尝试；**单回合所有模型请求共用最多 2 次传输重试额度**。首次退避约 0.5 秒、第二次约 1 秒，可有小幅抖动。合法 `Retry-After` 优先；等待超过剩余预算时结束并提示，不睡到超时后再发请求。
- 复用现有 80 秒模型等待总截止时间，90 秒回合租约、10 模型步骤、12 工具调用、12 次自动续做及现有 executor 限额不提高。每次等待和请求都使用同一截止信号；预算耗尽、停止和撤权立即终止。传输尝试单独计数，模型纠错仍占原步骤额度。
- 只选一个对话请求层实施重试；SDK、provider fetch 和外层 `generate` 不能同时叠加。不得为了重试而重新执行整次 agent 循环。未完整收到并验证的模型响应不能触发业务工具。
- Worker 已有批次恢复额度继续独立管理，沿用 OPT-18/P1 修复的累计预算。对话重试不能重置 Worker 失败次数，手工继续不能变成新预算的无限入口。
- 未知业务写入只能对账；原操作键、任务修订及停止令牌必须保持。重复确认或网络恢复不得产生重复采用/发布。
- 复用现有无进展检测，补充“相同输入/约束、没有新回执或成果”的判断证据；暂不开发独立循环检测平台或 critic 智能体。

## 5. 长会话与背景文档

### 5.1 上下文按事实组织

模型每轮收到：当前用户请求、权限内的对象摘要、当前有效要求、固定输入/选中范围、已完成成果引用、待解决事项，以及预算内的近期对话。任务事实从现有持久 task/回执生成，不增加另一份靠模型写入的长期记忆。

- 保留最近对话的既有上限，先让工具回执返回“结果摘要 + 可再次读取引用”；大正文仍按需分页读取。必要的调用与结果成对存在，不因截断产生孤立工具消息。
- “刚才那几条”仅在存在唯一、仍有效的选择引用时解析；候选修订变化或指代多义时显示当前范围并澄清，不能默认全选。
- 用户撤销或更正后，模型和界面都读取同一生效状态；旧说法可以在历史中保留，但标明已被替代，不能再约束下一次处理。
- 刷新、页面跳转、回合预算结束后仍能从数据库恢复任务；未发出的编辑框内容不等于服务端已接收的要求。

### 5.2 背景依据用可验证引用复用

- 保留 PDF/MD/TXT 提取、容量、个人会话归属、页/行定位和删除语义，不增加知识库或文档自动执行能力。
- 首次读取仍须确认相关正文与类别/定义对应；不能把一个编号或任意片段存在视为已验证。
- 对已确认的定义提供会话内引用，绑定附件、提取版本/哈希、页/行范围与原文。后续工具只提交引用，服务端恢复同一原文并进入既有校验与冻结快照，减少模型反复抄写。
- 同一背景未变时可复用；被移除、哈希/规则变化或权限失效时不能继续引用。用户自定义兜底类别仍需要真实用户要求，不能伪装成标准原文。
- 旧 definitions 记录继续校验读取；只有当前需要的定义按需转换，不批量改写历史会话。使用现有规则/依据 JSON 保存引用，无独立引用服务。

## 6. 独立项目助手页面

### 6.1 导航与会话

- 新路由：`/projects/:projectId/assistant`；具体会话：`/projects/:projectId/assistant/:sessionId`。URL 可刷新、返回及定位，鉴权后才能读取。
- 项目侧栏“项目助手”与原始数据、测试集、数据处理并列。顶部和对象页的既有助手入口统一导航到此页；正式切换后不长期维护功能完整的旧抽屉。
- 项目助手首页恢复本账号在该项目最后打开的可用会话；没有会话时显示新会话空态。失效链接说明不可访问，不泄露其所属账号或项目。新会话仅在现有创建动作发生时保存，避免打开页面就产生空会话。
- 会话列表可收起，支持搜索名称、创建、重命名和删除；复用现有分页和管理 API，不因搜索一次加载所有消息。若当前清单接口缺少搜索，仅补同一授权清单的名称过滤及分页，不新建搜索服务。
- 个人会话仍只属于本人；管理员不因角色获得他人聊天内容。查看角色只能查询其获权的正式内容，不见草稿和未发布处理正文。

### 6.2 布局和信息顺序

| 区域 | 常驻内容 | 按需展开 |
| --- | --- | --- |
| 会话栏 | 会话名称、当前会话、新会话入口 | 搜索、更多操作；可整体收起 |
| 页头 | 会话名称、当前任务的简短真实状态 | 当前对象与目标详情、停止/恢复 |
| 对话区 | 用户消息、简短助手回复、当前需要处理的事项、输入框 | 历史操作明细、旧步骤 |
| 工作区 | “结果”“资料与要求”两个业务页签 | 结果详情/来源、完整方案、历史批次 |

无结果时对话区占主要空间，工作区按需打开；进入结果审核后工作区默认展开，聊天约占 35%、结果约占 65% 的可用内容宽度。提供“展开结果”使结果使用整块主内容区；不用拖拽分栏库。

当扣除项目导航后主内容不足约 1,100px，聊天与工作区改为页签切换，保留输入、选择和各自滚动位置；会话栏收起，避免在笔记本上出现四列窄面板。长表格仅自身滚动，页面不横向溢出。焦点、键盘、窄窗口及 reduced-motion 沿用现有组件能力。

页头只保留一处当前阶段；同一数量和当前要求不在聊天、任务卡、状态卡反复复制。只展示真实步骤、已完成/目标数量和更新时间，不制造百分比、预计完成时间或模型思维链。

### 6.3 输入、附件与对象上下文

- 用户直接发短提示；空态提供“整理这份资料”“基于现有题目扩写”“先帮我设计方案”等少量示例，点击只填入输入框，不自动执行。
- 输入框提供背景附件和选择资料入口。背景附件沿用已有 PDF/MD/TXT；原始数据上传继续走已有解析与映射流程，不把背景文件当成可直接采用的记录。
- 从资料/草稿/版本进入时带入经服务端校验的对象上下文，并在输入框上方显示简短对象标签。仅导航或选择新对象不会修改正在执行的任务；用户发送要求后才形成相应意图。删除标签不删除数据。
- 有有效固定选择时携带现有选择引用，不能仅靠“当前页 10 条”文本定义范围；没有固定引用就只带对象，不声称已经带入记录选择。
- 保存未发送输入；提交失败使用同一消息和幂等键重试，不清掉后来输入。运行中可继续编辑草稿文字，但不建立新的并行发送队列；沿用同会话单次执行约束。用户需要中断时使用现有停止，再发送修订要求。

### 6.4 消息与动作

- 助手回复支持安全的段落、列表、代码块和简单表格；复用已有 Markdown 依赖或最小必要渲染，禁用原始 HTML、远程内嵌资源和执行式链接。不将模型文本解析为操作卡。
- “查看结果”“继续未完成步骤”“确认保存”“发布”等按钮来自服务端已验证的事实/提案。纯文本说“完成”不能产生成功状态或替代确认。
- 如果用户明确只要方案，可显示“按方案执行”，通过现有用户消息入口表达执行意图，并绑定当前方案修订；旧方案变化后不能执行旧卡。不增加绕过 Agent/权限校验的通用执行接口。
- 错误区仅在确有问题时出现，显示原因、保留成果与恢复动作。等待后台和等待用户确认是正常阶段；不会为了避免红字而把失败显示为成功。

### 6.5 frontend-v1 对齐

复用 donor 的项目壳、字体、背景、浅边框、圆角、按钮、图标、表格、输入框、对话框和 tooltip。帮助提示延续现有浅色浮层；正常页面不堆积说明卡，不使用大面积深色块。新布局按上述顺序落到 `frontend-v3/`；不改 donor 或冻结原型，不复制 Codex/DeepSeek 的视觉皮肤。

本方案记录 Owner 授权的新页面行为修订；无需另开发一套原型工程才能开始。OPT-24 的局部布局与真实空态/运行/审核状态一起验收。

## 7. 完整结果审核与保存

### 7.1 单一当前成果

默认查看当前助手任务的完整有效候选；历史批次入口用于追溯。不能把一个运行的 10 条预览与整任务 200 条统计混在一起。

- 复用 OPT-10/17 的有效集合、稳定来源/候选身份、替换/追加/排除和保存回执逻辑。助手任务可关联多个处理任务/运行，按助手当前任务的真实有效引用汇总，不假设二者一一对应。
- 后续调整替换选中候选；未选项保留。扩写新增项按新增身份计数，参考输入不计入新增成果；被取代、排除、失败或不符合当前约束的历史产物不混入可采用总数。
- 前后端使用同一有效集合处理统计、搜索、分页、结构核对和采用。每行携带当前实际运行/结果引用及稳定采用身份，不能仅以表格下标定位。
- 当前 API 若只支持 `run`，在既有会话候选入口增加明确的任务范围读取模式；保留 `run` 为历史批次查看。任务模式不能接受前端任意拼接的运行清单。服务端返回由当前任务修订和有效结果派生的 `reviewRevision`，不建新的候选表。
- 选择绑定当前任务、有效集合修订和稳定行身份；结果发生替换/排除时重新核对选择。旧范围不能静默映射为另一批数据，已失效选择提示重新确认。

### 7.2 用户操作

- 默认列：问题、期望输出、Metadata、来源；保留搜索、现有筛选、分页、选择本页/全部匹配和记录详情。来源区分“该记录来源”与“本次生成的参考范围”，不假称精确逐条生成依据。
- 结构问题可筛选，去重和补齐复用已有数据处理能力。结构通过与内容审核分开，生成内容不会自动标为语义正确。
- 用户选中若干行后发送“这几条改得更口语化”等简短指令；输入区显示“仅调整已选 N 条”。服务端冻结准确范围，修改后保留其余成果和原草稿冲突基线。
- 从草稿发起的任务默认“保存回原草稿”；新建任务显示实际目标，其他保存去向收纳为次级入口。保存/发布前展示目标、数量和影响，复用现有确认卡及修订检查，不新增重复确认。
- 保存成功显示真实草稿/资料链接；用户目标含发布时再使用现有发布确认。查看结果、后台受理、结构检查完成都不能冒充交付成功。
- 用户只采用部分结果时准确标明部分，历史结果和当前已保存状态可追溯；连续点击或网络丢响应不得重复追加。

## 8. 读取与性能

- 页面先读会话清单和当前轻量状态；按需分页读消息，打开结果区再读候选，打开资料/要求或明细再加载大正文。后台状态轮询不得反复传整段聊天或候选正文。
- 优先扩展/裁剪已有 status 响应，不新建实时事件系统。活跃任务沿用当前约 1.5–2 秒轮询；待确认/终态停止活跃轮询，隐藏页面降低频率或暂停，回到前台/用户动作后重新核对。
- 会话、项目或权限切换时取消旧请求并隔离查询缓存；旧响应不能覆盖新会话，403 立即清除无权正文。返回页面不重复提交消息或任务。
- 沿用现有加载骨架和保留旧数据的刷新方式。不能用更长动画掩盖接口延迟；分别记录首屏状态、历史消息和首批结果的实际耗时、请求数及字节数。
- 使用现有 query 状态与组件；不新增跨账号全局缓存、全量预加载、websocket/SSE 服务或新监控平台。

## 9. 具体用户流程与测试口径

### 9.1 目标流程示例

1. 在原始数据选择一个文件，进入项目助手；输入“帮我整理这份资料，先给个方案”。助手读取必要摘要并给出方案，不创建处理任务。
2. 用户说“按方案做”；当前有效资料、目标、字段保护和步骤由服务端绑定，助手提交后台处理并显示真实进度。
3. 结果出现后在同一页面审核整任务候选；选中两条，说“这两条改得更自然一点”，只调整选中项。
4. 用户点击保存确认；原草稿场景保存回原草稿。刷新后实际内容和来源一致；需要发布时另按既有发布确认操作。

这些是验收提示词示例，不是用户必须背诵的固定命令。缺少实质业务选择时允许一次针对性的澄清；技术 ID、配额计算和下一工具不由用户补填。

### 9.2 固定基线

复用已有 HTTP 假模型/隔离持久化及真实模型脚本，整理为一个小型入口，支持按案例选择和输出结果 JSON；不开发评测平台。基线包括以下 10 类，完整断言由对应 Ticket 管理：

| 案例 | 短请求/场景 | 最终检查 |
| --- | --- | --- |
| A1 查询 | “这份资料有多少条，包含哪些字段？” | 正确范围与真实统计，无业务写入 |
| A2 只规划后执行 | “整理这份资料，先给方案” → “按方案做” | 规划不写入，执行沿最新方案，无空计划卡死 |
| A3 确定性清洗 | “清理这份资料的多余空白” | 只改授权内容，其他字段不变 |
| A4 扩写 | “参考这些题再扩写 8 条” | 新增数量真实，参考输入不计入成果；重复/缺口可解释 |
| A5 局部改写 | 选 2 条 → “这两条更口语化一点” | 只改选中项，稳定身份与其余成果保留 |
| A6 要求更正 | 调整数目/撤销要求/仅重排独立要求 | 新要求唯一生效；无意义重排不重做步骤 |
| A7 长会话 | 超过 6 回合后“按刚才的要求继续” | 当前约束与固定引用可恢复；模糊指代不扩大范围 |
| A8 背景依据 | 附小型文档 → “按附件分类，保留原题” | 引用真实，分类与字段保护可核对；不把结构检查当语义通过 |
| A9 故障恢复 | 注入暂时故障、无效参数、未知写入响应、预算耗尽 | 有界恢复，不重复写入，正确保留成果/解释暂停 |
| A10 保存/发布 | “保存到这个草稿”及显式发布目标 | 真实固定确认、冲突保护、回执、刷新和成果链接一致 |

OPT-20 先记录修复前基线，不以必须全部通过阻止开始修复。每张只重跑受影响案例；最终固定 HEAD 汇总一次。A9 的可控故障主要用假模型，不对真实服务制造故障。

真实模型的小样本：A1–A8 与 A10 各执行一次；A2/A4/A5 各再重复两次，分别记录总次数、成功数、自动恢复、需要用户澄清/额外提示、人工内容修正、耗时和 token（provider 提供时）。同一最终 HEAD 下重复案例直接复用，不再每张全跑。原始输入/要求不变时比较修复前后结果；未拿到完整数据就报告样本数与限制，不声称统计意义的稳定率。

### 9.3 完成门槛

- 权限、未知写入、确认、幂等、字段保护及修订冲突的确定性回归全部通过，无剩余 P0/P1。
- 上述小样本不得再依靠补充内部工具/ID/批次的长提示才能完成；未完成项必须记录原因并修复可复现的编排缺陷，不能通过删困难案例达标。
- 已完成处理但模型总结失败仍可直接审核；刷新/离开页面后可恢复；结果数量与实际采用/发布内容一致。
- A2/A4/A5 的同版本重复样本逐次列出结果；语义错误、人工修改和自动恢复分开计数，不以全量 schema 通过替代内容质量。
- 小样本通过后再做一次同会话 200 条集成任务，使用已授权资料的隔离副本/新产物；全量结构与来源校验，内容审核记录实际范围和修改数。未核对全部内容不能称“200 条全部可用”。旧 OPT-05/09 的人工验收仍由 Owner 决定。
- 默认串行执行真实模型样本，不加 5/10 人压测、两小时稳定试验或服务器重启测试。不在 Owner 正在使用的会话中故意制造失败，不自动采用/发布其现有候选。
