## 1. 决策与完成目标

采用现有 AI SDK 和业务执行器内的机制整理：统一参数失败分流、要求修改、恢复资格及状态投影，保留现有模型连接、PostgreSQL、MinIO、Worker、权限和业务回执。目标是让普通请求和连续更正经过同一套可验证规则，失败后有可执行的恢复动作。

| 备选方式 | 本次取舍 |
| --- | --- |
| 继续按单个错误追加修补 | 可用于独立缺陷；本次已有共享判断冲突，须整理共同合同 |
| 在现有执行器内收敛职责 | 采用；直接覆盖已证实根因，可沿现有业务接口验证和逐阶段接入 |
| 更换运行时或增加通用工作流层 | 当前证据指向业务合同与恢复判断；暂无因此扩大技术栈的必要性 |

本次选择依据是实际工具回执与代码中的重复判断；未新增框架对照实验，不宣称该方案保证任意模型零失败。模型服务拒绝、真实业务歧义和预算用尽仍可能停止任务，停止时须保存事实并说明下一步。

实施范围以完整根因及直接共享合同为单位。允许合并重复判断、提取有实际调用者的共用模块、调整内部接口和删除替代路径；每项结构调整要说明解决的职责冲突、调用者、兼容方式和验证路径。保留现有单执行器、有限业务动作和持久化模型，按需增补现有 JSON/DTO 的可选字段。若发现必须新增表、外部框架或扩大公开能力，应先记录证据与具体设计差异。

UI 继续使用 frontend-v1 的组件、文字层级、密度与状态样式，正式代码位于 frontend-v3。当前阶段沿用人工内容审核；本次完成目标为流程、合同与恢复正确，不重新启动旧 248/400 条质量验收，不将历史质量问题改签通过。

## 2. 当前机制与拟调整后的流程

| 环节 | 当前已确认问题 | 调整后的责任 |
| --- | --- | --- |
| 输入与要求 | 修改数量时模型重写完整交付，带入无关场景错误 | 模型提出本次变更；服务端合并原事实、计算派生值并校验 |
| 参数校验 | 缺必填与 minItems 分走不同纠错路径，语义缺失进入无损修复 | 同一失败分类器根据错误路径、现有事实和业务含义选择恢复 |
| 执行与恢复 | 重试资格、模型请求预留时间、前端按钮各自判断 | 一个恢复决策供会话读取、控制请求和执行前校验共用 |
| 提示 | “已有原始资料”被执行声明正则误判，覆盖真实补充要求 | 提示优先来自已持久的阻塞原因和真实回执 |
| 诊断 | 同一 turnId 的重试替换首次失败 | 按轮次和尝试保存过程，关联最初失败与恢复结果 |

正常流程：普通请求 → 当前对象/背景/要求 → 业务变更提议 → 规范化、合并与完整校验 → 原子保存生效要求 → 既有执行器按真实回执推进 → 结果审核与固定确认。

失败流程：记录尝试及原始错误 → 判定是机械纠错、上下文修正、业务澄清、回执核对或预算暂停 → 在同一授权及累计预算内恢复 → 校验当前修订后保存/执行。校验失败不提交业务副作用，也不把未保存变更展示为已生效。

## 3. 责任落点与替代关系

优先在已有模块收敛职责，不按本表强制新增文件或通用接口。

| 现有位置 | 应承担的统一责任 | 退出或收敛的重复行为 |
| --- | --- | --- |
| assistant/tool-repair.ts 与工具实际 validator | 错误分类、无损归一、有限修复及再次校验 | 每个工具独立追加外层修复循环；只按错误文案猜测分流 |
| assistant/delivery-plan.ts、requirements.ts 及 plan_task 保存路径 | 局部变更合并、派生数量、依赖失效、原子生效 | 模型重复维护展示总数；局部保存与整份计划更新的不同语义 |
| assistant/budget.ts、tasks.ts 与现有恢复入口 | 实际可用额度、恢复方式、幂等领取和执行前复检 | canResume、请求预留时间、按钮各自制定条件 |
| assistant/store.ts 与 agent.ts 最终回复路径 | 由阻塞事实、保存回执与运行回执投影状态/提示 | 服务端事实被自然语言关键词过滤覆盖；模型解释代替保存事实 |
| assistant/diagnostics.ts 与现有 JSON 观察记录 | 尝试级诊断、恢复关联与累计计数 | 用同一 turnId 的最终结果抹去前次失败 |
| frontend-v3 项目助手 | 展示服务端恢复能力，提交失败后刷新状态，保留输入 | 前端独立认定可恢复；持续显示已失效按钮 |

agent.ts 保留 SDK 接线与业务工具适配。提取真正被多个入口共享的决策，不拆出只有转发作用的模块。每阶段接入时同步移除被替代的新任务路径；历史冻结合同按既有版本明确兼容，读取旧任务不写回迁移、不触发重跑。

## 4. 参数失败分类与有界纠错

| 失败类别 | 判定与处理 | 用户体验 |
| --- | --- | --- |
| 无损格式问题 | 白名单可逆归一，如已知结构包装/容器解析；完整 validator 通过且语义不变才使用 | 无需用户提供工具参数 |
| 业务值或结构不足 | required、minItems、配额/数量冲突等结合实际合同判断；先利用已保存合法事实，仍不足才让模型作受限上下文修正 | 不让无损修复凭空新增场景或删除约束 |
| 引用问题 | 只从有权限的真实对象/背景目录绑定；无法确认则限定读取或询问业务对象 | 不猜 ID、不扩大数据范围 |
| 截断/不可解析输出 | 记录 finishReason、长度与解析错误；一次受限重提只包含待变更交付和必要依据，完整校验后才能执行 | 保留旧方案和本次修改意图 |
| 真正用户业务歧义 | 无法由现有要求、文档或事实确定的选择 | 只问缺少的业务信息，已给信息不重复询问 |
| 未知副作用 | 超时/断线无法判断写入结果时先按原 operation ID 查回执 | 已完成操作不重复提交 |

分类器以实际 validator 的结构化错误为输入。关键词名只作为证据之一；例如 required 字段若可从同修订已保存事实补齐，不必请求模型；minItems 若需要创造新业务内容，就不能进入无损格式纠错。

同一业务修改共用既有修复额度：机械修复、上下文修正和截断重提共享最多 2 次额外纠正请求，并受更小的剩余模型/时间/验证限额约束。复用现有修复计数，不再叠加“每层各两次”。本地成功归一不额外请求模型；跨重试/续段仍继承该修改的已耗额度。错误路径及有效输入均无进展时停止自动重复。

多交付只向修正请求投影出错的交付、用户本次更正及必要事实，修复后合回原请求并做完整校验。合法分类、未改交付、背景和权限不能通过省略/清空来绕过校验。未确认允许的请求重构归入上下文修正，不作为无损修复。

## 5. 要求修改：先合并校验，再整体生效

继续以 executionPlan 中的交付目标及现有生效要求为权威，不增加第二份长期计划。

1. 已有 deliveryId 的输入表达本次变更，字段缺省表示保留；清除只接受现有合同允许且明确的空值/删除动作。新交付走完整创建校验，避免为修复旧交付而放松新建约束。
2. 数量修改保留未要求改变的场景和依据。2 条或 1 条生成目标不等于场景清单必须缩成 2 项或 1 项；既有合法场景可继续由分配器使用。
3. 服务端从各交付计算整体总数和展示摘要。单一类别配额可按明确新数量派生；多类别明确配额与新总数冲突时，按已授权分配规则处理，无规则则只澄清分配选择，不能随意删类别或按比例猜测。
4. 结构化数量和规则决定展示；模型生成的派生描述从当前事实重建。用户原始描述中的业务条件保留，不用全局数字替换改写正文。无法确认是旧派生描述还是用户显式约束时保留待核对。
5. 复用现有待修改/恢复记录保存本次意图及基准修订；校验成功后同事务更新生效要求、执行资格与必要确认失效。失败时旧方案仍可查看，本次修改明确标为未生效，并阻止受影响步骤继续按旧目标执行。无关已保存成果保持。
6. updateSaved/“已保存要求”只由对应修订的真实保存回执产生；单独 control.explanation 不代表保存。迟到纠错结果不能覆盖更新的用户要求。仅规划授权在恢复后仍只规划。

## 6. 恢复资格、截止时间与累计预算

### 6.1 一份决策，三个调用方

会话读取、控制请求、执行前复检共用一个恢复决策，输出可用动作、原因、适用修订与有效期。沿用现有消息/控制入口和恢复记录，必要的响应字段兼容增补，不新增公开路由或第二套调度。

- 同段重试：沿用当前轮次的原截止时间和尝试上限；必须满足与实际请求一致的 requestFitsDeadline，租约及授权也有效。
- 继续规划/执行：上一段已结束，原任务总额度尚足，且有可验证的待完成位置时，使用现有续做机制形成一个关联原轮次的新有界段。模型、工具、传输、修复及自动事件计数继承；业务 operation ID 与成功回执保持。
- 预算用尽、无进展限额或必要事实失效：不给无效重试按钮；分别显示限额、补充信息或重新核对入口。

新段只获得其自身至多 80 秒且不超过剩余累计活跃额度的时间窗口；它不是重置旧段 startedAt/deadlineAt。故障重试计数和参数纠错额度绑定原业务修改身份，不因新 turnId 获得额外尝试；真实新要求的处理仍受同一任务总预算。活跃时长只结算实际执行区间，用户等待和后台等待不重复扣账。

旧合同保留每段10模型/12工具/2传输重试、任务累计130/156/26及1,040,000ms上界；旧自动事件额度沿OPT-39。新任务初始授权仍沿用这些默认值；OPT-49的新版本合同才按§10.4提供明确且有限的额外授权及事件额度推导。普通继续不能增额，已冻结的更小额度和外层测试上限优先，不能把新授权规则回填旧预算。计数取既有持久值与本次实际增量，不修正或清零旧预算。旧状态缺少足够恢复证据时保留数据并说明限制，不猜造检查点。

上述“新段继续”已由 OPT-44 实现：覆盖旧文档把同段重试与跨段继续都解释为“沿用同一截止时间”的部分；同段重试仍保持原截止时间。自动恢复须满足原授权、有进展和额度；无进展到限后停止，不能依靠创建新段绕过。

### 6.2 并发、未知结果与页面

领取恢复沿用 session 锁、task revision、execution token 与幂等键；双击、两个标签页或迟到响应最多启动一次同一恢复工作。恢复前复检权限、依据版本、修订及真实回执；用户已停止/撤权/更新要求时旧恢复失效。

按钮使用同一服务端能力和有效期。临近过期可按返回有效期刷新/禁用，服务端仍最终裁决；409/拒绝后立即刷新会话，显示具体原因并保留输入。若仍可新段继续，显示对应动作；规划修改失败时不只暴露已经过期的同段重试。

## 7. 反馈与诊断

- 提示由当前持久事实共同构造：已保存成果、未生效修改、真实阻塞和可用动作分别表达。停止、权限、修订、依据变化及有效额度限制决定能否继续；待修改/澄清不能提前返回并遮盖阻塞。旧失败不覆盖当前成功回执。未知字段保留不确定性，具体优先级与接线按§11统一。
- 服务端构造的背景上传提示和保存摘要直接使用可信状态，不再交给“已…生成/扩充”正则判断。对模型自由总结的执行声明，用真实回执约束并保留具体阻塞原因。
- 背景前提一致：当前从零生成仍要求可读取背景；说明场景/数量不能代替上传。未提供文档时允许保存不完整意向并明确缺失项，不能把不完整意向宣称为完整可执行方案。
- 诊断按 turnId + execution_attempt 保存；同尝试内可更新快照，新尝试保留旧结果，新段用原轮次关联。记录首次失败、纠错类型/次数、最终结果、长度终止原因、请求耗时与预算拒绝，计数分清本尝试与整个任务。
- 复用现有受限 JSON 观察记录及历史容量；超出明细容量时保留首个根因和最新恢复摘要，不建立事件溯源平台。记录字段路径、错误码和数量等最小诊断，不保存密钥或任意用户正文。
- 已被覆盖的历史诊断不回填推测结论。第 3 项首轮具体协议错误仍标记证据不足，后续独立记录用于定位。

### 10.1 修复实际失效的调用合同

- **方案修改**：首次建立、已有方案增量修改、核对已有要求分别选择输入合同。修改只让模型提交真实交付引用和变化；服务端合回生效事实后完整校验。字段省略不撤销约束。无变化请求也须经服务器核验并留下对应修订的核对回执，不能以口头确认替代。截断后实际缩小Schema、工具集和上下文；失败正文不作为下一次完整输入重放。
- **资料发现**：优先已明确选择的来源；泛指“这些数据”不等同于名称搜索“数据”。一次内部发现聚合有权限的少量候选，足以询问具体对象后收束；没有新名称、范围或分页意图不继续扫目录。候选澄清直接由真实结果呈现，不依赖最后一次模型总结成功。
- **处理提议**：按清洗/改写/扩写暴露各自合法参数；来源、输入范围、输出数量分别表示。服务端在无副作用阶段一起校验配置、范围、Metadata键和字段保护，再进入既有处理服务。显式“全部当前文件”可编译为真实固定范围；选中文件或读过预览本身不是全量授权。计划派发、直接工具和恢复共用预检及有界业务纠错。
- **完成与错误**：只读、核对、保存和提交有各自真实终点；已确认无写入的校验失败才可改参数重提，未知副作用先查原回执。修改身份、修复计数和停止原因贯穿普通消息、按钮和自动继续。既有最多2次额外纠正、其中最多1次截断重提不因换turn增加。

### 10.2 会话、业务任务与执行段

| 层次 | 责任与边界 |
| --- | --- |
| 助手会话 | 保存个人交流及背景关联；可顺序承载不同目标，不把第一项目标预算绑定整段聊天终身；历史分页读取 |
| 助手任务 | 一个明确目标及其补充、授权、要求修订、回执和累计消耗；普通继续、改名、改数量和换表达仍属于原任务 |
| 执行段 | 一次有界活动窗口；让出后从可证未完成位置续接，不重复成功副作用，不获得新任务预算 |
| 预算授权 | 对当前任务明确给予的一份有上限执行额度；原额度和使用记录不覆盖，后续授权单独关联并累计 |
| 执行检查点 | 当前要求/依据修订、未完成位置、已有业务回执和消耗引用；不是模型重写的任务总结，也不是新权限 |

同会话只保留一个当前可执行任务，不增加并行任务管理器。用户明确提出独立新目标且旧任务已终结，可建立新任务；旧任务尚未结束时，只有明确切换并保留旧进度才切换，有歧义只澄清这一点。模型不得因失败、耗尽或一句“继续”擅自创建新任务。读取旧成果不切任务；旧任务恢复使用原身份、授权与账本。新任务不得隐式继承旧字段限制、来源范围或采用/发布确认。

持久化优先复用现有session/turn/task JSON和回执；终结任务保留可定位的合同/预算快照，当前状态只存必要引用，不把所有历史任务复制进一个不断增长的JSON。允许为真实读写需求增补版本化字段/索引，不建设第二套任务服务。旧任务按旧策略解释，不读取即迁移、清零、重写预算；缺少事实就明确受限。

### 10.3 长对话上下文

统一请求投影包含当前目标、有效要求、待修改意图、阻塞问题、授权、必要回执、相关背景片段与有限近期对话；已撤销约束和历史错误不再作为当前指令。背景文本仍是不可信资料，不能从其内容取得执行权限。需要旧细节时按有权访问的引用受限读取。

模型输入容量、单次输出token、执行段次数、任务额度和测试总额度分别度量。上下文按配置的输入容量预留工具Schema及输出空间，先裁历史工具正文和重复附件，不能静默丢当前目标或未完成修改。必要事实仍超容量时分交付/步骤投影，不能声称已完整读取被省略资料。不增加常驻模型总结链或向量库；有界事实投影由持久状态构造。

新合同下会话累计100条turn不再是任务失败条件：历史分页和单请求窗口有界，自动事件与用户消息分别统计。用超过100条的合成历史验证，不进行100次真实模型调用；数据库容量和访问保护继续有效。历史存储容量到限应显示具体归档/新会话选择，不能伪装为模型错误，也不自动删除历史。

### 10.4 预算与进展驱动续接

沿用§6共享恢复决策，补齐下列分层；本节对新版本任务的预算授权含义优先，旧冻结策略仍按原义。

| 限制 | 新合同处理 |

| 处理Worker配方预算 | 保持原根任务/批次的冻结边界；对话续接不重开处理运行或重置其生成、核对预算 |
| Computer Use验证额度 | 独立于产品任务，是更外层总限制；任何新任务、续接授权和纠错都不能突破该次验证上限 |

新版本任务的额外授权使用一个保守预设：至多再执行一个默认段（10模型步/12工具调用/2传输重试/80秒活跃时间），且受更紧管理员/项目/验证上界约束。授权内容展示待继续的目标、追加上限及已保留进度；不新增可任意填数的预算控制台。授权只增加允许量，历史used、deadline和原policy保持；任务汇总同时列累计已耗与累计明确获准量。为同一失败修改再尝试时，须在该授权内明确包含该修改的一次新有界修复尝试（仍最多2次纠正，其中最多1次截断），旧尝试计数保留；模型或普通重试不能自批。

每次授权绑定用户、任务、要求修订、待完成位置、用途、过期条件和幂等键；一个任务同一时刻只有一份活动额度，审批/双击不能重入或双增。不能把上述产品功能用于追加已经关闭的历史验收预算，也不能通过克隆失败任务绕过限额。当前会话普通新任务与人工追加旧目标额度在记录和UI中明确区分。

进展来自新保存要求/新固定范围/新业务回执/当前检查点前移；重复查询、重复错误、相同状态重读和重复事件不是进展。用现有推进节点计算新任务的有限事件额度，重复Worker事件幂等收尾，不计作新工作；即使有进展也受资源总额约束。达到无进展限制后不靠生成新段恢复。后台等待沿现有任务事件触发，无模型轮询；用户/后台等待时间与实际活跃时长分开记录。

恢复读取、消息入口、按钮、队列领取和发请求前共用判断；保存成功后响应丢失先查回执，新要求、停止、撤权或依据变化使旧恢复失效。计划模式不得变成生成权限。达限暂停、等待用户、模型超时、参数失败分别显示，不将所有停止都报“请重试”。

## 11. 2026-10-23 全链路机制合同

### 11.1 一份可信准备结果

现有执行器内部统一“操作意图＋当前任务/修订＋授权要求＋可信对象/背景引用”事实输入。建立、修改、核对和删除采用明确的目标合同；更新必须有当前真实交付身份，新建不能混入更新。目标歧义只询问缺失业务信息，不让用户填写内部id。

正常调用、SDK纠错、业务失败纠错、补保存和恢复共用准备顺序：引用解析→目标绑定→授权变更合并→确定性派生→完整校验。结果表达合法规范化提议，或结构化问题和所需事实；不得只返回布尔accept。相同提议不因入口不同而得到不同结论。模型初次提议是待校验数据，不能成为新的授权来源；写事务仍复检权限、修订和依赖。

OPT-46负责共享结果与方案规则，OPT-47实现处理规则及所有处理调用方。二者可保留各自业务准备函数，共用错误/修复协议；不追求把不同业务强塞成一个大函数。

### 11.2 一条有限纠错链

每次修复产生最新候选、最新问题及可信相关事实；下一次在原修改身份和剩余限额内使用这些结果。保留首次错误和原用户要求。按规范化候选/问题及业务回执判断是否有进展；未知工具结果先查回执。两次纠正、其中至多一次截断的原限制保持；新增授权另按§10.4，不能偷偷新开一层循环。

### 11.3 执行阶段与回执

准备不产生业务副作用。执行仍调用现有命令及事务；复合命令显式携带无提交、部分提交、已提交或结果未知的事实与子回执。仅错误码不足以判断无副作用。目标创建和处理提交分步发生时沿原命令查目标/运行回执后继续，不能重建目标或清除部分成果。采用/发布的固定确认及事务回执不变。

### 11.4 任务、请求和恢复各有一份权威状态

当前执行依赖绑定taskId；历史展示另按原权限控制，不能通过裁剪历史绕过访问限制。整体请求投影包括system、Schema、当前事实、历史、引用及输出预留；首次、修改、纠错和恢复均在实际出站边界核算。关键词仅作可靠快路径，未知表达走既有结构化理解/必要澄清，不靠不断扩充触发短语保证业务语义。

实际HTTP尝试、SDK步、工具调用和活跃时长分别计量；实际请求从同一边界预留/结算。头部、正文和解析阶段耗时可区分，未发出与结果未知不能混淆。进展仅由新有效要求/范围/回执/检查点前移证明；发现读取在有限阶段内推进，查询正文变化不授予长期续段资格。

会话读取、消息、控制、队列及发请求前共用恢复决策。当前成果、待保存修改、阻塞原因和可用动作是独立事实；前端消费同一服务端投影，不重算预算或猜错误提示。旧失败不得覆盖当前成功，待修改不得掩盖当前阻塞。

| OPT-49 | 账本、进展计算、队列、恢复资格和请求时钟 | agent/recovery各自解释进展；SDK步代替真实请求；响应头代替完整请求耗时 |
| OPT-50 | 页面状态/动作、公共回归证据与既定两项CU | 前端再次推断失败原因；以两项CU覆盖声明代替前票缺失机制 |

每票记录实际调用方、旧路径退出、旧格式兼容和受影响回归。共用模块必须有真实调用者；避免转发包装、平行新引擎或一次性拆分全部大文件。未取得性能证据的读放大/锁竞争仅在受影响路径用隔离查询计数/并发夹具检查，不额外建设性能平台。

跨入口组合测试索引见[§5.20](test-plan-data-selection-and-assistant.md#full-agent-review-tests)。原默认、旧预算和OPT-50两项CU上限均保持；本次只更新方案与票据，不实施业务代码、不重跑已完成部分。

### 11.6 全工具参数合同与恢复一致性（逐字段补审）

事实及逐字段表统一见[参数审查](assistant-tool-parameter-review-2026-10-23.md)，本节仅规定拟实施合同。15个业务工具继续调用现有服务；允许收敛共享条件/范围准备与错误类型，不建立独立参数平台，不为追求同形抹去各工具实际业务差异。

1. **声明与执行**：每个字段明确省略、null、false、空数组的含义，及依赖哪个可信事实补齐。模型声明可省略未来或可绑定引用；完整执行前必须验证。类型、条件必填、互斥范围、语义归一及派生容量来自同一业务准备规则。分步计划、直接调用、纠错和恢复得到相同规范化结果或问题；权限/修订/副作用围栏仍由现有事务复检。
2. **选择与范围**：来源、输入ID、条件选择、整范围及UI勾选分开表达，显式模式互斥；选取条件不能静默丢弃，false不能被当成未提供。已有勾选与新全部/条件请求冲突时要求一次明确范围选择，不擅自扩大或缩小。条件复用现有selectRecords语义（明确Metadata键、文本trim及大小写规则）；旧固定IDs不重算。random单位仅在可信要求明确时派生；每次实际种子、配置、固定IDs和hash一致，省略seed时在首次固定时生成并持久复用，重新抽取需原有明确授权。
3. **条件字段与语义**：按工具/operation/target.kind校验允许字段及条件必填；草稿新建/继承/复用在返回复用前统一准备，不暗改purpose或把忽略字段称已生效。trim后的空值、重复键/场景在副作用前准确返回；只能无损规范化，不能静默删除用户分类或数量。用户明确场景数优先于默认3场景，生成条数与场景数是两种约束；未指定场景仍可采用当前默认，不扩大场景管理功能。
4. **容量与有效要求**：准备后再验证最终参数长度和全请求窗口。requirements完整持久保留，不能无界拼接为instructions或截掉约束；复用冻结要求与简短执行指令的现有通路。不能容纳必要事实则返回具体容量问题或现有分交付处理，不默认调大8000/token/预算，不新增模型总结链。不同工具合理的接口子集长度可保留，需在对应声明与准备一致表达。
5. **错误与纠错**：错误包含实际tool、operation、字段路径、原因及可用事实，不将纯选择器参数错误变成未知操作，也不把augment提示套给generate。一次返回所有可证配置/范围问题；未知业务信息只问必要选择。下一次纠错消费最新问题并完整复验，原两次/截断一次计数不变。没有副作用的预检可安全纠正，已提交/部分提交/未知必须先按原回执对账。
6. **冻结身份与兼容**：新操作先取得规范化准备结果再建立指纹/回执；恢复使用原身份和已固定范围，不能因绑定差异新开操作。旧合同按持久版本及可证回执解释，不批量重算hash/seed、补写旧要求或迁移旧预算。人工构造旧输入仅构成风险证据，必须用隔离兼容夹具证明可达或给出反证，不能据此改签线上故障原因。
7. **核对与确认**：读取工具可以记录证据/核对，但不能因读取历史结果切换当前任务或虚增进展；来源与角色权限同时控制页面、工具结果及模型投影。采用/发布仍保存固定确认参数，客户端不能提交另一组写入字段；确认前复检原修订/范围，未知回执先对账。前端只消费统一中文原因和恢复能力，技术字段留诊断，继续沿frontend-v1。

责任分工：OPT-46提供统一准备/错误协议及规划字段，OPT-47接入选择、处理、草稿复用与采用准备，OPT-48接当前事实/引用/容量投影，OPT-49接规范化冻结身份与恢复，OPT-50核对全工具覆盖和页面。依赖顺序不变；实际字段清单是审查快照，实施时更新相关Schema/调用方及公共回归，不另维护第二份手写运行时合同。
