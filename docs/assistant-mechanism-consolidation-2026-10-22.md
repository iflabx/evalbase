## 1. 决策与完成目标

采用现有 AI SDK 和业务执行器内的机制整理：统一参数失败分流、要求修改、恢复资格及状态投影，保留现有模型连接、PostgreSQL、MinIO、Worker、权限和业务回执。目标是让普通请求和连续更正经过同一套可验证规则，失败后有可执行的恢复动作。

| 备选方式 | 本次取舍 |
| --- | --- |
| 继续按单个错误追加修补 | 可用于独立缺陷；本次已有共享判断冲突，须整理共同合同 |
| 在现有执行器内收敛职责 | 采用；直接覆盖已证实根因，可沿现有业务接口验证和逐阶段接入 |
| 更换运行时或增加通用工作流层 | 当前证据指向业务合同与恢复判断；暂无因此扩大技术栈的必要性 |

本次选择依据是实际工具回执与代码中的重复判断；未新增框架对照实验，不宣称该方案保证任意模型零失败。模型服务拒绝、真实业务歧义和预算用尽仍可能停止任务，停止时须保存事实并说明下一步。

实施范围以完整根因及直接共享合同为单位。允许合并重复判断、提取有实际调用者的共用模块、调整内部接口和删除替代路径；每项结构调整要说明解决的职责冲突、调用者、兼容方式和验证路径。保留现有单执行器、有限业务动作和持久化模型，按需增补现有 JSON/DTO 的可选字段。若发现必须新增表、外部框架或扩大公开能力，应先记录证据与具体设计差异。

UI 继续使用 frontend-v1 的组件、文字层级、密度与状态样式，正式代码位于 frontend-v3。当前阶段沿用人工内容审核；本次完成目标为流程、合同与恢复正确，不重新启动旧 248/400 条质量验收，不将历史质量问题改签通过。

## 2. 当前机制与拟调整后的流程

| 环节 | 当前已确认问题 | 调整后的责任 |
| --- | --- | --- |
| 输入与要求 | 修改数量时模型重写完整交付，带入无关场景错误 | 模型提出本次变更；服务端合并原事实、计算派生值并校验 |
| 参数校验 | 缺必填与 minItems 分走不同纠错路径，语义缺失进入无损修复 | 同一失败分类器根据错误路径、现有事实和业务含义选择恢复 |
| 执行与恢复 | 重试资格、模型请求预留时间、前端按钮各自判断 | 一个恢复决策供会话读取、控制请求和执行前校验共用 |
| 提示 | “已有原始资料”被执行声明正则误判，覆盖真实补充要求 | 提示优先来自已持久的阻塞原因和真实回执 |
| 诊断 | 同一 turnId 的重试替换首次失败 | 按轮次和尝试保存过程，关联最初失败与恢复结果 |

正常流程：普通请求 → 当前对象/背景/要求 → 业务变更提议 → 规范化、合并与完整校验 → 原子保存生效要求 → 既有执行器按真实回执推进 → 结果审核与固定确认。

失败流程：记录尝试及原始错误 → 判定是机械纠错、上下文修正、业务澄清、回执核对或预算暂停 → 在同一授权及累计预算内恢复 → 校验当前修订后保存/执行。校验失败不提交业务副作用，也不把未保存变更展示为已生效。

## 3. 责任落点与替代关系

优先在已有模块收敛职责，不按本表强制新增文件或通用接口。

| 现有位置 | 应承担的统一责任 | 退出或收敛的重复行为 |
| --- | --- | --- |
| assistant/tool-repair.ts 与工具实际 validator | 错误分类、无损归一、有限修复及再次校验 | 每个工具独立追加外层修复循环；只按错误文案猜测分流 |
| assistant/delivery-plan.ts、requirements.ts 及 plan_task 保存路径 | 局部变更合并、派生数量、依赖失效、原子生效 | 模型重复维护展示总数；局部保存与整份计划更新的不同语义 |
| assistant/budget.ts、tasks.ts 与现有恢复入口 | 实际可用额度、恢复方式、幂等领取和执行前复检 | canResume、请求预留时间、按钮各自制定条件 |
| assistant/store.ts 与 agent.ts 最终回复路径 | 由阻塞事实、保存回执与运行回执投影状态/提示 | 服务端事实被自然语言关键词过滤覆盖；模型解释代替保存事实 |
| assistant/diagnostics.ts 与现有 JSON 观察记录 | 尝试级诊断、恢复关联与累计计数 | 用同一 turnId 的最终结果抹去前次失败 |
| frontend-v3 项目助手 | 展示服务端恢复能力，提交失败后刷新状态，保留输入 | 前端独立认定可恢复；持续显示已失效按钮 |

agent.ts 保留 SDK 接线与业务工具适配。提取真正被多个入口共享的决策，不拆出只有转发作用的模块。每阶段接入时同步移除被替代的新任务路径；历史冻结合同按既有版本明确兼容，读取旧任务不写回迁移、不触发重跑。

## 4. 参数失败分类与有界纠错

| 失败类别 | 判定与处理 | 用户体验 |
| --- | --- | --- |
| 无损格式问题 | 白名单可逆归一，如已知结构包装/容器解析；完整 validator 通过且语义不变才使用 | 无需用户提供工具参数 |
| 业务值或结构不足 | required、minItems、配额/数量冲突等结合实际合同判断；先利用已保存合法事实，仍不足才让模型作受限上下文修正 | 不让无损修复凭空新增场景或删除约束 |
| 引用问题 | 只从有权限的真实对象/背景目录绑定；无法确认则限定读取或询问业务对象 | 不猜 ID、不扩大数据范围 |
| 截断/不可解析输出 | 记录 finishReason、长度与解析错误；一次受限重提只包含待变更交付和必要依据，完整校验后才能执行 | 保留旧方案和本次修改意图 |
| 真正用户业务歧义 | 无法由现有要求、文档或事实确定的选择 | 只问缺少的业务信息，已给信息不重复询问 |
| 未知副作用 | 超时/断线无法判断写入结果时先按原 operation ID 查回执 | 已完成操作不重复提交 |

分类器以实际 validator 的结构化错误为输入。关键词名只作为证据之一；例如 required 字段若可从同修订已保存事实补齐，不必请求模型；minItems 若需要创造新业务内容，就不能进入无损格式纠错。

同一业务修改共用既有修复额度：机械修复、上下文修正和截断重提共享最多 2 次额外纠正请求，并受更小的剩余模型/时间/验证限额约束。复用现有修复计数，不再叠加“每层各两次”。本地成功归一不额外请求模型；跨重试/续段仍继承该修改的已耗额度。错误路径及有效输入均无进展时停止自动重复。

多交付只向修正请求投影出错的交付、用户本次更正及必要事实，修复后合回原请求并做完整校验。合法分类、未改交付、背景和权限不能通过省略/清空来绕过校验。未确认允许的请求重构归入上下文修正，不作为无损修复。

## 5. 要求修改：先合并校验，再整体生效

继续以 executionPlan 中的交付目标及现有生效要求为权威，不增加第二份长期计划。

1. 已有 deliveryId 的输入表达本次变更，字段缺省表示保留；清除只接受现有合同允许且明确的空值/删除动作。新交付走完整创建校验，避免为修复旧交付而放松新建约束。
2. 数量修改保留未要求改变的场景和依据。2 条或 1 条生成目标不等于场景清单必须缩成 2 项或 1 项；既有合法场景可继续由分配器使用。
3. 服务端从各交付计算整体总数和展示摘要。单一类别配额可按明确新数量派生；多类别明确配额与新总数冲突时，按已授权分配规则处理，无规则则只澄清分配选择，不能随意删类别或按比例猜测。
4. 结构化数量和规则决定展示；模型生成的派生描述从当前事实重建。用户原始描述中的业务条件保留，不用全局数字替换改写正文。无法确认是旧派生描述还是用户显式约束时保留待核对。
5. 复用现有待修改/恢复记录保存本次意图及基准修订；校验成功后同事务更新生效要求、执行资格与必要确认失效。失败时旧方案仍可查看，本次修改明确标为未生效，并阻止受影响步骤继续按旧目标执行。无关已保存成果保持。
6. updateSaved/“已保存要求”只由对应修订的真实保存回执产生；单独 control.explanation 不代表保存。迟到纠错结果不能覆盖更新的用户要求。仅规划授权在恢复后仍只规划。

## 6. 恢复资格、截止时间与累计预算

### 6.1 一份决策，三个调用方

会话读取、控制请求、执行前复检共用一个恢复决策，输出可用动作、原因、适用修订与有效期。沿用现有消息/控制入口和恢复记录，必要的响应字段兼容增补，不新增公开路由或第二套调度。

- 同段重试：沿用当前轮次的原截止时间和尝试上限；必须满足与实际请求一致的 requestFitsDeadline，租约及授权也有效。
- 继续规划/执行：上一段已结束，原任务总额度尚足，且有可验证的待完成位置时，使用现有续做机制形成一个关联原轮次的新有界段。模型、工具、传输、修复及自动事件计数继承；业务 operation ID 与成功回执保持。
- 预算用尽、无进展限额或必要事实失效：不给无效重试按钮；分别显示限额、补充信息或重新核对入口。

新段只获得其自身至多 80 秒且不超过剩余累计活跃额度的时间窗口；它不是重置旧段 startedAt/deadlineAt。故障重试计数和参数纠错额度绑定原业务修改身份，不因新 turnId 获得额外尝试；真实新要求的处理仍受同一任务总预算。活跃时长只结算实际执行区间，用户等待和后台等待不重复扣账。

现有每段 10 模型/12 工具/2 传输重试、任务累计 130/156/26 与 1,040,000ms 上限继续作为产品硬上限；任务已冻结的更小额度和测试限额优先，自动事件额度沿 OPT-39，不能由继续按钮放大。计数取既有持久值与本次实际增量，不修正或清零旧预算。旧状态缺少足够恢复证据时保留数据并说明限制，不猜造检查点。

上述“新段继续”已由 OPT-44 实现：覆盖旧文档把同段重试与跨段继续都解释为“沿用同一截止时间”的部分；同段重试仍保持原截止时间。自动恢复须满足原授权、有进展和额度；无进展到限后停止，不能依靠创建新段绕过。

### 6.2 并发、未知结果与页面

领取恢复沿用 session 锁、task revision、execution token 与幂等键；双击、两个标签页或迟到响应最多启动一次同一恢复工作。恢复前复检权限、依据版本、修订及真实回执；用户已停止/撤权/更新要求时旧恢复失效。

按钮使用同一服务端能力和有效期。临近过期可按返回有效期刷新/禁用，服务端仍最终裁决；409/拒绝后立即刷新会话，显示具体原因并保留输入。若仍可新段继续，显示对应动作；规划修改失败时不只暴露已经过期的同段重试。

## 7. 反馈与诊断

- 提示顺序来自当前持久事实：需要的业务补充、待生效修改、真实处理中/待确认/已保存、实际可用恢复动作。未知字段保留不确定性，避免模型自然语言覆盖事实。
- 服务端构造的背景上传提示和保存摘要直接使用可信状态，不再交给“已…生成/扩充”正则判断。对模型自由总结的执行声明，用真实回执约束并保留具体阻塞原因。
- 背景前提一致：当前从零生成仍要求可读取背景；说明场景/数量不能代替上传。未提供文档时允许保存不完整意向并明确缺失项，不能把不完整意向宣称为完整可执行方案。
- 诊断按 turnId + execution_attempt 保存；同尝试内可更新快照，新尝试保留旧结果，新段用原轮次关联。记录首次失败、纠错类型/次数、最终结果、长度终止原因、请求耗时与预算拒绝，计数分清本尝试与整个任务。
- 复用现有受限 JSON 观察记录及历史容量；超出明细容量时保留首个根因和最新恢复摘要，不建立事件溯源平台。记录字段路径、错误码和数量等最小诊断，不保存密钥或任意用户正文。
- 已被覆盖的历史诊断不回填推测结论。第 3 项首轮具体协议错误仍标记证据不足，后续独立记录用于定位。

## 9. 验证范围与完成口径

验收权威矩阵见 [测试计划 §5.18](test-plan-data-selection-and-assistant.md#518-机制整理验证待实施)。先用固定失败回执与可控模型在既有 HTTP/Worker/前端入口验证，再安排一次明确预算的 Computer Use；真实模型调用集中用于普通提示流程，不反复重跑已完成样本。

沿用首批五项的独立新会话与小样本规模：模糊需求、两份交付、只讨论再存方案、连续改数量、替换第二主题。必要文档在适当阶段提供，用户无需说工具参数、内部 ID 或替系统安排修复。结构与保存事实用全量数量/回执核对，内容质量由人工审核，本轮不扩展语义质量门槛。

本批五项的具体普通提示、业务终点、新验证额度与停止条件统一在 [OPT-45](../.scratch/assistant-optimization/issues/45-state-feedback-and-five-flow-acceptance.md#五项-computer-use-计划) 维护。真正执行须在当次授权范围内记录新验证身份和可审计计数，原会话/旧预算不复用重置。剩余额度不足则停止并报告；本次文档工作不发起这些调用。

分别报告首次成功、系统自动纠正后成功、用户正常补充/确认后成功、技术干预后成功及最终失败。一次真实失败随后恢复，首次失败仍保留；缺日志写未验证。自动恢复成功不冒充首次成功，人工补工具参数不算普通提示通过。受控故障下正确保留并停止可通过对应保护断言，但不等于用户交付完成。

完成需同时具备：统一决策实际被各入口调用、替代分支退出、关键边界回归通过、五项各自达到预期业务终点、数据/预算保护证据和准确失败记录。通过这些小样本不推断任意模型/文档零失败。
