# 项目助手整改方案

2026-10-08（Asia/Shanghai）。状态：整改设计已记录，Owner 分别授权的 OPT-06/07 已实施验证完成；实际进度见 [实施台账](../.scratch/assistant-optimization/spec.md)。OPT-08 尚未开始，最终 checkpoint 尚未完成，本次单张授权不切换 Owner 验收环境。方案的代码审查基线为 `65a5055e22267f1e29f54923f4e1bf9f488bb42d`，复审方案时的文档提交为 `544c9e5`；工作区仍为 `codex/assistant-optimization` 分支。

整改目标是让用户在一个会话中，用简短要求完成通用测试数据任务：助手理解目标和背景、查看资料、选择方法、执行处理、根据中间结果调整，最后交付可审核的候选及真实成果入口。范围覆盖这条完整流程中的能力和体验缺口，已发现故障用于验证，不作为范围上限。

保留现有数据处理和持久化基础，改进要求表达、步骤执行、错误恢复和结果审核。后台运行成功、结构核对通过、内容可用和用户确认分别判定。技术结构是否值得增加，依据它能否支撑这些明确的用户行为、减少重复逻辑，并能通过公开流程验证。

## 3. 保留的能力与本轮范围

- 保留 AI SDK ToolLoopAgent、Fastify、PostgreSQL、MinIO、现有 Worker 和业务服务；保留权限复检、幂等回执、字段冲突、来源保护及人工采用/发布确认。
- 支持原始数据清洗、语义改写、按要求扩写、从文本提取信息、分类后筛选及测试集创建。测试类型和分类由用户要求、现有数据或背景文档决定；安全题库仅为综合验收样例。
- 继续使用问题、期望输出、有序 Metadata 三字段。意图标签和实体结果使用这套合同表达；本轮不扩展为被测智能体运行平台、多轮轨迹执行或任意结构 Schema 编辑器。
- 不新增多代理、向量库、知识库、插件市场或通用工作流编辑器。保留现有模型连接与运行预算；不以增加重试次数、放宽超时或切换模型掩盖接口问题。
- 复用 `frontend-v1` 视觉与组件，在 `frontend-v3` 呈现当前任务、结果和恢复操作；冻结原型保持只读。

| “通用能力验收”可能变成多套子系统和重型压测 | 不同业务样本共用现有工具与处理能力；复用受影响测试，用小样本和一次综合任务验收                             |

## 4. 职责调整

| 工作       | 模型负责                                                   | 服务端负责                                                        |
| ---------- | ---------------------------------------------------------- | ----------------------------------------------------------------- |
| 理解请求   | 识别目标、提议方法、指出真正歧义                           | 验证对象访问权、范围、容量和参数一致性                            |
| 保存要求   | 给出结构化要求及必要语义说明                               | 规范化并保存唯一生效版本，生成数量和分类的展示摘要                |
| 执行方案   | 查看资料、选择或组合已有处理能力；依据中间结果调整后续方法 | 当前步骤执行前固定必要参数，绑定真实输入/结果，按业务完成条件推进 |
| 批量处理   | 分类、改写、扩写等语义工作                                 | 分页、分批、计数、固定选取、合并、缺失恢复、回执核对              |
| 质量与交付 | 根据用户已授权要求调整内容                                 | 结构核对、差异展示、采用与发布事务；内容由用户审核                |

简单查询、单次清洗或少量扩写不强制先展示完整计划。复杂任务才保存多步骤方案；用户只要求方案时保持规划状态，用户已明确要求执行时不增加“是否开始”的重复确认。采用与发布继续使用原有确认卡。

## 5. 整改顺序

### 第一部分 理清目标与处理入口

1. 沿代表性任务核对短请求、当前资料和背景如何进入实际处理；明确要求保留，实质歧义才澄清。助手可以查询或读取小样本后决定方法，不要求用户先写详细执行步骤。
2. 区分期望输出固定标签与 Metadata 分类，统一现有要求的替换、撤销及校验。核对失败返回具体字段、差额、已满足条件及可恢复动作；禁止清空限制或改候选标签强行放行。
3. 保留现有 200 条候选和全量分类产物，将原会话恢复列为回归；同时保留通用任务入口，避免只为这份数据设置专用规则。

### 第二部分 完成可靠的任务推进

1. 在现有任务和步骤中补齐必要对象、参数、结果引用与修订；按已有业务动作检查完成，不设计通用条件表达式。
2. 明确参数的步骤由服务端有界推进；需要理解新结果或调整方法时调用模型。支持读取、处理、选取、补足和局部调整的组合，不强制所有任务采用同一条处理流水线。
3. 后台入队只代表等待处理；处理终态、核对结果、采用和发布分别用真实回执判断。用户更正后保留可证兼容的成果，失效范围采用架构 §9 的有序步骤规则。
4. 在实际冲突处统一状态读写，删除被替代的分支和提示词补丁。任务、运行和确认各保留自身事实；不要求一次拆分全部文件或重写整个调度器。

### 第三部分 交付自然、可理解的工作区体验

1. 在现有助手工作区统一呈现当前生效要求、真实阶段、已保留成果和需要用户决定的事项。正常推进时不用技术提示打断；后台等待、真正失败和待审核要能区分。
2. 候选可对照来源、查看核对问题，并通过自然语言继续调整；沿用结果预览、局部调整和确认入口。操作已经成功而回复失败时显示成果，重试复用真实回执。
3. 小样本覆盖清洗、改写、意图扩写、实体提取和背景分类；另用简短目标验证助手自行选择方法、依据结果调整及同会话更正要求。不同业务共用处理能力，不新增各自的工作流子系统。
4. 小样本达标后完成一次同会话综合验证。现有 200 条任务用于恢复验证；必要的新执行链可用受控样本补充，避免重复全量模型处理。

| Ticket                                                                                                   | 用户可见成果                           | 依赖         |
| -------------------------------------------------------------------------------------------------------- | -------------------------------------- | ------------ |
| [OPT-06 目标理解与生效要求管理](../.scratch/assistant-optimization/issues/06-active-requirements.md)     | 短请求、背景与更正形成一致的实际要求   | 现有代码基础 |
| [OPT-07 可靠执行与成果恢复](../.scratch/assistant-optimization/issues/07-execution-and-recovery.md)      | 正确推进、后台衔接、失败后继续且不重复 | OPT-06       |

## 6. 交付判定

详细用例与记录口径统一在 [测试计划 §5](test-plan-data-selection-and-assistant.md#5-整改验收计划)。交付须同时满足：

- 普通用户不需要提供内部 ID、工具参数、分页游标，也不需要替系统纠正算术或工具格式。用户给出目标后，助手能选择适合资料的方法；中间结果需要调整时，沿现有授权继续或只澄清必要业务选择。
- 单任务在同一会话保留上下文、成果与恢复位置。初始提示、必要澄清、需求修改、确认点击、系统纠错提示和自动回合分别计数。
- 已确定目标因系统错误而需要用户发送“继续”、改参数或重复要求，计为未通过；测试操作者代写详细技术提示也算人工干预。
- 数量及结构检查使用全量结果；小样本内容逐条审核。人工修正必须单列，不能合并为“模型生成成功”。
- 耗时分别记录规划、排队、模型处理、核对和恢复；先建立实测基线，再确定优化目标，当前不虚设绝对时延或模型准确率承诺。
- 采用、发布、刷新和下载使用相同成果身份；版本内容与导出一致。固定版本上的通用场景及关键恢复检查通过后，才能交由 Owner 验收。

## 7. 实施边界与停止扩展的条件

开发时先沿代表性用户流程核对现有工具、要求保存、步骤推进、后台结果、候选审核和页面反馈。既查已知故障，也补足上述目标流程中尚未暴露的必要缺口；按行为做连续的小改动，不以“代码整理”为由全面重写。

新增模块、参数或状态必须对应本方案中的用户行为或数据保护要求；先复用现有能力，确有重复或职责冲突时才拆分。继续使用现有 SDK、数据库、Worker 和有限业务动作。本轮不建立任意流程图、动态依赖引擎、通用规则语言、事件溯源系统或第二套调度器。

旧任务以可读、成果不丢、已执行操作不重复为基础；只在真实引用足够时恢复未完成步骤，不为推断所有历史自然语言计划建设自动迁移系统。性能先使用现有运行日志和受控测量，不增加专用监控平台。

当通用任务、关键恢复及工作区验收成立，且新路径已替换对应旧路径，本轮即可交付。后续发现明确容量、并行执行或复用需求时，再单独评估是否扩展；不把未来可配置性或文件拆分数量设为完成条件。

本文记录设计及当前进度，具体实现以各张验证记录为准。未实施的类型、内部步骤字段和兼容处理由架构定义目标，不能当成已经存在的 API。无新增公开接口、数据表或数据库迁移承诺；如实施需要改变这些边界，先把具体必要变更写入设计。现有分支、验收库、一个长期项目及两个账号继续保留；不合并、推送或正式部署。
