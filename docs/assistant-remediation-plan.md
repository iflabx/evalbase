## 3. 保留的能力与本轮范围

- 保留 AI SDK ToolLoopAgent、Fastify、PostgreSQL、MinIO、现有 Worker 和业务服务；保留权限复检、幂等回执、字段冲突、来源保护及人工采用/发布确认。
- 支持原始数据清洗、语义改写、按要求扩写、从文本提取信息、分类后筛选及测试集创建。测试类型和分类由用户要求、现有数据或背景文档决定；安全题库仅为综合验收样例。
- 继续使用问题、期望输出、有序 Metadata 三字段。意图标签和实体结果使用这套合同表达；本轮不扩展为被测智能体运行平台、多轮轨迹执行或任意结构 Schema 编辑器。
- 不新增多代理、向量库、知识库、插件市场或通用工作流编辑器。保留现有模型连接与运行预算；不以增加重试次数、放宽超时或切换模型掩盖接口问题。
- 复用 `frontend-v1` 视觉与组件，在 `frontend-v3` 呈现当前任务、结果和恢复操作；冻结原型保持只读。

## 4. 职责调整

| 工作 | 模型负责 | 服务端负责 |
| --- | --- | --- |
| 理解请求 | 识别目标、提议方法、指出真正歧义 | 验证对象访问权、范围、容量和参数一致性 |
| 保存要求 | 给出结构化要求及必要语义说明 | 规范化并保存唯一生效版本，生成数量和分类的展示摘要 |
| 执行方案 | 确定必要业务步骤；需要语义判断时继续参与 | 固定可执行步骤，绑定真实输入/结果，按完成条件推进 |
| 批量处理 | 分类、改写、扩写等语义工作 | 分页、分批、计数、固定选取、合并、缺失恢复、回执核对 |
| 质量与交付 | 根据用户已授权要求调整内容 | 结构核对、差异展示、采用与发布事务；内容由用户审核 |

简单查询、单次清洗或少量扩写不强制先展示完整计划。复杂任务才保存多步骤方案；用户只要求方案时保持规划状态，用户已明确要求执行时不增加“是否开始”的重复确认。采用与发布继续使用原有确认卡。

## 5. 整改顺序

### 第一部分 修复当前阻塞和反馈

1. 区分期望输出固定标签与 Metadata 分类。读取旧规则时显式标明字段；规则矛盾进入修正流程，不通过清空限制或改候选标签强行放行。
2. 核对失败返回具体字段、差额、已满足条件及可恢复动作。缺参数由助手纠正；用户未作出的业务选择才需要询问。
3. 保留现有 200 条候选和全量分类产物。在原会话修正规则后复核，发现内容问题再按用户授权选取替代或调整相应范围。

### 第二部分 整理要求和步骤执行

1. 以统一的字段规则表达数量、允许值、覆盖与配额；文字说明只补充语义，不另设一套可冲突的数量权威。
2. 每个步骤保存必要输入、允许修改字段、输出引用和可机械验证的完成条件。依赖尚未生成时引用前一步成果，由服务端解析；禁止模型猜测运行编号。
3. 依据当前步骤及实际回执推进。后台入队只代表等待处理；处理终态、核对结果、采用和发布分别有自己的完成条件。
4. 用户更正后保留不受影响的成果，使受影响步骤和确认失效；不能仅按步骤标题是否变化判断成果还能否复用。
5. 合并重复的计划义务和状态维护，删除被新接口替代的提示词补丁；按行为职责整理现有文件，不为缩短文件而创建通用抽象层。

### 第三部分 通用场景和工作区验收

1. 先用小样本验证清洗、改写、意图扩写和实体提取，再验证背景分类与长任务。
2. 当前任务集中显示实际阶段、已保留成果、阻塞原因及下一操作；技术诊断和历史工具回执折叠。
3. 重试复用已保存输入、参数和回执。模型回复失败不能把已成功的业务操作变成需要重做的数据处理。
4. 小样本达标后再验证一个同会话综合任务。现有 200 条任务用于恢复验证；通用能力不得只由它证明。

以上为一个整改主题的实施顺序，不新建 Ticket、不增加逐小项人工 checkpoint。取得开发授权后在同一整改批次完成必要自动验证，最后交付一个固定提交的隔离验收环境。

## 6. 交付判定

详细用例与记录口径统一在 [测试计划 §5](test-plan-data-selection-and-assistant.md#5-整改验收计划)。交付须同时满足：

- 普通用户不需要提供内部 ID、工具参数、分页游标，也不需要替系统纠正算术或工具格式。
- 单任务在同一会话保留上下文、成果与恢复位置。初始提示、必要澄清、需求修改、确认点击、系统纠错提示和自动回合分别计数。
- 已确定目标因系统错误而需要用户发送“继续”、改参数或重复要求，计为未通过；测试操作者代写详细技术提示也算人工干预。
- 数量及结构检查使用全量结果；小样本内容逐条审核。人工修正必须单列，不能合并为“模型生成成功”。
- 耗时分别记录规划、排队、模型处理、核对和恢复；先建立实测基线，再确定优化目标，当前不虚设绝对时延或模型准确率承诺。
- 采用、发布、刷新和下载使用相同成果身份；版本内容与导出一致。固定版本上的通用场景及关键恢复检查通过后，才能交由 Owner 验收。

## 7. 需要补充的调查与实施边界

开发前只核对三处现有实现：步骤参数保存和回执绑定的最小改动；旧任务规则与成果的兼容读取；小批语义任务的质量及耗时。若发现现有机制无法在这些边界内可靠工作，再针对缺口比较替代方案并记录取舍，不先行迁移框架。

本次交付为文档。未实施的类型、内部步骤字段和兼容处理由架构定义目标，不能当成已经存在的 API。无新增公开接口、数据表或数据库迁移承诺；如实施需要改变这些边界，先把具体必要变更写入设计。现有分支、验收库、一个长期项目及两个账号继续保留；不合并、推送或正式部署。
