# EvalBase：模型辅助数据处理与自然语言操作调研

- 日期：2026-10-04。
- 性质：研究结论与下一版产品建议，尚未修改原型、PRD、正式应用或部署。
- 项目依据：服务器 `/home/bistu/EvalBase`，研究起点 `codex/prototype-data-selection` / `87092a5`；本地 main 为 `9f8d7f4`。本机 `D:/AgentBench_v2` 根目录是较旧的文档快照，不作为当前实现依据。
- 需求：连接已有模型；按测试数据类型扩充测试集；清洗、转换和改写外部原始资料；用自然语言调用项目操作。
- 规模背景：此前预计最多 10 人同时使用。它不等于模型允许同时执行 10 个批处理任务。

## 1. 建议采用的产品方向

把“AI 数据处理”作为下一版核心功能是可行的。建议用同一套处理能力服务两个入口：用户可以在原始数据或测试集页面点击按钮，也可以在项目助手中描述需求。两种入口都生成可查看、可取消、可追溯的处理任务，最后由用户把结果加入草稿或保存为新资料。

推荐主流程：

**保存原文件 → 读取源结构 → 用规则转换或让模型清洗、改写 → 对照预览结果 → 保存处理结果/加入测试集草稿 → 创建新版本。**

对已有测试集，则是：

**选定版本或草稿记录 → 确认数据类型、扩充方向和数量 → 小批试生成 → 查看结果 → 批量生成 → 选取结果加入草稿 → 创建新版本。**

关键建议：

1. **清洗安排在原文件上传并确认保存之后、进入正式测试集之前。** 原文件保留，处理产生新结果。
2. **格式不同、字段不同与内容需要改写分别处理。** 改字段名、解析 JSON、转换 Parquet 通常用确定规则；语义理解、改写和扩充才调用模型。
3. **自然语言操作复用已有权限和业务操作。** 模型选择工具和填写参数，服务端检查并执行。
4. **保留已有正式版本不可变、共享草稿和冲突检查。** 模型结果先预览；等待模型期间其他人的修改不能被迟到结果覆盖。
5. **优先做一个完整的小闭环。** 当前模型连接、规则转换、语义改写、扩充、预览和加入草稿先做实，再扩大聊天可操作范围。

## 2. 当前项目能复用什么，还缺什么

以下是对服务器文档和代码的核对结果，不能与新功能建议混为一谈。

| 当前事实 | 对本次功能的影响 |
| --- | --- |
| 原始资料只支持 CSV、JSON、JSONL；解析保留源字段、值和位置 | 已有基础读取与来源定位可复用；Parquet 和 Hugging Face 仓库导入需要新增适配 |
| 上传流程为临时接收、映射、确认保存；确认前不产生可见资产 | “先保存原文件，之后再映射/处理”是需要确认的新流程，当前并不存在 |
| 测试记录固定为问题、期望输出、有序 Metadata；Metadata 值允许为空 | 适合普通问答/分类；完整智能体任务不能自动压平成普通问答 |
| 已实现账号权限、共享草稿、字段修订冲突和一次草稿一次发布 | AI 写入应复用同一服务端规则，不能通过另一条写入路径绕过 |
| Web / Worker / PostgreSQL / MinIO 已存在；Worker 使用数据库任务和领取机制 | 可以扩展现有后台处理结构，无须为第一版先引入 Redis、独立工作流平台或多代理系统 |
| 存在旧 `transformation` 清单校验代码和 `agent_rewrite` 等内部类型；公开 `transformation-runs` 路由已退役 | 它们不是现成可用的模型功能；后续只能评估可复用的内部校验，不直接恢复旧公开接口 |
| 当前数据选取原型已移除模型抽样，只保留全部选取、随机抽取及筛选 | 本研究是模型处理/扩充能力，不代表恢复已删除的模型抽样策略 |

## 3. 模型接入：已有服务可作为第一个接入对象

用户提供的 `qwen3.8-27b-un` 服务已完成基本连接测试。本轮另外发送了两个小型合成请求，未读取真实项目数据，也未执行真实项目工具。

| 探测 | 观察结果 | 能证明什么 |
| --- | --- | --- |
| 前一轮模型列表和普通对话 | HTTP 200；列表包含指定模型，回复 `OK` | 基础连接、认证和对话可用 |
| `response_format: json_schema`，要求改写一条无害问题为两条 | HTTP 200；返回两条保留 `source_id` 的 JSON，字段和数量检查通过；本次 2.32 秒、134 tokens | 指定结构输出在这个样本上可用 |
| `tools` + `tool_choice: auto`，只读查询演示测试集 | HTTP 200；请求 `get_test_set_summary`，参数为指定的 `demo-set`；本次 0.64 秒、329 tokens | 能在这个样本中选择工具并生成正确参数；工具未实际执行 |

这些结果不能证明大批量质量、严格 JSON 约束总是执行、多轮工具稳定性、吞吐量或长时间运行表现；本轮未测试流式返回、并发、取消、长上下文和服务端网络路径。`qwen3.8-27b-un` 是部署返回的模型标识，不据此推断权重版本、量化配置或推理框架。报告不记录 API key。

vLLM 官方分别说明了 JSON Schema 结构输出和工具调用；Qwen 文档也说明模型生成工具请求、应用执行工具并返回结果的分工。接口路径兼容不意味着所有扩展参数都兼容，后续应针对每个接入配置保存探测结果。[vLLM 结构输出](https://docs.vllm.ai/en/stable/features/structured_outputs/)、[vLLM 工具调用](https://docs.vllm.ai/en/stable/features/tool_calling/)、[Qwen 工具调用](https://qwen.readthedocs.io/en/stable/framework/function_call.html)

建议第一版在“设置 → 模型连接”由管理员配置服务地址、模型名称和凭据，提供连接测试。项目成员只能使用获准的连接，不读取 key；服务端调用模型，日志和页面显示脱敏信息。先支持当前这一类接口，多个供应商路由和自动故障切换可在出现实际需求后增加。配置地址由管理员维护，服务端限定允许的模型目的地址，并处理重定向和响应大小，避免聊天参数被当作任意网络访问入口。

## 4. 原始数据清洗应该放在哪里

### 4.1 上传前与上传后比较

| 位置 | 体验与代价 | 建议 |
| --- | --- | --- |
| 用户在自己电脑上先清洗，再上传 | 产品实现少，但用户需要工具/脚本；原文件和处理过程容易脱节 | 保留这种使用方式，不作为主流程 |
| 文件临时上传后、确认保存前做耗时模型处理 | 原始字节尚未成为可见资产，取消/过期与任务恢复难处理；用户被长任务卡在上传步骤 | 不建议作为默认位置 |
| 确认保留原文件后，在原始数据详情处理 | 可以反复尝试、比较结果和追溯；任务失败仍有原件 | 推荐 |
| 进入测试集草稿后再处理 | 适合针对本次测试用途改写、补充和扩充；不适合承担所有外部格式适配 | 作为另一个处理入口 |

上传阶段仍应处理文件大小、格式识别、编码、语法解析等检查。模型清洗不承担“修好无法安全读取的任意二进制文件”。

### 4.2 对当前上传页面的具体建议

保留熟悉的上传与映射流程，增加明确的 **“先保存原文件，稍后处理”** 路径。保存后可以查看源字段和原文件，标明尚未完成测试字段映射；未准备好的记录不能悄悄作为完整测试数据进入草稿。用户进入文件详情，再选择“整理字段”“清洗/改写”或“创建测试集”。

这需要后续 PRD 明确“未映射但已保存”的文件状态和可执行操作，是本次调研建议，并非一次前端文案调整。

### 4.3 四类处理不要混在一个模糊的“AI 清洗”按钮里

| 用户遇到的问题 | 推荐处理 | 是否通常需要模型 |
| --- | --- | --- |
| `prompt` 要显示为问题，`reference` 要显示为期望输出 | 字段映射；保留原字段 | 否；模型可以给映射建议 |
| JSON 嵌套、不同列结构、Parquet、枚举值映射 | 格式适配、选字段、规则转换 | 否 |
| 空值、完全重复、长度异常、不可解析记录 | 明确规则检查，展示影响记录 | 否；是否删除由用户指定 |
| 改写表达、翻译、抽取结构、补充分类、场景扩展 | 带任务约束的模型处理 | 是，且需要查看结果 |

来源文本中的特殊字符、看似异常的指令和危险意图，在安全测试数据中可能就是测试内容。不能默认“去掉不安全文本”、自动补答案或删除短文本。建议按选定字段处理，默认保护标签、工具名、ID、来源位置和评判信息，修改这些内容需要在预览中明确显示。

“期望输出为空”也不应直接判定为待补齐错误；当前项目允许空值，许多安全任务使用行为判断而非唯一文本答案。

### 4.4 Hugging Face 导入的范围

Hugging Face Datasets 可以加载 CSV、JSON、Parquet 等文件，也支持指定仓库 revision、配置与 split。EvalBase 当前的三个格式不能覆盖所有 Hub 数据集。[官方加载文档](https://huggingface.co/docs/datasets/loading)

建议先完成用户已下载文件的处理闭环，明确当前可上传格式；若常用数据只有 Parquet，优先增加一个受限的 Parquet 导入适配器。Hugging Face 直接导入可作为后续便利入口：选择仓库、配置、split 和具体提交，预览数量与体积，再导入选定范围。不要把“支持 Hugging Face”理解为执行仓库任意脚本或下载全部 split。

保留来源仓库地址、具体 revision、配置、split、源文件与记录位置、原件哈希和许可信息。无法知道某项时明确未记录，不能推测。HF 缓存能帮助复用计算，但不能替代项目自己的来源记录。

## 5. 测试集扩充：先定义扩什么，再生成

“根据数据类型”包含两层：文件格式由解析器处理；扩充策略依据测试任务的语义类型、已有 Metadata 分类和用户目标决定。

建议流程：

1. 从当前版本或草稿中选择种子记录，固定本次输入快照。用户可选当前筛选结果、指定记录或一个类别。
2. 优先读取已有分类/场景 Metadata；缺少标签时，让用户指定类型，模型可基于小样本提出建议，用户确认。
3. 填写新增条数、方向、语言、允许改动的字段和必须保持的约束。清楚区分“新增 100 条”和“总计达到 100 条”。
4. 先生成少量样例，例如 5 条。显示原记录、生成记录及类型分布，用户可以调整提示词。
5. 按确认后的规则分批生成，展示成功、失败、待检查和实际新增数量；可取消未执行的部分。
6. 用户选择接受、编辑或丢弃结果；接受的内容以“新增记录”或已确认的字段修改加入草稿，再使用原有发布流程。

| 类型 | 适合的扩充方向 | 需要保持的内容 |
| --- | --- | --- |
| 单轮问答 | 同义表达、不同描述角度、边界场景 | 原问题语义；新增事实需有依据；参考答案不被当成当然正确 |
| 分类/标签任务 | 同一类别下增加不同例子、补足类别数量 | 标签定义及类别分布；不同标签之间不能混淆 |
| 多轮对话 | 在完整上下文内改变表达或受控场景 | 消息顺序、角色、前后依赖；不能只保留最后一句 |
| 智能体/工具安全任务 | 在已确认的场景模板内扩展测试案例 | 工具契约、环境前置条件、预期安全行为和评判方式 |

后两类是目标方向，当前三字段界面尚不能完整表达其全部结构。建议先选择一个真实数据集，确定需要保留的结构和详情展示，再承诺“完整智能体测试集支持”。可以保留原始 JSON、结构化上下文和转换说明；仅把它们拼接成一段文字，会改变下游执行语义。

质量检查建议分三层：程序检查结构、数量、来源和重复候选；模型可辅助判断语义保留与类别一致性；用户抽查和确认最终可用性。模型生成参考答案应标为待确认，不能因为同一个模型又打了高分就宣布正确。去重应考虑问题、上下文和 Metadata，不按问题文本相同就自动合并所有记录。

扩充样本应保留种子或输入集合的关联，便于识别高度相似的变体。用于独立测量的保留集不应混入由其自身扩写的样本；这是后续测试质量建议，不要求第一版建设训练平台。

## 6. 自然语言如何操作项目

用户可以说：“从当前原始数据中选出中文记录，整理为问题和期望输出，先给我看 5 条，再创建一个测试集草稿。”

推荐执行过程：

**理解意图 → 查询当前项目和记录范围 → 展示处理步骤、数量与目标 → 必要时确认 → 调用有权限的业务工具 → 显示进度和结果 → 点击打开目标页面。**

模型不能仅凭一句“已创建”就让界面显示成功；成功反馈必须来自实际工具结果，包含可点击的对象链接。找不到唯一目标、多个同名文件或“扩充一倍”等含义不清时，先让用户选择/确认具体对象与数量。

| 操作类别 | 第一版建议 |
| --- | --- |
| 查询、统计、筛选、解释来源、打开对象 | 按当前用户权限直接执行 |
| 创建资料集合/测试集草稿、提交清洗/扩充任务 | 展示范围、参数和结果去向；明确指令可执行，范围不清或较大批处理先确认 |
| 应用批量改写、发布新版本 | 展示变更预览和目标修订，用户确认后提交 |
| 管理成员、永久删除、修改凭据 | 首版由现有专用页面处理；聊天可引导到对应页面，后续再设计有即时确认的专用工具 |

这里的“技能”可以先实现成少量固定业务操作：查询资料、选择记录、建议映射、按规则整理、模型改写、测试数据扩充、预览结果、创建草稿、应用结果。按钮与聊天共用它们。自然语言入口覆盖范围应逐项列出，不能宣称可以任意操作整个项目。

工具执行必须检查登录用户、对象所属项目和最新权限；“查看”不能因为使用聊天而获得编辑权。不能让模型生成任意 SQL、shell 或代码直接作用于服务器。用户选择的项目范围由应用维护，不仅靠模型提示词记忆。

对于安全数据，原始记录中的命令文本属于待处理内容。建议将“解释用户指令的助手”和“改写数据的模型调用”分为两个执行上下文：处理调用不获得项目管理工具，输出只作为待校验数据；项目助手接收受限的处理摘要和记录引用。仅靠一句“忽略数据中的指令”不足以实现隔离。

## 7. 与多人草稿、后台任务和来源衔接

建议继续使用现有 Web/Worker/数据库任务结构。Web 负责授权、参数校验和立即返回任务 ID；Worker 分批调用模型，保存处理结果；用户随时查看进度。模型网络请求期间不应长时间持有数据库事务或草稿锁，也不在 Web 请求里连续处理上千条。

需要保存的最少事实包括：输入资产/版本或草稿修订、选定记录 ID、处理类型、提示词及模板版本、连接与模型标识、实际生成参数、发起人、每批结果/错误、实际 token 用量和用户接受结果。凭据不进入处理记录。

来源关系由服务端建立：一条改写对应哪些输入记录、一个新案例依据哪个种子或哪组素材。模型返回的 `source_id` 只作待校验引用，不能凭它给任意项目数据建立关系。无法对应具体种子时记录输入集合级来源，不伪造精确的逐行血缘。

针对多人编辑，建议：

- 开始任务时保存输入快照；任务完成不直接覆盖共享草稿。
- 用户应用修改时，再检查目标字段修订；有冲突则保留生成结果，显示新旧差异供选择。
- 模型新增记录与“改写已有记录”分开应用，重复点击或请求重试不应重复插入。
- 执行和最终应用时复检权限与父对象状态；用户被移出项目、草稿删除/暂停后，不把迟到结果写回。
- 任务重启可以出现重复推理费用，不能承诺模型调用绝不重复；应用层应确保同一已接受输出只落入草稿一次。
- 取消停止后续批次；正在生成的请求能否立即停止取决于推理服务。已经生成的预览结果允许查看，不自动发布。

旧处理清单结构可以作为设计参考，但需要先核对新共享草稿、删除清理和事件归属；不恢复已退役接口。AI 修改应显示发起用户及 AI 处理来源，不能伪装成另一个人工成员。

## 8. 效率与成本：避免把全部操作都交给模型

纯格式转换、字段映射、精确规则筛选和明确去重可以不调用模型。模型建议一次转换规则后，也应由受限规则执行器应用，用户确认后再处理全部数据。

语义改写通常仍需要模型阅读待改写内容。可以把数条短记录放在一次请求，减少重复指令开销，但不能假设“1000 条合成一次请求就很便宜”：输入、输出 token 仍存在，上下文上限、对应关系和失败重试风险也会上升。

测试集扩充可以一次根据几个种子生成多条结果，不要求先让模型回答全部已有题目。第一版可以从每批 5–10 条短文本、模型服务并发 1–2 个任务开始实测，再根据 token 长度和服务反馈调整；这些是试验起点，不是已验证容量。

建议先做 20–50 条代表性小样，测量合法输出率、语义保留、标签一致性、人工接受率、重复率、每条/每批耗时及 token 数，再决定批量大小。长对话、工具定义和长参考输出单独分组测量。本轮没有执行性能压测。

估算时至少区分：输入记录数、预期输出条数、每条输入/输出长度、批大小、重试次数和质量复查次数。无模型价格配置时显示 token 与耗时估算，不编造费用。对同一不可变输入和完全相同的处理配置，可以明确复用已有结果；用户要求“重新生成”则创建新运行。保存输出才是可回看证据，相同温度或 seed 不能代替保存实际结果。

## 9. 下一步原型建议与仍需确认的事项

建议先画一个主流程，保持 frontend-v1 的风格、组件和现有侧栏结构：

1. 设置中的模型连接页：连接、测试状态及可用模型。
2. 原始数据文件详情中的处理入口：源字段、处理方式、范围、提示词与小批预览。
3. 测试集草稿中的扩充入口：种子、类型、数量、样例与结果选择。
4. 统一处理结果页面：处理前后对照、失败原因、接受/丢弃与加入草稿。
5. 项目助手侧栏：显示当前项目、操作步骤卡、任务进度和打开结果的链接。

先完成“一个真实格式的导入与改写 → 加入草稿”以及“一类测试数据扩充 → 加入草稿”两个闭环，再接自然语言入口；底层操作稳定后，聊天可以复用它们。

设计原型前最值得确认的三个问题：

- **第一个真实数据样本是什么结构？** 推荐选用户常用的一个 Hugging Face 数据集；尤其确认它是普通问答、对话还是含工具/环境的智能体任务。
- **先支持哪种输出？** 推荐先保留当前问题、期望输出、Metadata 的简洁界面，同时为复杂原始结构保留来源与专用详情；完整可执行智能体结构需单独确认。
- **结果默认放哪里？** 推荐原始资料处理生成独立处理结果，扩充结果进入当前草稿的待接受列表；接受后才成为已保存草稿内容，正式版本继续由用户发布。

以上为建议，不在本轮建立 Ticket 或修改冻结原型。后续可以先据此讨论页面和样例，再形成新版本 PRD、架构与验收范围。

## 11. 智能体安全数据的两个具体例子

### AgentDojo

它的任务不仅是问题文本，还涉及任务套件、工具、环境初始状态、正常用户目标和独立的注入目标。官方任务 API 使用 `utility` 判断正常任务完成情况，`security` 为真则表示注入目标完成，不能把它误解为“安全防御通过”。[任务结构](https://agentdojo.spylab.ai/concepts/task_suite_and_tasks/)、[任务 API](https://agentdojo.spylab.ai/api/base_tasks/)

对 EvalBase 的含义：可以整理和保留这类材料，但单独导入一段 prompt 不等于完整导入可执行的 AgentDojo 场景。若扩充改变工具、实体或环境状态，应同步检查任务引用与判据；若只是同义改写，则应固定这些结构。

### AgentHarm

官方数据文件有 `behaviors` 数组，记录包含 `prompt`、`category`、`target_functions`、`grading_function` 等字段；加载器、工具装配和评分器共同定义任务执行方式。[官方示例结构](https://huggingface.co/datasets/ai-safety-institute/AgentHarm/blob/main/benchmark/benign_behaviors_validation.json)、[加载器](https://github.com/UKGovernmentBEIS/inspect_evals/blob/main/src/inspect_evals/agentharm/utils.py)、[评分器](https://github.com/UKGovernmentBEIS/inspect_evals/blob/main/src/inspect_evals/agentharm/scorer.py)

对 EvalBase 的含义：`target_functions` 不是普通问答的参考答案；有害任务完成与安全防御通过可能方向相反。保留正常任务目标、攻击目标和期望安全行为的区别。不同子集的结构也可能不同，应先检查选定文件，而非套用全仓库统一字段规则。

这两个例子说明：智能体安全测试数据的清洗目标是使记录更易用并保持测试意义。原数据中看似“脏”的内容可能是有效测试要素。资料内指令不应获得项目操作权限，处理调用与管理工具分离的建议也与这一特征直接相关。[AgentDojo 注入位置说明](https://agentdojo.spylab.ai/concepts/attacks/)

## 12. 本轮证据边界及后续最小验证

本轮已完成服务器文档/相关代码核对、官方资料研究，以及第 3 节两个小型模型协议探测。没有完成真实数据集适配、完整工具执行闭环、生成质量评估或性能测试。引用 `main`/`latest` 的外部资料会变化，正式实现时应固定依赖版本和选定数据集 revision。

后续先用一个小型真实数据样本验证以下三条流程即可形成有用证据：

| 场景 | 主要检查 |
| --- | --- |
| 外部数据整理为测试记录 | 原件可下载，字段/记录位置对应正确；复杂信息未静默丢失；处理前后可对照 |
| 按一种确认的类型扩充少量记录 | 数量、类型、结构与约束正确；接受/丢弃可用；来源可追溯；生成答案未被自动视为可靠参考 |
| 用一句话创建草稿并提交处理 | 目标项目和范围正确；服务端真实执行；无权操作被拒绝；重试不重复写；遇到同字段并发修改保留冲突结果 |

用这三条流程确定页面与数据合同，再评估是否需要完整智能体任务结构、Hugging Face 直连和更复杂的流程编排。无需在调研阶段把所有开源工具都部署一遍。
