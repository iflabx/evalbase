## 架构变化

| 部分 | 原有实现 | 本轮实现 |
| --- | --- | --- |
| 服务组织 | Fastify、PostgreSQL、MinIO、独立 Worker；大部分 HTTP 业务集中在 app.ts | 维持模块化单体，提取账号、上传、共享草稿、版本、删除实际业务；app.ts 18,047 → 11,442 行，保留尚未证明可退役的历史路径 |
| 批量数据 | 逐条 INSERT，来源/作者归属反复扫描 | 500 行有界 JSON 批次，同一事务和稳定 ID/顺序；修订映射复用 |
| 版本读取 | 页、数量、来源与 Metadata 分别解析成员 | 一次受权限和状态约束的物化 CTE 复用解析结果 |
| 上传 | 映射预览重新解析；确认时持锁读取文件 | 缓存前 5 个有效样本；解析串行并移到确认事务前；提交时重查状态、映射、对象、归属、容量和幂等回执 |
| 协作 | 根布局与草稿重复在线轮询；修改触发全量选择来源刷新 | 共用 2 秒在线查询；精确事件更新记录修订；无搜索的页外修改不重取当前页；隐藏窗口暂停事件轮询，5 秒心跳保留 |
| 空闲 Worker | 50 ms 领取循环与 250 ms 维护 | 50/100/200/400/800/1000 ms 退避，维护 1 秒；工作后复位 |
| 清单编码 | HTTP 主线程规范化序列化、哈希与分配 | 每进程最多一个短生命周期 Node 编码线程；算法和字节保持不变，退出后释放下一位调用者；错误不堵塞队列 |
| 运行与诊断 | tsx 启动、开发依赖镜像 | 编译 Node 产物、运行依赖镜像、非 root 用户；有界 HTTP/SQL、池等待、内存和事件循环指标，可关闭 |

没有增加公开发布状态、用户操作、数据库业务表或外部基础设施。前端控件与布局保持既有原型及已确认覆盖。

### 测量中发现并处理的回退

1. 未统一统计信息的一次基线分页在来源选项 SQL 上长时间运行，主动取消后 [保留部分结果](../../.scratch/architecture-performance/results/statistics-uncontrolled.partial.json)，未计入成功中位数；后续两组统一 ANALYZE 与 60 秒语句超时，三次均完成。
2. 最初批量化使清单编码与分配集中，发布期混合负载两次 P95 约 3 秒，见 [未移出 CPU 前的结果](../../.scratch/architecture-performance/results/before-cpu-offload.json)。在规范化各步骤之间让步也未稳定解决。CPU 采样显示主线程序列化与 GC 成本，最终把同一编码算法放入一个串行工作线程；最终三次均低于 1.5 秒。

### 发布协议的取舍

采用 CPU 工作线程，保留同步发布响应和最终 MinIO 写入的现有事务协议。10,000 条数据首次发布仍需数秒，但当前测得的其他会话保持可响应；改成后台业务任务或移动对象写入需要新增发布阶段、失败恢复与唯一结果协议。此次证据支持维持现有协议。后续若持续负载、多个重发布或最大体积数据使交互明显延迟，再针对该真实负载设计后台发布；当前测量未覆盖这些情形。
