## 1. 结论及其准确含义

**正式采用 Deep Agents TypeScript + LangGraph，作为后续独立重建的目标技术栈。** 这是经有限适配验证支持、在本次 Owner 明确授权下作出的研发选型决策；正式助手全功能验收和环境切换尚未完成。

理由是：当前 qwen-new 已能通过真实 SDK 调用项目业务工具；两项预登记参数故障均有真实模型纠正证据；现成工具循环、数据库检查点和人工中断可以复用；最小业务闭环暴露的恢复、来源及回执问题已找到应用接入层原因并有定向关闭证据。不需要包装旧编排器，也没有证据要求再自建一套通用规划/纠错框架。

**原方案 §8.2 的严格整轮门槛不改记为全通过。** 首轮为 4 项普通 CU 通过、2 项失败、1 项未完成，L02 首轮有基础设施干预；后续只在新授权的限额内修复和复测缺口，代码版本、部分数量及表达不同。因此不能宣称“同一冻结版本七项原样全部通过”，也不把后测成功回写原 manifest 的 adoptionGatePassed。本次依据下表作范围明确的技术采用判断，保留完整交付验收门槛；不以“换个框架”承诺零参数错误或生产稳定率。

原验证活动已收口，无自动待执行的补跑。尚缺证据进入后续正式接入范围，在对应功能可用且获得授权时补齐；本次不新建预算或票据。

## 3. 原问题到关闭证据

| 验证项/问题 | 已有事实 | 收口判定与边界 |
| --- | --- | --- |
| L01 类型错误 | 真实 SDK 拒绝注入错误，真实模型一次纠正后只读前三条 | 纠错能力已验证；受控注入不计自然错误率 |
| L02 截断参数 | 一次纠正后仅提交一个 job；首次漏配模型 Worker，补齐同一镜像后原 job 保存 3 条 | 参数纠正通过，末端保存有证据；首轮环境阻断及人工干预保留，未补跑一次无干预整项 |
| CU-A1/A2 清洗 | 各保存前 5 条，保护字段与原件不变、链接和刷新正确 | 保留原通过，不重跑 |
| CU-B1/B2 仅方案→修改→执行 | 方案时无 job/草稿；修改后分别保存 3/2 条及新名称 | 保留原通过；不据此证明任意多交付修改 |
| CU-C1 暂停超过单次时限后不能恢复 | P1 复验在原首次开始超过 68 秒后继续同一 run，保留次数并保存 3 条 | 暂停期限与持久等待缺口关闭；P1 首次 no_progress 仍为失败记录；不是原 5 条表达重跑 |
| CU-C2 未覆盖在途暂停、重复回执 | P1 复验覆盖实际 Worker 执行中停止恢复；P3 新旧确认与唯一回执、实际采用均正确 | 两个机制分别有关闭证据；原 C2 的 5 条和第二种表达未原样复测，不改签原未完成 |
| CU-D1 背景来源跳错页面 | 首轮已生成并保存 8 条；P2 新 4 条背景样本来源可回到原会话，原 8 条来源也按权限只读打开 | 链接缺口关闭，原生成不重跑；不外推大规模内容质量 |
| 暂停查询误说预算不足、要求已保存混同草稿保存 | S1 执行中补测显示正在停止/已暂停；S2 无回执、旧卡失效、实际保存后均准确；服务端投影和 R5～8 支持 | 已测查询路径关闭；解释工具误选风险见 §5，不声称所有自然语言输出已机械约束 |

P1 和 S1 的执行中时序使用真实模型响应加最长 15 秒的 Worker 响应交付延迟。它证明 Worker 执行期间的停止与恢复合同；不能把人工窗口冒充自然生产竞态，或据此证明供应方一定能撤销已经收到的请求。已经发出的请求仍计费并留痕。

F01～F08 证明的是相应受控分支，不是完整产品范围：F06 经应用入口覆盖分段、实际请求记账、超时和无进展；F07 则在独立 Harness 的低阈值下触发真实摘要中间件并读取当前要求，未覆盖“正式应用中摘要后再修改要求→业务保存→摘要费用对账”的全流程。F03 的直接业务幂等断言由后续实际确认/未知回执回归补充，不能仅凭 helper 测试宣称所有写操作可重放。

## 4. 采用什么，应用还负责什么

| 层 | 已实际复用或接入 | 正式重建时的约束 |
| --- | --- | --- |
| Deep Agents Harness | createDeepAgent 工具循环、中间件接口；真实摘要路径有机制证据 | 使用现成循环；不用旧 executeAssistantTurn 或旧 plan_task 包装成工具；不宣称所有内置能力都已启用 |
| LangChain 模型和工具 | ChatOpenAI、结构化 tool、SDK 参数解析及工具结果关联 | 业务 Schema 为权威；非法参数反馈仍可能需要当前模型纠正，不能把框架当作零错误保证 |
| LangGraph | PostgresSaver、线程检查点、interrupt/Command 恢复 | 复用持久图；应用保护停止令牌与写入回执；检查点不替代业务事务 |
| 有限适配中间件 | 工具允许清单、同回合修改限制、截断反馈、有限纠正/无进展保护 | 未修改上游依赖源码；现有自定义反馈确实存在，不能宣传为完全零适配。扩工具时核对保护范围，不层叠新的规划修复链 |
| EvalBase 业务与宿主 | 真实资料/背景读取、处理 Worker、固定确认、幂等采用、草稿、预算及状态投影 | 身份、权限、来源修订、容量、确认和保存成功事实仍在服务端；Worker 的既有 AI SDK 可以保留 |
| 页面 | 最小验证页复用 frontend-v3 壳与组件 | 页面仍是验证入口；正式助手页面、85 项能力与原生文件/敏感输入桥尚待接入 |

具体实现见 [Harness](../../src/assistant-rebuild/harness.ts)、[宿主](../../src/assistant-rebuild/host.ts)、[检查点保护](../../src/assistant-rebuild/checkpointer.ts)、[状态投影](../../src/assistant-rebuild/status.ts)。普通工具原有 6 项，最后一轮增加 read_task_status 与仅只读阶段使用的 answer_question；没有向模型开放 shell、任意网络、真实文件系统或子智能体委派。允许清单及数据库保护继续属于正式接入合同。

现有约 1,264 行宿主集中会话、模型工具、后台关联、确认和控制，适合本次验证范围，不应直接通过继续堆工具承载全部 85 项。后续允许按已有真实调用者拆出业务工具注册和应用控制边界；复用已经明确的提交保护和业务服务。这里确定结构调整原则，不提前设计通用插件平台、另一套任务阶段机或一组空包装层。

选型原因是已证明可复用且符合项目 TypeScript/业务边界，并非证明它在所有场景比 AI SDK、DeepSeek Harness 或 Codex 更稳定。此次没有同样本、同配置的成功率对照，不能作这种结论。
