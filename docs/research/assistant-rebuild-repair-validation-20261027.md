## 修复合同

1. 新验证任务由服务端冻结 `execution_config.timeoutScope=request`：60 秒限制每个实际模型请求，最多 3 次批次调用；已预占的调用不退还，首次开始时间不改写。外层 campaign 请求、行次、生成和连续墙钟上限持续累计。生成任务保留共享调用总数上限，暂停不再被误当成正在请求。历史未带此策略的 run 仍采用原批次/共享墙钟规则，不批量重写旧任务配置。这是有限验证策略，不是正式产品额度定值。
2. 来源页链接按数据库中真实项目、用户与新运行时会话归属生成；已存在的新运行时来源也能正确读取；旧会话保留原路由。其他已关闭验证 campaign 的会话可按原身份只读查看，写入、恢复和确认仍限制当前 campaign；读取历史不对账修改旧确认卡。不以模型提供或 ID 前缀猜测归属。
3. 保存未知结果只对账 executing 确认卡；expired 卡保留失效事实。展示按 acceptanceId 去重；同一操作仍用同一幂等键，不能重复创建草稿。
4. 为确定性验证执行中停止，验证 fetch 可配置 0–15000ms 的首个 Worker 响应延迟。先记录真实 Provider 响应，再延迟交付 Worker；不修改参数、内容、权限或写入结果。报告标记“真实模型 + 人工延迟停止窗口”，不冒充自然生产时序。

## 首次 CU 观察及追加定向修复
