# EvalBase 项目助手独立工作页面：调研与建议

2026-10-14。状态：研究建议，待 Owner 确认；不替代现行 PRD，不表示已开发或验收。本轮核对服务器主线 `f261a79437247349fd8f3e25b49819229ee5741e` 的前端、助手合同及架构，阅读开源源码和官方文档；未运行第三方产品或进行模型质量、容量测试。

## 1. 建议

为「项目助手」增加项目内独立页面，承担从提出目标、查看执行进度，到审阅候选和确认保存的完整工作。使用可折叠会话列表、主要对话区和按需打开的宽结果区，沿用 `frontend-v1` 的视觉语言。

保留现有 AI SDK、业务工具、后台处理和权限体系。业务页面的助手入口携带当前对象进入同一会话；第一版统一到独立页面，避免同时维护两套完整工作台。后续若确有边看业务页面边提问的需求，再提供共享同一会话状态的轻量侧栏。

这项调整主要改善操作入口、空间分配和任务可见性。模型分类准确率、生成耗时、长任务执行正确性仍需分别验证，不能把页面调整当作这些问题已经解决。

## 2. 当前实现与体验问题

依据 [项目助手组件](../../frontend-v3/src/components/project-assistant.tsx)、[候选组件](../../frontend-v3/src/components/assistant-candidates.tsx)、[背景组件](../../frontend-v3/src/components/assistant-background.tsx)、[根布局](../../frontend-v3/src/routes/__root.tsx) 及 [PRD §7](../PRD-data-selection-and-assistant.md#7-ai-04-项目助手)：

| 当前事实 | 对用户的影响 | 建议调整 |
| --- | --- | --- |
| 助手位于 `Sheet`，最大宽度 `max-w-6xl`，内部对话与任务区各占一半 | 即使抽屉已经较宽，候选三字段、来源和对照仍只能使用一半区域；背景、任务、统计、候选纵向堆叠 | 页面级空间；结果区按需占主要宽度，支持展开查看 |
| 会话使用下拉选择，`selectedSession` 保存在组件状态；没有独立助手路由 | 不容易浏览旧工作，也缺少明确的会话直达地址 | 会话列表与带会话身份的 URL，刷新恢复当前会话 |
| 已有 PDF/MD/TXT 背景、当前生效要求、计划、停止/恢复、候选审阅、采用/发布确认 | 能力已经不少，但入口分散、同级卡片过多 | 按「资料与要求—执行—结果」组织，减少重复状态和常驻说明 |
| 助手正文使用普通段落及 `whitespace-pre-wrap` | Markdown 标题、列表、表格等不能自然呈现，长方案像文本堆积 | 受限、安全的 Markdown 渲染；工具结果仍使用可信业务组件 |
| 候选读取和选择以 `runId` 为入口，页面同时展示本任务总数与本批数量 | 用户完成一个目标时仍可能需要理解后台分批 | 默认审阅任务的当前有效候选；执行批次放入详情 |
| 候选已经复用 `ProcessingReview`，有搜索、分页、对照和选择 | 有可复用基础，无需重新设计另一套数据表 | 调整承载布局，复用现有审阅、来源和保存语义 |
| 当前回合运行时禁止发送后续消息；任务状态通过轮询读取 | 缺少及时说明时容易被理解为卡住；用户可能重复提交 | 显示实际动作、等待原因和最后更新时间；保留后续输入，明确何时可提交 |

现行 [架构 §3、§9](../architecture/data-selection-and-assistant.md) 已定义服务端会话、要求修订、步骤、后台运行和真实业务回执。独立页面应呈现这些事实，避免在前端另建任务状态来源。

### 3.2 Codex

官方开源范围包括 CLI、SDK 和 App Server；不能把整个桌面产品或云服务视为可直接复制的开源前端。[开源组件](https://learn.chatgpt.com/docs/open-source)、[仓库](https://github.com/openai/codex)

App Server 明确区分 Thread（会话）、Turn（一次请求及执行）与 Item（消息、工具调用、变更等），支持恢复会话、执行事件、计划更新、失败/中断状态与审批交互。这些是客户端协议和运行时能力，不等于已经提供 EvalBase 的数据审阅界面。[App Server：核心概念、事件与审批](https://learn.chatgpt.com/docs/app-server)、[App Server 源码说明](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)

对 EvalBase 的设计推论：会话保留连续目标；进度依据具体步骤与运行；成果绑定实际候选、草稿或版本；确认动作紧邻将受影响的数据。不要仅凭模型的一段「完成」回复改界面状态。OpenAI 的官方集成说明也将业务界面、业务上下文和工具权限留给宿主产品管理。[官方集成说明](https://developers.openai.com/blog/codex-as-a-platform)

本次建议沿用 EvalBase 现有运行时。如果以后考虑 Codex App Server，需要单独验证现有 Qwen 服务的协议适配、部署方式、会话隔离和工具授权；本轮没有做这些兼容性实验，也没有据此建议更换模型或框架。

### 3.3 OpenHands

核查快照：`bf483c12efbfae5c0ab586293d8bbc92f712bbed`。当前 `OpenHands/OpenHands` 主线为 Agent Canvas（beta），官方区分 Canvas、SDK、Cloud 和旧 Local GUI；此处只引用当前 Canvas 的会话组织。[仓库范围](https://github.com/OpenHands/OpenHands/blob/bf483c12efbfae5c0ab586293d8bbc92f712bbed/README.md)

两个值得借鉴的模式：独立会话页面具有标题、消息、输入和运行状态；完整文件视图与上下文概览按需切换，聊天只保留有限高度的产物入口。运行中的当前动作也在输入区附近可见。[官方会话说明](https://docs.openhands.dev/openhands/usage/agent-canvas/conversations)、[仓库页面功能说明](https://github.com/OpenHands/OpenHands/blob/bf483c12efbfae5c0ab586293d8bbc92f712bbed/.agents/skills/verify-openhands/references/feature-map/F07-conversation-page.md)

对 EvalBase 的设计推论：让结果和参考资料共享一块可展开区域，减少多张长卡片同时出现；窄窗口使用「对话／工作区」切换。终端、代码编辑器、Git 操作、多后端选择与本轮数据工作无直接关系，不列入首版。

## 4. 推荐页面

### 4.1 入口和布局

- 项目左侧导航新增「项目助手」，与原始数据、测试集、数据处理同级。建议地址形态为 `/projects/:projectId/assistant/:sessionId`，这里只表达设计，不代表路由已经存在。
- 原始文件、测试集草稿、版本或处理结果上的助手入口携带对象和选中范围。进入页面不立即调用模型；沿用会话时明确显示本次页面对象与已有任务对象，防止无意切换作用范围。
- 项目导航沿用现有折叠方式。助手内部的会话列表可收起；普通笔记本宽度不常驻「项目导航＋会话列表＋聊天＋结果」四列。
- 日常交谈时，主体是适中宽度的对话和输入区。打开结果后采用约 35% 对话、65% 工作区的起始比例，结果可展开到主体全宽；实际断点由 `frontend-v1` 布局和原型验证确定。
- 小窗口用「对话／工作区」切换，保留未发送文字、已选候选和滚动位置；不把两块长内容各压成半屏。

主体的概念布局如下，非像素级原型：

```text
项目助手    会话名称                       资料与要求 · 执行状态
----------------------------------------------------------------
会话列表（可收起） | 对话与输入          | 工作区（按需打开）
新会话            | 当前目标            | 结果 / 资料与要求
最近工作          | 助手说明            | 候选表格、原文对照
处理中 / 待审核   | 简短执行进度        | 来源、检查结果、选中行
                  | 提出修改要求        | 保存目标 + 确认操作
```

### 4.2 首版功能

| 功能 | 用户看到和操作的内容 | 实施取舍 |
| --- | --- | --- |
| 会话管理 | 新建、搜索、重命名、删除，列表显示当前阶段；打开 URL 恢复同一会话 | 重用现有个人会话；不因此变为全项目共享聊天 |
| 简短请求入口 | 空态提供「创建测试集」「清洗整理」「改写扩充」「查看数据」等短示例；点击后填入可编辑请求 | 不要求用户先选内部工具、填写 ID 或一整张任务表 |
| 资料与作用范围 | 「添加资料」区分选择项目数据和上传参考文档；显示文件/草稿名、所选条数和目标草稿 | 原始数据上传沿用已有映射流程；PDF/MD/TXT 背景复用现有能力 |
| 当前要求 | 顶部一行摘要，可展开查看数量、分类、字段保护和背景依据；自然语言更正后显示更新结果 | 读取现有生效要求，不从聊天中维护第二份前端规则；不承诺完整长期记忆 |
| 方案与执行 | 简单查询直接做；复杂任务展示短业务步骤。用户说「先给方案」时给可读方案及执行入口 | 用户已经要求执行时不重复确认开工；保留现有授权和采用/发布确认边界 |
| 可理解的进度 | 当前动作、已完成/目标条数、等待原因、最近更新时间、停止和适用的恢复动作 | 无可靠总量时展示阶段，避免虚构百分比或时间；说明已保留成果 |
| 宽幅结果审阅 | 问题、期望输出、Metadata、来源；搜索、问题筛选、对照、分页、勾选、展开查看 | 复用 `ProcessingReview`；默认查看当前有效成果，旧轮次按需打开 |
| 针对选中内容继续处理 | 勾选几条后说「只重写这些，保留答案」；输入框旁标明已选范围 | 复用现有候选选择和局部处理保护；范围更新使旧选择失效时明确提示 |
| 明确保存 | 从草稿进入时突出保存回该草稿，其他目标放次要入口；采用与发布显示目标及影响数量 | 复用服务端提案、修订和真实回执；不能把改写追加成重复数据或覆盖别人新修改 |
| 可读回复和失败恢复 | Markdown 列表、短表格和链接；错误聚焦失败位置、已保留内容、一个明确的恢复动作 | 不在聊天堆模型参数和调用 JSON；技术详情折叠，限额耗尽不能伪装成可重试 |

「数据处理」保留为直接操作与查看处理任务的页面；「项目助手」负责自然语言组织连续目标。两处指向同一批任务、轮次和结果，避免分别复制一份候选、采用记录或处理状态。

### 4.3 一个用户流程

1. 在原始数据中选择文件，点击助手入口；页面已带上文件名及选择范围。
2. 如需遵循某个标准或规则，添加参考文档。用户只需说：「用这份资料做一个 200 条测试集，按现有类型均衡，不足的扩写。」
3. 助手查阅数据，概括目标和必要假设；缺少会影响结果的条件时只问对应问题。后台操作沿已明确授权推进。
4. 用户看到「已选取多少条、正在补充哪部分、哪些检查未通过」。详情可展开，但输入框和当前状态始终容易找到。
5. 完成后打开宽结果区，按类型和质量问题核对，勾选需调整的记录，在同一会话提出修改。
6. 用户查看将保存的内容和目标草稿，点击确认采用；发布仍走现有独立确认。成果卡可重新打开草稿及其来源。

这是拟验收的交互示例，不表示短提示词一定能一次获得合格内容。用户可以在同一会话更正条件，明确区分候选生成、人工审核、采用和发布。

## 5. 技术方案与复杂度

推荐依赖路径为：**独立页面 → 现有助手会话及任务服务 → 现有受权业务工具 → 现有处理 Worker → 真实候选与业务回执**。页面直接读取这些事实。

### 可直接复用

- 现有模型连接和 AI SDK；不因 UI 变化切换模型供应商。
- session/turn/task、背景提取、要求修订、有序步骤、停止与恢复。
- 处理任务及轮次、候选审阅、来源展示、草稿冲突检查、采用和发布确认。
- 原始数据和测试集的列表、搜索、加载、分页以及 `frontend-v1` 组件和 token。

### 必要新增或调整

1. **路由和页面承载**：拆出可复用的会话读取/操作逻辑、对话、资料、进度和结果组件；只按实际复用点拆分，不建立通用插件框架。会话身份、项目与账号权限参与缓存隔离。
2. **会话入口和当前上下文**：对象选择、范围摘要和背景入口。页面返回不停止后台任务；跨项目导航不能把当前会话自动改绑到新项目。
3. **任务级候选审阅**：当前组件按 run 读取，如果一个任务跨多个批次，需补充或调整服务端聚合分页读取，按现有有效候选范围去重、过滤和稳定排序。旧轮次结果不会重复计入。跨批选择必须绑定实际 run/result 身份及候选修订，不能仅用界面行号。
4. **轻量进度读取**：先测量现有会话轮询体积，复用可用摘要；正文、历史、候选按需读取。只刷新活动会话或进行中的运行，不为会话列表逐个拉取全部候选。后台等待不轮询模型。避免把独立页面做成新的大接口。
5. **可信展现**：回复采用安全 Markdown 渲染；计划、状态、结果和确认由结构化响应渲染。数据表及 Metadata 按文本处理，外部正文不能生成操作授权。

逐 token 流式回复可以在需要时单独验证。首版应先解决「已收到、正在做什么、结果在哪里、失败后怎么继续」，没有必要为了打字动画同时重写模型协议和执行循环。

当前按约 10 人同时使用设计。该方案不要求新服务、新数据库或另一套工作流引擎。若读取接口确有缺口，应针对缺口补充，不能预先承诺所有改动都是纯前端，也不能借机重构全部助手后端。

## 6. 落地顺序与验收重点

先确认三种页面状态的轻量原型：新会话、执行中、候选待审核；继续使用 `frontend-v1` 的浅底、蓝色主操作、字体、间距、图标和表格。对话正文减少层层边框，工作区保留必要边界；状态采用短文字和小标记，取消占大量空间的常驻说明卡。原型通过后再更新受影响 PRD 和开发 Ticket。

开发第一步完成独立路由、会话恢复、上下文入口、现有进度和结果组件重排；第二步围绕同一完整任务补齐任务级候选、局部调整和保存衔接。两步共同验收一个完整闭环，不以「抽屉搬到了页面」作为最终完成标准。

最小验收集合：

- 直接打开会话地址、刷新、切页面再返回，任务和已生成成果仍可读取；切项目、账号或权限变更不会泄漏旧正文。
- 用短请求完成「选取 → 处理 → 核对 → 局部修改 → 确认采用」，全程保持同一会话；背景、源数据和当前目标可辨认。
- 多批结果合并审阅时不重复、不遗漏；搜索、分页、选择和当前有效候选范围一致。
