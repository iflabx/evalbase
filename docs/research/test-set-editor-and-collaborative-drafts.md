# 测试集全页面编辑与协作草稿调研方案

- 日期：2026-09-27
- 状态：调研建议，待 Owner 选择；不修改现有产品合同，不代表已实现。
- 项目基线：服务器 `/home/bistu/EvalBase`，`codex/prototype-login-multiuser`，`4681499`。
- 本次范围：研究创建/派生编辑体验、资料规模和版本可变性；不修改原型、应用代码或部署。

## 1. 建议结论

建议把“新建测试集”和“继续创建新版本”改为完整页面，复用同一个编辑工作区。派生编辑直接带入父版本记录；只有需要追加资料时才打开资料选择页面，不再强制经过两页资料选择步骤。

建议加入可反复保存的共享工作草稿。用户在版本页点击“编辑数据”，自动打开或继续“基于 vN 的草稿”；多人可以在这个草稿内持续修改，准备好后一次创建正式版本。保存草稿不分配 vN，也不要求逐次创建正式版本。

不建议允许覆盖已创建的叶子版本。叶子仅表示没有后代，无法说明它未被下载、用于外部评测或被其他人引用。保留可变草稿与固定正式版本，能同时满足编辑便利和可追溯性。

## 2. 项目实际情况

当前服务器的权威文件是 [PRD](../PRD-evalbase-v1.md) 与 [CONTEXT](../../CONTEXT.md)。本机旧版 `PRD-v2-test-data-management.md` 不能用于判断当前产品。

- PRD FR-05/FR-06 与 CONTEXT 明确：创建得到不可变版本，后续增删改形成新版本；可从任一完整历史版本派生，保留固定父边与标签。
- 当前容量：一次编辑最多涉及 5 个资产、100,000,000 原始 bytes、10,000 条源记录；正式版本最多 10,000 条记录、100,000,000 bytes 内部规范化内容。本方案不自动提高这些限额。
- [ADR-0011](../adr/0011-incremental-test-set-version-storage.md) 已采用稀疏 Delta、Checkpoint 与统一读取，用户仍看到完整不可变快照。增加正式版本不等于每次完整复制所有数据，但仍有元数据、回放与维护成本。
- [架构](../architecture/phase1a-architecture.md) 允许在内部复用 Draft/lease 等机制，并不代表已经提供持久共享草稿的完整用户功能。
- 当前 [登录协作探索原型](../prototypes/THROWAWAY-phase1a-login-multiuser-vnext.html) 的 `testSetBody()` 先列出项目资料，再按文件展开记录，最后把编辑记录按来源整组展示；选择/编辑流程未复用版本浏览页的分页与筛选。样例少时可用，接近容量上限时会产生很长的列表。
- 原型的协作依赖浏览器本地账号数据与 BroadcastChannel 演示。在线头像、演示冲突提示不能证明正式服务已具备跨设备协作、断线恢复或安全的同时发布。
- 外观继续遵循 [frontend-v1 复用规则](../architecture/phase1a-frontend-reuse.md)：复用字体、颜色、表格、输入框、按钮与导航样式，仅借鉴外部产品的工作方式。

## 4. 完整编辑页

### 4.1 入口与状态

| 场景 | 建议入口与落点 |
| --- | --- |
| 新建测试集 | 打开编辑页，顶部填写名称和可选用途；空状态提供“添加资料”“手工新增记录” |
| 编辑叶子版本 | “编辑数据”打开基于该版本的共享草稿，直接看到全部继承记录 |
| 编辑历史非叶子版本 | “基于此版本编辑”，醒目标明父版本；创建时按现有规则形成分支 |
| 同一父版本已有草稿 | “继续编辑草稿”；协作者进入同一草稿，避免悄悄建立各自副本 |
| 已发布、墓碑或回收对象 | 保持各自现有浏览和删除限制；墓碑不提供编辑入口 |

首次进入可以只是草稿占位，第一次有效修改/添加记录时再保存实际草稿。建议同一测试集、同一父版本最多一个活跃共享草稿；不同父版本明确区分，禁止把两个分支的修改混在同一草稿。新建测试集也有独立草稿身份。

### 4.2 布局

```text
项目 / 测试集 / 基于 v3 的草稿
名称、用途                 在线成员  已保存至草稿  [退出编辑] [创建新版本]
记录 | 变更
搜索 / 来源 / 内容筛选 / 仅看已修改     [添加资料] [新增记录]
已选 50 条：批量操作 / 清除选择
复选框 | 序号 | 问题 | 期望输出 | Metadata | 修改状态
分页与总数                            右侧可展开单条详情编辑
```

- 保留项目侧栏，可收起以扩大空间；表头和主要操作区固定，不让用户滚到长列表底部才找到操作。
- 表格用于定位与短文本编辑；长问题、长输出、完整 Metadata 在可调整宽度的右侧详情区编辑，并提供上一条/下一条。窄窗口时详情区改为同页面完整详情视图。
- 继承的记录默认全部带入。修改十条记录无需重新挑选剩余几千条，也无需先走“添加资料”。
- “记录”显示完整当前草稿；“变更”只显示相对父版本的新增、修改、移除，点击可看前后值。已移除记录可在变更页恢复到草稿。
- 创建按钮仍采用现有“创建 v1”或“创建新版本”用词，旁边说明将生成固定快照；不引入审批、强制修改理由或版本命名步骤。正式标签仅在创建成功时分配。
- 退出保留已保存草稿。丢弃草稿是独立明确操作，并说明它会影响正在共同编辑的人；普通返回/切页不会丢弃内容。

## 5. 大量资料与记录选择

“添加资料”进入完整资料选择页，顶部始终提供“返回编辑”和“添加所选记录”。返回时保留草稿、筛选、当前页和选择。

1. 左侧展示可搜索的数据集与文件，支持折叠和数量信息，避免默认展开所有资料。
2. 中央按选中文件显示可搜索、可筛选、分页的记录表；右侧按需预览完整内容。复用当前已有的来源、问题是否填写、Metadata 等筛选语义。
3. 区分“选择本页 50 条”和“选择全部筛选结果 2,360 条”。显示跨页选择总数，并提供“仅看已选”和“清除选择”；切换分页不会清空选择。
4. “选择整个文件”应是显式操作，不能把仅仅查看文件误认为把文件全部加入。添加按钮显示真实条数。
5. 在执行批量添加时固定这一次的候选记录集合与顺序；后续筛选变化、其他人上传文件或再次点击按钮，不应静默改变本次操作范围。
6. 超出 5 资产/10,000 条等限制时指出具体超出的量，保留选择供调整。批量选择不是取消容量上限。
7. 防止同一次选择操作被重复提交，但不按问题文本自动合并不同来源的记录；重复内容仍按现有规则提示，不偷偷去重。

正式实现采用有界分页/查询；跨页全选不能靠把全部数据加载进浏览器。原型可以用 Mock 模拟大数量、分页与选中摘要，但不能据此宣称真实 10,000 条性能达标。

## 6. 批量编辑

首批建议提供：批量移除、批量添加/修改/移除指定 Metadata 字段，以及“仅看新增/已修改/已移除”。批量操作先展示目标数量与作用范围；遇到同名 Metadata 字段时明确“只填空白”或“覆盖选中值”，避免隐藏覆盖。

保留逐行编辑和上一条/下一条。为长文本显示完整编辑区与快捷保存反馈。查找替换、表格粘贴、保存筛选视图、复杂批量改写可以后续加入，避免第一版变成通用数据处理平台。

撤销必须有明确范围。多人情况下“撤销我的修改”不能回退整个共享快照，从而抹去他人的工作；若目标字段已被别人继续修改，展示冲突而不直接回滚。

## 7. 能否直接修改叶子版本

技术上能实现，但不建议用“没有子版本”作为允许覆盖条件。例如：上午下载了 v3 做评测，下午同事修改仍叫 v3，晚上再次下载便得到另一份数据；版本图虽然还是叶子，v3 已经失去稳定含义。

| 方案 | 用户体验 | 代价与建议 |
| --- | --- | --- |
| 原地覆盖正式叶子版本 | 保存直观 | 历史引用、导出缓存、内容 hash、溯源与增量基线不再稳定；不推荐 |
| 每次保存自动生成历史版本 | 编辑顺畅，类似 Langfuse 方向 | 需要区分内部修订与用户看到的里程碑，避免正式版本图充满微小改动；可作为未来方向 |
| 共享草稿反复保存，完成后创建正式版本 | 连续编辑方便，版本数量可控 | 需增加草稿持久化和并发规则；最适合当前 EvalBase |

因此“暂时不新建正式版本就持续修改”完全可以提供，编辑对象建议命名为“基于 v3 的草稿”。草稿内部仍需修订号支持同步与冲突判断，但它不消耗 v4/v5 标签。

如果坚持界面里一直叫 v3 且直接修改，则底层也应保存不可变 revision，导出、评测和分享必须引用 version ID + revision。这样仍需要完整修订体系，且用户必须理解同一个 v3 的多个状态，比共享草稿方案更复杂。

## 8. 多人协作规则

- 共享内容以服务端草稿为准；不同用户/设备通过草稿 ID 进入同一工作区，父版本固定不漂移。
- 顶部保留在线头像，单元格显示编辑者；保存状态分别显示“保存中”“已保存至草稿”“连接中断，修改尚未同步”。
- 不同记录或不同字段可以并行编辑；同字段优先采用短时占用提示与服务端修订检查。冲突保留双方输入，不静默采用最后到达的值。短时锁需超时/断线释放，不能永久阻塞字段。
- 删除一行、批量修改与别人正在编辑相交时，也需要冲突提示；只处理输入框冲突不够。
- 创建正式版本针对一个明确的已同步草稿修订。未确认保存、冲突未处理时不能把用户以为已包含的数据漏掉；创建操作需要原子性和幂等性，双击或两个成员同时创建不会产生重复版本。
- 创建期间明确显示正在提交的草稿状态；成功后该次草稿内容转为对应正式快照。后续编辑开启下一草稿，不把创建后的修改悄悄塞回刚刚生成的版本。
- 查看者保持只读；编辑者/负责人沿用已经确定的项目权限。是否限制“创建版本”到负责人属于另一个权限选择，本方案不顺带添加审批限制。

## 9. 建议的原型迭代顺序与验收

第一轮：替换两个大弹窗为同一全页面工作区；加入资料筛选、分页、跨页选中、详情编辑和变更视图。用 0 条、少量记录、接近 10,000 条的 Mock 场景检查布局与操作语义。

第二轮：加入显式草稿、自动保存状态、退出后继续编辑、多人冲突/断线/同时创建场景。原型阶段演示这些状态；正式研发需要服务端持久化、并发测试和容量验证。

验收重点：

- 从 v3 修改 10 条时不必重新选择原有资料；旧 v3 下载内容不变。
- 跨页选中 500 条、排除 3 条后，最终添加明确为 497 条；改变筛选不误清空或扩张原选择。
- 退出再进入恢复草稿；未保存失败不会假显示成功。
- 两人改不同字段可同步；同字段冲突可解决；移除行与批量修改不会覆盖他人输入。
- 创建新版本包含确认的草稿修订；失败保留草稿且不消耗标签；同一次创建重试不重复生成版本。
- 查看者、已移除成员、过期连接的操作权限被正确处理。

正式开发前再将选定方案同步到 PRD、CONTEXT、架构及相关 ADR、流程图与 Tickets。共享草稿是新增用户生命周期，现有正式合同明确没有可编辑版本，不能仅把 HTML 改成大页面便视为完成正式设计。
