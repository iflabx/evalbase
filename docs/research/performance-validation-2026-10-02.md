## 5. 瓶颈与优化建议

### 已证实的问题

1. **单文件超限不能返回可处理的 HTTP 错误。** `requests-heavy.jsonl` 中 50,000,001 byte 上传约 393 ms 后 `fetch failed`、status 0。原生 HTTP 复核约 261 ms 后 `ECONNRESET`，可见资产 27→27。`src/storage/artifacts.ts` 的超限 meter 错误后调用 `stream.destroy()`，而 pending-upload 路由稍后才试图发送 413；代码与真实传输现象支持这一原因。不是 OOM，也没有新资产。本次没有修改应用；首轮日志/hash 在 `attempt1/`，恢复决定在 `resume-decision.json`，该失败一直保留。
2. **20 条分页仍有全版本成本。** 停止负载后的有界只读 EXPLAIN：100 条模板约 19.93 ms，10,000 条约 611.63 ms；后者解析 10,000 个成员、对 `case_revision` 做 10,000 次索引访问、Metadata 展开 20,000 项，临时块读/写 2,600/1,300。计划的成员函数启动约 427 ms。这是大夹具已存在时单次诊断，不与先前小库客户端基线拼成提速/退步比例。
3. **导出命中缓存仍有明显成本，重操作干扰存在。** 重复万条 CSV 仍约 1.5–1.9 秒；当前版本模块在查缓存前读取当前/父记录、计算变更及 canonical fingerprint。减少这部分重复工作是代码支持的推论；STOP 后没有再做缓存 HTTP 复测，不能声称已经测得其精确 CPU/SQL 份额。浏览器慢翻页与 Web 生命周期 loop 峰值、SQL 全版成本一致，但未采 CPU/GC profile，不把相关性当作完整归因。

### 优先优化方向

| 顺序 | 建议 | 预期用途 / 成本 / 风险 |
| --- | --- | --- |
| 1 | 修复超限流处理，给真实 HTTP 传输返回 413；覆盖已知长度及流式超限 | 小范围正确性修复，成本低；须保留中止存储/清理和容量限制，不能只用注入测试 |
| 2 | 让 CSV 缓存命中避免重新构造完整记录/溯源 fingerprint | 降低重复导出与其他用户等待，成本中；每次权限、状态、删除和证据失效仍必须校验 |
| 3 | 减少分页读取中的全记录加载和重复来源/Metadata 汇总 | 重点改善万条读取及重操作干扰，成本中；保持排序、计数、过滤及成员完整性合同 |
| 4 | 按实际高 bytes 路径测编码/解析和内存，再逐处减少大字符串/对象副本 | 降低 100 MB 场景 RSS/主线程等待，成本中；哈希、CSV 字节及发布原子性须保持 |
| 5 | 复核测试内存保护的文件缓存口径及数据库/存储预算，再安排未完成容量场景 | 避免把可回收缓存误称堆泄漏；成本低，须仍保留 OOM、压力与主机余量保护，不能本轮临时放宽保护线 |

没有测量这些改动的收益，不承诺百分比或人数上限。当前进程/数据库/Worker/对象存储结构可以继续优化上述路径，证据不足以支持为最多 10 人引入微服务、Redis 或容器编排平台。
