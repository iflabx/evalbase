## 1. 结论与证据边界

**工程判断：继续使用 ToolLoopAgent、PostgreSQL 会话/回合、现有处理运行与 Worker，补齐可持久恢复的阶段与预算让出即可。** 当前任务主要是有限业务步骤与有界批处理，已有恢复机制可以承接新增检查点；本次证据没有显示迁移框架是必要条件。

## 2. ToolLoopAgent 固定版本的实际边界

### 2.1 停止条件、步骤与工具调用

| 来源事实                                                                                                                                                                                                                                                                                                                             | 对当前问题的影响                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `ToolLoopAgent.generate()` 委托 `generateText()`；默认停止条件为 `isStepCount(20)`。[固定源码](https://github.com/vercel/ai/blob/ai%407.0.127/packages/ai/src/agent/tool-loop-agent.ts)                                                                                                                                              | SDK 管理一次调用内的循环，没有替应用保存跨回合任务。                                                   |
| `isStepCount(n)` 按已经完成的 `steps.length === n` 判断；条件数组任一为真即停止。`stepCountIs` 在该版仍是弃用别名。[停止条件源码](https://github.com/vercel/ai/blob/ai%407.0.127/packages/ai/src/generate-text/stop-condition.ts)、[导出源码](https://github.com/vercel/ai/blob/ai%407.0.127/packages/ai/src/generate-text/index.ts) | 一步是一次模型响应及其工具执行，不能把步骤数当工具数；协议纠错另开调用时，必须使用应用层共享计数。     |
| 一次响应可包含多个工具调用；`executeTools()` 用 `Promise.all` 执行。`stopWhen` 在该步工具输出收齐后才判断是否继续。[执行源码](https://github.com/vercel/ai/blob/ai%407.0.127/packages/ai/src/generate-text/generate-text.ts#L1632)                                                                                                   | 设置让出标志不会自动阻止同响应已经返回的后续工具。依赖顺序、工具总预算及副作用门禁要在业务工具内落实。 |
| `prepareStep` 在每次模型请求前运行，能调整 `toolChoice`、`activeTools`、说明与消息；覆盖的消息成为后续步骤的基础。[官方循环控制](https://ai-sdk.dev/docs/agents/loop-control#prepare-step)                                                                                                                                           | 适合安排当前阶段、缩小工具集合、检查软预算和保留上下文；它不负责后台唤醒。                             |

**工程判断：** 保留当前工具队列的串行执行，并把“已提交处理后延后同响应后续工具”的保护扩展到预算让出。单纯增加 `stopWhen` 或在提示词里要求少调用工具，不能代替这个保护。直接按 SDK `stepNumber` 计数也不能覆盖第二次协议纠错调用；共享预算应覆盖整个业务回合。

### 2.2 finishReason、错误与 abort

`finishReason` 是最后一次模型响应的结束原因，取值包括 `stop`、`length`、`tool-calls`、`content-filter`、`error`、`other`。SDK 的聚合结果保留最后一步原因；这个字段没有“业务目标已完成”或“应用预算已让出”的含义。[官方返回值](https://ai-sdk.dev/docs/reference/ai-sdk-core/generate-text#returns)、[固定结果实现](https://github.com/vercel/ai/blob/ai%407.0.127/packages/ai/src/generate-text/generate-text.ts#L1766)

固定源码允许在 `stop` 和 `tool-calls` 两类响应中执行原生工具；循环还会检查工具输出是否齐全和停止条件。因此，不能仅从一个 `stop` 推断没有工具调用，或从 `tool-calls` 推断所有业务步骤已完成。[允许执行的原因](https://github.com/vercel/ai/blob/ai%407.0.127/packages/ai/src/generate-text/is-tool-execution-allowed-finish-reason.ts)

SDK 接受整体 `abortSignal` 与超时设置，并把信号传到工具执行；工具异常会被转换为工具错误结果。[官方调用参数](https://ai-sdk.dev/docs/reference/ai-sdk-core/generate-text#parameters)、[固定工具执行源码](https://github.com/vercel/ai/blob/ai%407.0.127/packages/ai/src/generate-text/execute-tool-call.ts)

**工程判断：** 应用分别保存 SDK 结束原因和自身的终止原因。`length` 应视为输出可能不完整，不能解析普通文本工具代码后执行；停止/撤权/来源失效要依靠现有数据库修订与执行令牌阻止提交。Abort 不能撤销已经提交的数据库事务或保证外部请求没有生效，也不能取代业务回执恢复。

### 2.3 持久续做与工具回执

普通 ToolLoopAgent 的运行时在内存中。官方另一方案 `WorkflowAgent` 使用 Workflow 运行时，依赖 `@ai-sdk/workflow`、`workflow@5`，可持久保存模型调用与步骤；它不是给原类增加一个选项。[官方两类 Agent 对比与安装](https://ai-sdk.dev/docs/agents/workflow-agent)

SDK 返回标准 `responseMessages`，含累积的 assistant/tool 消息，可追加到下一次调用的历史。[官方工具消息](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling#response-messages)

**工程判断：** 历史工具消息供模型理解，真实业务回执供程序确认效果。恢复要先按保存的逻辑操作键、参数摘要与领域结果核对，再重建匹配的 tool-call/tool-result；不要仅因聊天里出现“成功”就跳过，也不要因为模型生成了新 toolCallId 就重新提交。大正文继续放处理产物，消息仅带受限摘要与可授权重读的引用。

## 3. 可靠后台执行的一手证据

| 来源事实                                                                                                                                                                                                                                                                                                                  | 可借鉴的机制                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| PostgreSQL 明确说明 `SKIP LOCKED` 可帮助多个消费者避免争抢队列表中的锁，但返回的是不一致视图，不适合一般查询。[SELECT 锁定规则](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)                                                                                                             | 领取阶段可以复用现有队列锁；业务状态与全量分类统计必须另查完整固定集合。锁本身不保证外部调用或副作用只执行一次。 |
| LangGraph Functional API 恢复时从入口重新执行，以检查点重放已完成 task 结果；尚未完成的 task 可能再运行，需要幂等键或结果核对。[确定性与幂等](https://docs.langchain.com/oss/javascript/langgraph/functional-api#determinism)、[幂等要求](https://docs.langchain.com/oss/javascript/langgraph/functional-api#idempotency) | 保存非确定性模型结果和完成回执，重启后复用完成批次，仅执行未完成工作。无需采用该框架才能落实这个模式。           |
| LangGraph 中断恢复会重跑节点开头，官方要求中断前副作用幂等或放在独立节点。[中断规则](https://docs.langchain.com/oss/javascript/langgraph/interrupts#rules-of-interrupts)、[副作用要求](https://docs.langchain.com/oss/javascript/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent)            | 确认等待必须持久化固定参数；恢复不能绕过原业务确认和原子回执。迁框架仍需这些约束。                               |
| 官方将重试、单次超时、耗尽后的错误处理，以及在边界干净停止后恢复分别描述。[故障处理](https://docs.langchain.com/oss/javascript/langgraph/fault-tolerance)                                                                                                                                                                 | 预算让出和失败重试应有不同事件与错误语义；不能把所有耗时结束都作为失败或无限重试。                               |

本次访问的 LangGraph `durable-execution` 入口已转向 [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence)。上述具体重放与幂等事实引用实际可读的 Functional API 和中断文档，避免沿用旧入口标题推断功能。

## 4. 当前项目基础与最小充分方案

### 4.1 已有基础（本机静态事实）

- [agent.ts](../../src/assistant/agent.ts) 已实现 `ToolLoopAgent`、10 步/12 工具/80 秒预算、协议纠错共享计数、业务工具串行队列、参数摘要操作键、回执恢复与处理提交后的让出。最后一步强制不调用工具；尚未完成的 `nextAction` 会触发未执行错误。
- [tasks.ts](../../src/assistant/tasks.ts) 已持久保存任务、修订和后续回合，以 `processing_completed`/`confirmed` 事件幂等安排续做，检查权限与依赖，并限制每段 12 个自动回合及会话总回合数。当前没有专门的预算让出事件。
- [Worker](../../src/worker/main.ts) 已有 `FOR UPDATE SKIP LOCKED`、租约、attempt 与失效执行保护；[processing](../../src/processing/execute.ts) 保存批次结果并复用成功产物。处理配方当前只有清洗、改写、扩写；字段白名单由 [protocol.ts](../../src/processing/protocol.ts) 校验。

这些事实是代码读取结果，不是本次运行测试结论。当前基线与已完成历史功能应按 [验收文档](../assistant-optimization.md) 继续核对。

### 4.2 可执行方案与真实阶段（工程建议）

方案至少保存当前目标、生效要求、明确来源范围、有限步骤、当前步骤和下一业务动作。步骤仅需覆盖本任务实际阶段，例如资料核对、方案准备、后台分类、规则选取、结果核对、等待审核；普通 JSON 状态与现有任务修订足够，不先建设任意 DAG 编辑器。

`plan_task` 保存方案后，执行器检查下一动作是否实际完成、已提交后台、等待明确缺项或等待确认。模型只写“接下来执行”时继续原授权动作；不能靠一个非空最终回复消除尚未履行的义务。真正澄清要保存具体缺项，且已经持久保存的数量、来源、类别定义和用户修订无需再次填写。

进度来自领域结果：已读片段、已提交的处理运行、已完成/总批次、已分类/未分类记录、各类别可选数、实际选中数和候选核对结果。模型可解释阶段；百分比、全部完成和最终数量由程序确定。只读预览的一页数据不能代表完整范围。

### 4.3 预算让出与恢复（工程建议）

1. **保留硬预算，增加软边界。** 在 `prepareStep` 以及工具队列执行前检查剩余步骤、工具数与墙钟时间。临近边界时停止新副作用，保存下一动作、固定对象引用、必要游标与真实进度。汇总可由服务端根据回执生成，不必为了文字汇总丢掉最后一个业务动作，也不能提高预算后继续无限执行。
2. **原子记录可续做边界。** 当前回合终结与检查点在同一事务中提交；预算让出保存明确原因及 `pendingAction`，不能清空目标或标为目标完成。已经有处理运行或待确认卡时进入对应等待，不同时排第二条预算续做。
3. **复用现有调度器。** 新增明确的 `budget_yield` 事件；事件键至少绑定任务修订和前一回合 ID。持久扫描发现尚未消费的让出点后调用既有续做入口，幂等约束防止双排。调度在浏览器关闭和 Web 重启后仍可发现检查点。
4. **续做先核对效果。** 重读当前授权对象与关联运行，恢复已有成功回执；副作用继续沿用原逻辑操作键。可另开模型回合刷新单轮预算，但逻辑步骤与原参数身份必须连续。现有同回合重试用的键不能直接复制成“新回合的新操作”。
5. **区别让出与异常。** 软预算触发且有可信检查点时可以自动续做；硬 abort、进程崩溃或响应丢失时先恢复领域回执。确认无法核对的未知副作用不能盲重放。部分成功要保留并说明未完成范围。
6. **保留整体上限与无进展退出。** 自动续做仍计入已有每段/会话上限。保存进度指纹，反复相同读取、相同游标或重复计划且无领域变化时进入明确失败/需输入，不能借让出事件无限续做。停止、撤权、来源删除和任务修订使旧检查点失效。

同响应包含“提交处理 + 后续写入”时，串行队列在处理回执提交后把后续工具标为延后；预算让出采用相同原则。延后不表示业务工具成功，不能新增成功回执。具体动作重新安排后仍复检权限、当前修订与原确认边界。

## 5. 全量语义分类后按规则选取（工程建议）

来源已经有可信的分类字段时，直接复用确定筛选；需要依据内容判断类别时，提交一个后台分类步骤，不能让短轮助手按每页 20 条逐轮读完并在模型记忆中累计标签。

最小流程为：冻结获授权的记录集合及来源身份 → 冻结类别定义、冲突/未知规则、配方和模型版本 → Worker 分批分类并校验稳定 sourceId → 持久保存逐记录标签与失败状态 → 程序按完整标签结果计算类别数量、配额与固定种子选取 → 输出候选预览与审核。

当前 `rewrite + allowedFields: [metadata]` 可以承载“只给候选增加分类”的模型结果，但还需让规则选取消费该固定处理结果，并保留原始来源身份。若分类只作为内部选取依据，可把分类映射放在已有处理产物，不必先把全部记录写入草稿或原始资产。它不是现成支持的完整链路，不能仅改变提示词便宣称完成。清洗/改写一条输入一条输出、用户允许字段和采用确认仍按当前合同校验。

必须区分两种任务语义：按自然内容分类后抽样，类别数量由内容决定，不能为了凑配额强制给每批贴固定数量的标签；按用户指定配额扩写新题目，才可按配额生成内容。当前生成配方中的批次配额逻辑不应原样用于语义分类。

- 模型只决定语义标签，程序校验允许类别、重复/缺失 sourceId、稳定输入范围及受保护字段。低置信或无法归类保留为明确状态，不凭样本推定未处理记录。
- 规则按固定分类快照执行。每类候选不足时返回实际缺口；多标签重叠按预先确定的去重/归属规则处理，不能由最后一个聊天回合随意补足。
- 分类统计显示已完成、失败、未知与未处理数量。只在覆盖范围明确且满足本任务完成条件时形成最终选取；部分结果不能展示成全量分类完成。
- 重试仅处理失败或缺失批次，保留成功分类；类别定义、模型配方或输入变化形成新的检查点/运行，避免混用两套含义。
- 业务 Metadata 中的分类不能替代用户要求的逐题期望输出；分类正确性仍需人工语义审核。采用/发布继续使用现有固定确认与领域事务。

## 7. 实施验证应覆盖的具体风险

1. 方案后没有文字承诺即停：假模型先保存计划再直接结束，原授权动作自动完成或出现真实澄清/确认等待。
2. 单步多工具：一响应返回超过剩余工具额度、相互依赖动作或处理提交后的写入；最终副作用、延后记录和回执数与预算一致。
3. 预算让出：资料读取多于单轮预算，自动续做不重复成功操作；任务数量、类别与游标跨回合保留；达到整体上限或无进展时明确停下。
4. 崩溃与响应丢失：在领域提交前后、检查点保存前后、后续入队前后注入故障；重启只恢复原逻辑结果，不多建处理、草稿、采用或版本。
5. 停止与修订竞争：已排续做期间停止、补充指令、撤权或删除来源，旧执行不能写入；待确认卡不被让出事件绕过。
