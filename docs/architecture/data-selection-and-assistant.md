## 1. 模块与依赖

本轮实测优化的范围与逐项证据见 [合同](../assistant-optimization.md) 和 [Spec](../../.scratch/assistant-optimization/spec.md)。缺失恢复复用 processing 批次与既有 Worker；采用同步以同账号、运行、候选及目标参数的真实回执为依据。下载沿用两个受权 CSV 接口，由浏览器使用已有 fflate 无压缩打包为单个 ZIP，不增加服务器导出路由。

- 保持 Fastify + PostgreSQL + MinIO + Worker + frontend-v3。AI SDK 7.0.127、兼容 provider 3.0.62 固定版本，实测后写锁文件；不引入 Python、Redis 或另一个工作流平台。
- 筛选、处理、助手各有窄业务模块；HTTP 与 Agent 共用业务函数。通用循环由 SDK 承担，权限和持久化由项目控制。
- source-selection 旧添加接口保留既有合法调用的语义直到前端切换完成；新增固定预览接口支撑新操作，不能用旧即时查询冒充固定集合。
- UI 复用现有 ui/button、input、dialog、table、card、下拉与表单样式。新助手不复制供应商 UI 样式。

## 2. 固定选取

- 服务端白名单条件，AND 合并。映射到可见字符串后 trim + 大小写无关比较；缺失 Metadata 为空，禁止动态 SQL 字段名。
- 最多 5 个资产、10,000 记录的有界候选在服务端计算。来源去重身份保持 assetId + ordinal；parsedViewId 单独冻结以复现当时的视图/映射/内容摘要，映射变化不产生新的来源身份，来源失效拒绝应用。
- 正式随机选取采用固定种子与稳定来源身份的 SHA-256 排序，按 hash 后稳定身份排序取前 N；算法版本 `sha256-rank-v1`。排序结果恢复原始稳定来源顺序展示。比例按候选数向下取整，数量不足取全部。不要改变旧 recipe 的不同过滤语义。
- PostgreSQL 保存 preview ID、project、draft、creator、规则、视图与候选/选中 ID、基准 revision、创建时间、应用回执。无须在表中复制原始正文。
- 预览查询分页，人工选择提交候选 ID 子集/排除集合；服务端检查只能来自冻结候选。UI 修改配置立刻 dirty，不能确认旧结果。
- 应用事务锁定草稿、复检授权/依赖/基准 revision，复用批量写入和容量检查，写选取历史和回执并更新 revision。回执优先核对重复请求；业务失败全部回滚。
- 草稿变化时返回当前 revision，UI 明确核对后提交该 revision，不自动重试覆盖。发布时在同一发布事务关联选取历史，来源页按版本读取。

## 3. 模型连接与短轮 Agent

- 实例级连接由管理员维护。key 使用 AES-256-GCM 与服务端环境主密钥加密，数据库只存密文/nonce/tag；响应只返回 hasKey，不回显密钥片段。配置更新采用连接 revision，运行保存配置快照/版本引用。
- 端点为明确 http/https base URL；拒绝凭据、片段、重定向。模型工具参数不能修改目的地址。真实端点 TLS 按系统信任验证，不禁用证书检查。
- 以 createOpenAICompatible().chatModel() 对象传给 SDK。先验证非流式多轮，再流式；结构输出必须本地校验。请求超时、输出 token、工具步骤和正文大小有上限。
- 测试兼容端点的强制工具解码不支持 `uniqueItems`：仅从模型侧 Schema 描述省略该关键字；本地 Ajv 保留完整 Schema，重复参数仍被拒绝且不产生业务副作用。
- 服务端会话保存用户消息、回合状态与工具结果摘要；single-flight/数据库锁约束同会话并发。模型不持有客户端 cookie、密钥或任意项目能力。
- 会话管理遵循 PRD §7：`PATCH /sessions/:sessionId` 仅接收 title，以 `custom_title` 独立保存用户名称；读取优先使用此名称，任务标题继续按任务更新。`DELETE` 复用任务控制事务的并发锁、job/run → session 锁序和修订 fencing，删除提案、回合与背景后删除会话；背景相关处理副本复用既有清理队列，已采用的独立资料、草稿和正式版本保留。两接口校验当前项目访问权、本人身份及 Origin/CSRF，查看权限账号也可管理自己的会话。
  删除仅取消本人关联的运行，不取消只查询过的其他成员任务。并发局部调整发生数据库死锁时最多重试整个删除事务两次；已提交删除不因对象存储暂时故障变成失败，返回 `deleted: true, cleanupPending: true`，Worker 继续处理持久清理队列，附属副本立即不可读。响应丢失时前端通过 `GET /sessions/:sessionId/status` 精确核对当前账号的会话是否存在，不依据分页清单或历史可读性推断；确认已消失后完成页面清理；无法核对或会话仍存在则保留确认框与输入。重命名取消旧会话查询后更新名称缓存。
- 写操作提案与确认在服务端持久化；确认与领域副作用使用稳定逻辑 operation ID。同一操作的参数 hash 不一致拒绝。
- SDK 钩子只记执行观察，不代表与数据库事务原子。崩溃后通过业务回执核对；未完成回合显示 interrupted。无需增加完整图运行时。
- 遥测显式关闭外发，日志记录 ID/状态/耗时而不记录凭据与任意数据正文。

### 当前实现约束

- 助手使用非流式短轮请求，HTTP 提交后返回 202，前端读取服务端进度。每回合最多 10 个模型步骤、12 次工具调用、80 秒模型等待；数据库回合到期为 90 秒。每账号最多一个运行回合，实例最多三个，每会话最多 100 回合。工具格式误写为文本或原生工具协议校验失败时，至多纠错一次；共享该回合的步骤、工具和超时预算，并保留真实调用回执，不解释执行 XML。最后一步仍预留汇总，附件读取后可用剩余步骤完成真实提交。
- 历史工具调用与回执使用标准 assistant tool-call / tool-result 消息配对，每个历史回合的工具正文总计最多 6,000 bytes，超出部分省略并通过当前工具重读；不将 JSON 回执拼成普通助手回复。纯解释与必要澄清可以直接回复；简单请求按需调用业务工具。复杂执行按 §9 的持久步骤进行，不以强制第一步工具调用代替任务正确性。
- 确认卡固定参数并保留 20 分钟；60 秒执行租约和随机 lease token 防止旧执行覆盖新状态。过期只禁止新副作用，仍可只读核对已提交的领域回执。进程中断后先恢复业务回执；已固定的未完成步骤按 §9 续做，未知模型响应不能作为执行事实。
- 创建草稿和确认采用/发布直接复用现有授权业务函数及事务守卫。服务端持有当前身份，模型不能提供路径、cookie 或请求头；聊天与页面的写入规则相同。
- 读取未发布内容或执行写操作的回合标记 `requires_write`，后续历史继承该约束；账号降为查看后不能读取或继续使用这些正文。永久删除按实际依赖清理相关会话，删除无关草稿不影响其他会话。恢复领域回执时同时补齐依赖。
- 每轮重建会话已实际引用的对象与成功确认回执；仅提供有限历史及每类最多 20 个已关联的文件/版本/草稿摘要。短引用由服务端稳定映射回实际 ID，未知引用返回可恢复错误，最终访问仍复检领域权限。焦点草稿优先当前授权页面，其次最近确认结果；不自动把无关项目对象加入依赖。
- 本轮授权对象快照置于真实历史之后、当前用户请求之前，标明仅为业务事实、不构成操作授权。SDK 7 不允许在 messages 中添加 system 消息，因此使用有明确边界的数据消息，并在 instructions 中规定其解释规则。记录读取结果包含实际 source、currentObject 和一致性标记；用户明确指定其他对象时保留该来源，不能因标记不同而重定向。同名空草稿的结果不能证明当前草稿内容丢失。
- 回合提交可附 `{kind,id}` 页面上下文，仅接受原始文件、草稿、版本或测试集类型；服务端验证归属与当前权限，将上下文和消息共同绑定幂等摘要，并保存于既有依赖字段。不接受客户端操作者、项目覆盖或工具历史。
- 同一会话已由助手创建的同名活跃草稿默认复用；明确另建的要求使用独立提交。不存在的目标先查询或澄清，不用创建空草稿代替故障恢复。
- 前端即时保留提交消息，重试沿用原消息、页面上下文与操作键，旧响应只清空其对应输入。任务卡读取现有处理运行状态；入队不等于处理完成，采纳和发布显示实际回执。会话编号按创建顺序计算，不受最近更新排序影响。

## 4. 上传和处理任务

- 上传确认加 raw-only 明确模式；保留解析/大小/幂等检查，mapping readiness 独立存储。旧解析视图回填为已整理，所有草稿来源入口统一检查可用状态。
- 后整理复用映射组件。原件确认时保存有明确 ID 的解析视图，未整理映射版本为 0；首次整理以 CAS 更新为 1，随后固定，不提供重映射入口。旧视图保持已整理版本 1。原始字节和来源身份不变；持久预览引用确定的视图与映射摘要。
- 处理 run 保存 actor/project、类型、模板/参数、输入快照引用/哈希、模型版本、目标和基准修订、阶段、结果引用、统计和错误码。大正文放不可变产物，数据库只存需要查询的索引与引用。
- job 复用已有唯一键、租约、心跳、有限重试和取消。增加任务类型领取范围，普通 Worker 与模型 Worker 分工；模型并发从一个消费者开始。所有提交按有效 lease/attempt fencing，失效 Worker 不覆盖新结果。
- 以确定批次 ID 保存成功结果；重试仅处理缺失/失败批次。外部模型请求可能重复，业务结果与应用必须去重。
- 原始数据和固定版本输入不可变；草稿输入为提交时快照。接受覆盖草稿字段时校验字段 revision，不能用全量旧快照覆盖其他用户修改。
- 新增生成记录可保存为派生资产/来源记录并记录输入来源边和处理说明；修改现有记录另保留处理关联。两个发布路径和来源读取都必须保留真实处理归属，不将模型结果标记成手工新增。
- 产物 reference inventory 同时接入 Worker orphan scan 与永久删除对象清理。回收暂停相关读写并保留可恢复内容；撤权仅阻止被撤权主体访问，不破坏其他成员仍可使用的数据；永久删除才按依赖闭包清理独占正文。共享后代与已接受独立产物按真实依赖保护。
- 输入和批次产物使用 `processing/<run>/<part>/<write UUID>/<hash>` 私有路径，不与其他运行共享可删除正文。批次存储前在事务内复核有效租约和来源；持久清理队列加孤儿扫描负责失败写入残留。
- 当前 `processing-v5` 配方固定每批最多 20 条；超过 20 条的新扩写任务按 10 条输出分批，并向模型提供本批在整批中的 offset/count/total，避免每批重新从相同主题开始；其他处理保持 20 条上限。完整模型请求最多 40,000 bytes、8,192 输出 tokens、60 秒批次超时、最多 3 次任务尝试；分批预算包含系统说明、背景和补足提示。模型请求只投影当前 id、问题、期望输出、Metadata 和可选原始数据，sourceId 必须复制当前 id；历史 baseline、来源关系和字段修订只在服务端用于溯源与冲突核对，避免模型混用历史编号。已有 `processing-v1` 保留原记录字节分批，`processing-v2` 保留原完整请求分批与模型数据形状；`processing-v3` 保留映射投影及原采样参数。旧配方均不重新划分成功批次或改变 ordinal。已有 `processing-v4` 保留 20 条扩写分批及原请求形状。新 v5 与已有 v4 请求、助手工具调用明确 temperature=0.2；这不替代内容语义审核。实际发送仍检查完整请求预算，无法容纳则明确失败并保留已完成结果。运行保存配方版本与预算，未知配方不能按新代码静默执行。输出总量仍遵守 PRD 容量，单个派生文件还遵守原有 50MB 上传边界。
- 来源记录 ordinal 与现有 CSV/JSON/JSONL 解析器一致，从 1 开始；派生资料和前端来源位置沿用这个值，不再额外加 1。处理结果 ID 的 `batch:index` 仍从 0 开始，与来源序号分别处理。Metadata 逐记录存储有序键值对，不把不同记录的大小写键合并成全文件映射。来源与修改页展示处理类型、输入类型及处理任务入口。

### OPT-11 展示读取补充

输入预览在原接口上可选接收搜索、既有 Metadata 条件和已选视图；返回授权范围的完整匹配 ID、隐藏已选数量及来源摘要，正文仍分页。结果读取的可选 `view` 返回同一授权集合的分页记录、实际字段差异、完整统计与持久采用回执；默认读取协议保持兼容。助手候选的同类展示先执行既有任务有效范围、局部修订替代和固定候选约束，并在读取后复核任务修订，不能以最后一个运行代替整个任务成果。

`processing/presentation.ts` 集中生成窄展示 DTO；采用回执去重且只投影目标、文件名和数量，不返回冻结要求或背景正文。`processing/provenance.ts` 按当前页批量核对真实运行输入、候选父身份、批次回执及可访问的解析记录，最多追溯 32 层并共享请求内缓存。精修仅对实际选中输入追加处理步骤；扩写保持“模型生成／参考”含义。无法证明的历史关系明确缺失，来源不可访问时不返回名称或正文；摘要不写回资产身份。不新增表、迁移、公共路由或持久血缘系统。

手动处理和助手复用 `ProcessingReview` 及筛选组件，按需打开只读详情。助手预览在原会话核对任务全部有效批次，保留原有确认与权限边界。保存继续使用现有 CAS 和幂等协议；未知副作用锁定原请求及键进行对账，明确拒绝才允许重新确认。轮询沿用现有节奏，失败保留已确认结果；普通浏览不调用模型。

实施与两轴审阅、公开验证记录见 [OPT-11 验证记录](../../.scratch/assistant-optimization/opt11-verification.md)，Owner 验收单独记录。

### OPT-12 连续操作读取补充

- 未提交配置只保留在当前标签页的 QueryClient，键包含账号、项目及来源；正文仍使用授权分页。查看来源在新标签页打开；成功提交清除该配置，登出通过现有完整导航清除内存。重新进入配置页强制重核权限和来源修订摘要，修订变化保留要求但暂停提交，重新选择才恢复。
- 复用 `processing-inputs` 返回来源修订摘要和当前来源中已发现的 Metadata 字段名（最多 100 个候选，仍允许手动输入其他合法字段）。来源修订由解析视图、映射、草稿修订或不可变版本与记录身份构成；它是恢复提示，不替代原有提交、字段保护和 CAS 校验。
- 复用运行列表的最近 100 项读取；保存标识批量读取现有有效回执，不累加重放数量。执行完成仅由运行终态、预期产物和已知执行问题派生，旧原因不明的 partial 不推断为完成，原终态及采用资格不改写。
- 现有结果读取增加有界 `search`，在服务端完整授权范围内匹配正文、Metadata 及可见来源名，再统一统计、分页和返回匹配身份。来源展示复用原批量授权投影，不逐行调用 API，也不向浏览器发送全量正文。助手入口继续使用同任务有效候选的原范围校验。
- 配置和结果展示继续使用 donor 控件。结果查询按条件隔离；短暂读取失败仅保留此前已确认的内容并禁用选择/保存，权限或来源失效不以缓存恢复正文。连续核对通过同一分页读取跨页移动；保存、幂等及未知结果对账协议不变。无新增数据表、迁移、依赖或公共路由。

### OPT-13 结果继续处理与来源展示

- 复用 `processing/refine.ts` 的冻结输入、运行入队、背景与来源校验，明确三种业务模式：助手 `refine` 保留未选候选；手动 `continue` 只以所选实际结果建新运行；`rerun` 复制该运行自己的完整输入快照。新快照在现有对象中保存 continuation、父运行及累计允许字段，不新增表或迁移。完整快照字节哈希验证失败或缺失时拒绝提交，不能以最新内容替代。
- 路由清单：`POST processing-inputs` **reused**，增加只接受父运行及所选身份的结果/重新运行预览；`GET processing-runs`、结果/状态/核对及 `POST accept/retry/cancel` **reused**，保持原权限、CSRF、分页和恢复约束。新增薄路由 `POST processing-runs/:runId/followups` 只接受 continue/rerun 及既有处理配置。无当前前端调用的 `POST :runId/refinements` **retired**；助手直接调用原领域函数，其保留全量候选语义及固定确认保持不变，回归改用真实助手 HTTP/SDK 工具入口。
- 后续输入只使用服务端已保存的结果和来源身份，浏览器只发送选中 ID。清洗/改写保留候选采用身份及最初草稿基线；扩写产生新的候选身份，后续清洗/改写最终仍追加。重新运行是新意图，采用身份重新建立，但保留该运行输入的可证来源链。模型连接及配方在新提交时读取当前获准配置；确定性清洗仍不调用模型。
- 手动继续与保存共享项目事务锁，提交和保存均核对跨账号实际采用账本；并发保存不能使已采用候选获得新身份。所有运行核对跨轮重复采用；普通/助手运行仍保留原有同轮显式另存及字段冲突语义，手动后续运行还拒绝同轮重复采用。原有幂等键和 effect 回执继续在同一事务生效；先恢复已提交请求，再拒绝新的重复采用。此锁适用于目前最多 10 用户，只有实测争用后才细分。
- 草稿来源结果的默认主操作直接绑定实际来源草稿，累计授权字段和最初字段 revision 用于 CAS；最终扩写结果追加，普通转换更新所选原记录。另存保持显式次要操作；成功只依据真实回执，不自动发布。未确认提交和保存请求在当前标签页保留完整请求与键，锁定改参后核对；明确拒绝才允许重新提交。
- 来源投影继续按授权当前页批量查询。摘要保留原始/参考文件和必要处理标记；详情按参考资料、实际运行顺序与时间、保存目标组织，中间文件折叠。仅相同运行链接和步骤去重，两个扩写运行均保留。授权草稿目标从真实 acceptance 查询，不依据文件名猜测；没有记录或当前不能访问时不补造历史。
- 系统产物名称统一使用 UTF-8 中文。`scripts/repair-processing-names.ts` 默认只预览；apply 必须先以独占方式创建备份映射，再按资产/项目/关联扩写运行/旧名称精确更新，回执中的同一文件名同步修正。rollback 使用同一映射和条件反向更新；重复 apply 不再修改。仅命中已确认的 `鎵╁厖结果-运行尾号.jsonl`，不转码用户文件、不修改对象字节或来源身份。
- 控件沿用 frontend-v1 的 Button、Dialog、DropdownMenu、表格及 token。实施、边界复验与 checkpoint 固定版本见 [OPT-13 验证](../../.scratch/assistant-optimization/opt13-verification.md)。

### OPT-14 列表读取与加载体验

- `GET processing-runs` 复用原路由，新增有界 limit/offset/search/status；最近 100 项、顺序、私人背景及来源生命周期校验不变，授权范围筛选后统计并分页，单页最多 20 项。SQL 只读取列表所需投影，来源摘要按请求复用，发起人批量关联，采用回执只读取当前页；完整任务要求、输入身份、模型配置及产物正文仍由详情路径按需读取。助手领域读取不调用此分页接口。
- `hasActive` 覆盖当前授权最近历史，而非仅当前页；活跃历史每 5 秒更新，终态历史停止定时更新，隐藏窗口暂停。成功创建/取消/重试/保存使历史失效；返回、恢复前台、重新联网及显式刷新会核对。受影响只读列表缓存 15 秒，键含账号、项目及条件，过渡旧行不可按新范围操作；读取使用 AbortSignal，防抖 275 ms 并避开中文组合输入。
- 公共品牌外壳先出现，正文等待会话及权限。受影响列表保留标题、表头、列宽与分页区域；首次失败不能冒充已确认空结果。同范围后台更新保留最近真实结果及输入/选择，固定状态区避免反复插入提示；401/403/404 隔离旧内容，短暂网络/5xx 保留已确认内容及恢复入口。登录先取消/清理私有查询；侧栏项目、个人资料与在线状态按账号隔离。
- 约 200 ms 后才显示加载提示；骨架采用 donor token，首次内容和页面切换仅 180 ms 淡入，后台更新不重播。减少动态效果时关闭动画。保存/采用/发布仍使用原权限、范围、CAS 与幂等复核，不因展示缓存放宽写入。
- 无新表、迁移、路由、依赖或动画框架。变更限于 Web/列表读取，Worker 配方与模型调用不变；实际验证及独立服务代码版本见 [OPT-14 记录](../../.scratch/assistant-optimization/opt14-verification.md)。

## 9. 方案执行与预算续做

本节是 2026-10-08 的整改设计；§9.1 已由 OPT-06 实施（`08356cb`），§9.2–9.5 的执行与恢复由 OPT-07 实施，证据见 [OPT-06](../../.scratch/assistant-optimization/opt06-verification.md) 和 [OPT-07](../../.scratch/assistant-optimization/opt07-verification.md)。完整场景矩阵、原失败任务及最终 checkpoint 仍由 OPT-08 验证。产品行为以 [PRD §7](../PRD-data-selection-and-assistant.md#7-ai-04-项目助手) 为准。复用当前会话 task、回合、proposal、job、processing run 与领域回执；不建设通用 DAG 引擎。这里的字段是内部设计，不作为新增公开 API。

### 9.1 单一生效要求

在现有任务要求写入处集中规范化并验证，返回生效任务或带具体字段的修正信息。来源、固定范围、目标数量及 new/final 含义、可编辑字段、字段规则、背景依据和语义说明分别保存。数字和规则的界面摘要由该状态生成；模型不得再同步维护多份数量权威。先收拢已有调用；只有直接复用需要时才提取共享函数，不要求额外服务层。

规则范围限于现有三字段及允许值、覆盖、配额等已有能力。明确期望输出与 Metadata 键的归属，每项含义仅有一个有效写入口；旧 `allowedLabels` 按期望输出规则兼容读取。可以复用现有存储形状，不为统一表示迁移所有旧数据。需要转换时只在同一读取/校验处处理，不能让模型同时填写两套同义参数。同一字段的冲突返回具体差异；不能按类别名称猜测字段或静默丢弃约束。不提供规则表达式、任意谓词或插件式校验器。

未提供字段的更新保留原规则，明确撤销则清除；这两种语义只由规范化模块解释。用户更正的结构化结果与原话一并保留：原话为意图依据，当前结构为执行依据，有不一致时先修正或澄清。受保护字段规则可用固定输入做预检，但小样本预检不能证明全量语义或覆盖达标。

### 9.2 可执行步骤

沿用现有有序步骤和有限业务动作。复杂任务中，一个步骤在执行前应能取得下列必要信息；已有 task/run/proposal 中的事实直接引用，不在每个步骤完整复制。简单请求仍可直接调用相同业务能力，不强制建立多步骤计划。

| 内容                             | 用途                                                                 |
| -------------------------------- | -------------------------------------------------------------------- |
| 稳定步骤身份、业务动作、当前修订 | 区分重试与新的业务意图；显示标题不承担身份或幂等作用                 |
| 输入引用与范围                   | 绑定来源/解析视图/草稿修订或前序成果；保留选择摘要                   |
| 适用要求与必要参数               | 可编辑字段、处理说明、数量或选取规则；当前步骤所需参数齐全后才能执行 |
| 结果引用与操作回执               | 记录实际 run、预览、候选集合、草稿或 proposal，避免依靠聊天文字传递  |
| 完成条件与状态                   | 明确等待后台、核对结果、等待用户确认或已完成；状态由真实结果导出     |

后续步骤可在前序结果出现后补齐参数；当前步骤未具备可验证输入时不能执行。通过已有任务成果或明确前序步骤取得实际结果引用，不保存虚构 ID，也不增加任意引用表达式。模型可查询资料、比较处理结果、组合已有能力并修订后续方法；影响目标、权限或允许修改字段的变更仍走生效要求校验与必要澄清。

本轮采用有序推进，Worker 内继续使用已有批处理与并发。结果不足时可插入补足步骤，审核后可追加局部调整；不需要通用分支、循环节点或动态依赖图。完成检查使用对应业务动作的现有校验与回执，不能让模型编写可执行条件，也不建立通用完成条件解释器。

步骤完成必须同时匹配当前修订、动作、对象、输入范围和操作回执。读取步骤核对要求的读取/统计范围；入队步骤转为等待对应运行；处理步骤检查对应运行终态及要求的结果范围；结构核对步骤以具体检查项为准；采用/发布步骤等待当前固定确认回执。不能只按工具名称或模型的“完成”文本推进。

OPT-09 补齐执行边界：当前草稿、预览和运行依赖仅从本方案真实回执取得；预览与所属草稿成对绑定，采用确认产生的新草稿进入后续依赖。全范围背景读取累积同一文档、哈希和查询范围的实际分页，未读完整不能推进或冻结为完整依据；未来的读取步骤不阻挡此前已完成读取所授权的处理。

OPT-07 实施采用步骤内的固定参数及现有领域回执：校验在复用成功意图之前执行，参数改变不能命中旧成功或旧 started 操作；已提交但汇报失败的写操作先恢复回执。旧资产页 `asset` 在恢复边界按实际 ID 转成 `assets` 输入。来源核对只接受当前目标/已复核计划明确的范围，`allTask` 只选择保留成果，不能把被更正排除的来源重新加入权限集合。服务端确定性续做每轮有界，仍使用原回合/工具、任务修订与停止检查。

### 9.3 调度与错误恢复

- 模型回合负责理解和语义决策；现有调度器推进已具备参数的确定性步骤，复用业务函数。已固定查询的翻页、计数、状态检查及回执恢复可由服务端完成；决定查什么、怎样处理及是否调整方法仍由模型完成。不另造可执行任意工具的调度框架。
- 权威按事实划分：task 保存生效要求与有序步骤，processing run 保存执行和产物，proposal/领域回执保存确认及提交结果。界面汇总读取这些事实；`nextAction`、临时义务标记或步骤游标不得互相覆盖同一事实。只整理受影响读写点，允许保留无冲突的既有字段；缓存与摘要只能派生。替代旧路径时一并退出其写入和提示词补丁，不做全库状态重写。
- 保留现有回合步骤/时长、自动续做、并发和会话容量限制；确定性推进也采用有界领取和事务，不能通过新的循环绕过停止或预算。无进展时停止并给具体原因。
- 一步的稳定操作键绑定任务、步骤修订及固定参数。重试先读真实回执，未执行才提交；结果返回丢失时复用成功操作。SDK tool-call ID 和模型重试生成的参数不能改变已保存意图。
- 用户修改要求后增加现有任务修订，作废受影响步骤和待确认卡。核对明确来源、固定参数及结果身份决定复用，不按标题前缀决定。不能证明后续步骤仍适用时，从最早受影响步骤起撤销后续执行资格，保留实际成果供重新核对；无法定位时从整个未完成方案核对。失效不删除产物，也不自动重跑全部处理。复用先前成果须重新验证当前约束；旧 Worker 结果仍属于旧输入，新目标不能直接认领。停止、撤权、来源失效及旧执行令牌的检查继续在实际业务提交处进行。
- 分开记录可修正参数错误、规则矛盾、处理失败、模型响应失败和内容待审核。恢复反馈包含步骤、字段或范围、已保留结果以及下一动作，供模型和 UI 共用；不返回凭据或整份数据正文。
- 数据操作已完成而模型总结失败时，用实际回执呈现已完成部分；未满足的步骤仍保持未完成。只对传输/临时故障有限重试，确定性规则错误须先修正，不能无限重放。

OPT-09 将可信的提交前校验失败记为无副作用；旧记录缺少标记时只兼容相同可信错误码。此类失败可修正参数，未知结果仍保持原操作键，普通回合与恢复回合都不能借重规划解除绑定。已纠正校验失败不阻断预算续做；未知失败只有同键真实成功才解决。固定步骤沿用成对 SDK 工具消息，业务失败保留具体原因和对账提示。

### 9.4 处理与内容核对

沿用 Worker 分批、冻结输入和成功产物，语义分类可通过 `rewrite` 与受限 `metadataKeys` 实现；原题、原标签及其他字段仍受保护。固定分类结果交给服务端选取，补足和局部调整保留稳定候选身份，不重新展开已缩小的来源范围。

简单空白清理、计数和字段检查优先走已有确定性实现。语义改写/生成由模型完成；分类配额不构成伪造分类或擅自更改保护字段的理由。先用明确的小样本核对语义效果，再开展大批量实测。结构检查与用户内容审核在状态和展示上分开，不新建自动“语义通过”标志冒充事实。

OPT-09 核对当前固定记录范围及处理实际冻结的背景片段；兼容部分可复用，旧范围不能覆盖新的明确范围。筛选、指定记录和全量处理均保存真实范围与内容哈希；有真实步骤回执的当前多批方案保留各批范围。当前字段保护与最初基线比较，单批约束仍与该批输入比较；局部采用确认只检查选中行，不以整批失败拒绝有效选中内容。发布核对草稿实际记录和采用来源账本，保持新增/最终数量含义；预计候选不计入已交付，部分交付不标整个目标完成。

### 9.5 旧任务兼容与验证

OPT-10 的边界修复沿用现有任务 JSON 和运行快照：`read_records.selection` 可仅固定选取范围；同来源、同条件的后续处理复用记录 ID、实际 seed 和内容 hash，明确重新选取使用 `reselect`。有效候选按真实来源记录身份替代旧转换结果，独立扩充仍保留新增；核对、预览及采用确认复用同一有效范围，不删除历史运行。

附件分类在既有 `classifications` 中记录 `basis=background` 与各允许值的 `definitions` 原文；用户自定义标签记录 `basis=user`。旧分类缺少依据时须先重核对，不能直接绕过。定义检查核对编号或名称与其对应原文条目，不接受仅含编号或借用其他条目的定义，也不证明每条结果语义正确。补读后先复核方案；已有成果仅在冻结的语义要求、分类定义与片段哈希保持相容时复用，实际变更仍阻止旧成果采用。已完成的写入回执作为历史事实保留，与新要求下的采用资格分别核对。

附件类别与用户额外指定的兜底标签可处于同一字段：兜底 `definitions[].basis=user` 必须引用用户最近真实指定该标签的短句（比较时允许句末标点），并与当前生效要求一致；明确撤销、否定及已失效要求不能授予例外。附件实际编号或完整条目名称仍须通过原文校验，正文中普通词的出现不占用用户标签。该保守词汇检查不承诺通用语义理解，含糊要求须澄清。定义边界识别编号、Markdown 标题及明确同一行类别分隔；纠错提示最多引用当前已选原文 320 字符。助手单次输出上限为 4,096 tokens，以容纳多类别方案 JSON；工具、回合、续做及副作用预算保持原有上限。

OPT-22 已统一模型可见的 `plan_task` 薄参数入口，question 与执行动作的互斥继续由服务端校验；旧 anyOf 模型兼容分支已删除，生成提示不代替业务守卫。SDK 参数校验与业务失败共用连续错误停止边界：同一工具、错误码和简短诊断连续重复才停止，不同字段错误允许继续纠正，仍受既有总预算约束；具体诊断供模型纠正及界面展示。同轮停止后未执行的排队写入不产生副作用，未知写入仍先核对真实回执，不能因重规划解除幂等绑定。

保留旧会话、run、固定候选、采用记录和正式版本。旧计划缺少对象或范围时，仅依据明确回执和真实来源补齐当前需要恢复的步骤；无法可靠还原则说明缺失，不能默认已完成或重新生成全部数据。已有资料足够时由助手重建待执行部分，只有缺少业务选择才询问用户。不解析所有历史聊天来批量推断计划，也不建设自动迁移所有旧计划的系统。冲突规则先展示并修正，不直接写库清除限制。已有 processing 配方按原版本恢复，不改写其成功批次。

优先利用现有 task JSON 与持久回执，不预先增加数据表或公共 API。部署前须在隔离副本验证旧任务读取、未完成步骤恢复、已采用数据去重和旧字段约束；具体检查见 [测试计划 §5](../test-plan-data-selection-and-assistant.md#5-整改验收计划)。如确需迁移或新增接口，应在实施前列出必要差异及兼容方式。

## 10. OPT-16 去重与补齐实现

## 14. OPT-20–25 助手稳定性与独立页面

OPT-20 已在 `configuredModel` 的 fetch 边界记录安全 HTTP 状态和响应头等待时间，在 Agent 终结边界按真实模型来源、工具回执及领域错误归类；未知应用异常保持应用分类。诊断继续保存到现有任务 JSON/回合 observations，使用现有回合 ID，按可选字段兼容旧会话。只保存版本、计数、时间及白名单分类，不保存异常正文、密钥或提示词。保留数据操作数来自已完成且无需用户确认的真实回执；无法确认的候选数量为 null。

独立诊断函数复用现有处理错误分类；测试脚本复用公开 HTTP、隔离数据库/桶和既有 Worker 执行器。实际验证及版本集中于 [OPT-20 记录](../../.scratch/assistant-optimization/opt20-verification.md)。

OPT-21 在现有 model fetch 外复用一个回合级传输包装器，SDK 重试保持关闭。原截止时间、模型/工具计数及传输尝试持久到可选 task.turnBudget，恢复先读原预算再检查执行令牌；旧任务按可用计数兼容。取消使用现有 dispatcher 检查和 AbortSignal，写入继续复检事务 fence。未知操作只查原键回执；处理成功而说明失败保留审核入口，成功说明或合法 Worker 恢复清除旧恢复标志。后台批次的累计 model_attempts 和截止时间不重置，不重写 Worker。额度定义仍见 [总方案 §4](../assistant-workspace-reliability-plan.md#4-失败如何恢复)，证据见 [OPT-21 记录](../../.scratch/assistant-optimization/opt21-verification.md)。

OPT-22 复用 task JSON、实际步骤及领域事务：模型能力按持久阶段和当前权限投影，读取与合法修复通道保留；完整业务校验仍在绑定参数后执行。省略来源、固定范围、运行、草稿或确认目标时绑定可证事实，显式撤销不恢复旧值；候选选择绑定所选真实批次，子集处理不能扩大声明来源。Metadata 局部键限制继续由原冻结输入和事务校验继承。

独立要求只做首尾空格清理、完全相同项去重和稳定比较；资产集合归一，有序步骤不排序，自由文本实质改变仍触发核对。旧任务仅在其旧键确实对应当前事实时兼容新键，不批量迁移或推断历史。规则实质改变与撤销待执行确认在同一 session fence 内提交；已领取但未提交的旧确认失效，已提交但丢响应的操作只核对原幂等键恢复真实回执，不重新执行。冻结背景要求使用同一比较口径。模型提示和工具合同标记 v2；无新表、API、依赖或 Worker 配方。实现、审阅及限制见 [OPT-22 记录](../../.scratch/assistant-optimization/opt22-verification.md)。

OPT-23 复用当前 task、合法业务对象和真实回执生成模型事实；有效要求完整保留，历史原话单独限长，近期成对历史只作参考。超过模型回执容量的记录读取返回有界导航摘要，保留读取范围和步骤完成证据；步骤使用原始可信结果推进，历史恢复也能按摘要回读正文，不能把部分读取当全量。当前来源不依赖最近 50 条历史引用是否仍存在。

勾选范围写入已有 task.selectedCandidates，后续回合省略选择时沿用可证范围；refine 按当前有效结果及稳定来源身份核对，已被子轮或独立重做取代的勾选拒绝，未被取代的旧批次仍可使用。背景定义首次沿用原语义校验，验证后在已有 task JSON 保存仅含字段、类别和绑定引用的注册项；引用绑定当前账号、会话、附件哈希、提取版本和实际页/行原文。服务端解析回完整旧 definitions，继续原校验和处理冻结，不将引用当作新的分类依据。伪造、跨会话、类别不符、删除或内容/位置变化均失效；旧完整定义继续兼容。显式撤销全部分类可清理旧背景依据，省略分类参数不清理。提示和工具合同标记 v3，无新表、API、依赖或模型摘要链；证据与限制见 [OPT-23 记录](../../.scratch/assistant-optimization/opt23-verification.md)。

OPT-24 在 frontend-v3 增加项目内个人会话路由，完整抽屉退出正式入口。页面按账号/项目/会话保存标签内未发送输入及原提交键，状态/消息/背景/候选查询按相同范围隔离并消费 AbortSignal。既有 sessions GET 支持名称过滤、分页及只读对象上下文核对；单会话 GET 的可选 status/messages 投影保留完整访问复检和无参数旧响应，状态不返回历史，消息按稳定游标分页。POST turns 的可选 expectedTaskRevision 沿原幂等回放、会话锁和权限校验执行，不新增工具直达入口。202 后取消提交前状态请求并重读，已受理提交收口不驱动终态轮询。安全 Markdown 仅用 React 文本节点，不生成操作卡或外部资源；复用既有任务/审核/背景组件，没有新依赖、表或 Worker 变更。详细证据见 [OPT-24 记录](../../.scratch/assistant-optimization/opt24-verification.md)。

OPT-25 默认 candidates 的 `scope=task` 复用 processing task 的当前有效引用，历史 `scope=run` 仅用于追溯。可信 task 关联、来源快照、当前成果/排除修订派生 `reviewRevision`，数量、筛选、分页、核对及采用使用同一集合。稳定来源身份与实际运行/结果引用分开；固定勾选服务端冻结跨批分组，继续处理只物化当前有效成果，缺失占位不计产出，后台未完成不进入完整采用。采用沿原草稿基线/字段修订与既有确认幂等，部分回执不能算整体完成；最终发布另确认。页面复用 ProcessingReview 和既有控件，无新结果表或 Worker 变更。已有批准方案启用时保留同来源/要求下的唯一步骤参数；筛选默认值计划/执行共同归一，错误计划参数不改变持久任务。边界、模型样本及集中验收见 [OPT-25 记录](../../.scratch/assistant-optimization/opt25-verification.md)。

- 不增加数据表或服务；必要的任务/规则/诊断字段按可选读取兼容旧任务。整体主业务顺序仍是资料→处理→审核→确认采用/发布，因此不改写历史 v2 主流程图或 ADR 的技术选型。实施状态与证据见 [OPT-20–25 台账](../../.scratch/assistant-optimization/spec.md)。

### OPT-29 文档生成合同（实现约定）

- 私人助手工具 `generate_candidates` 接收 `name`、`instructions`、`outputCount`（1–10000），可选 `purpose`、`metadataKeys`、`classifications`、`requirements`；分类及要求复用 `plan_task` 的校验合同。输出字段固定为问题、期望输出、Metadata，未要求的 Metadata 返回空数组。工具不接收资产 ID、记录 ID 或伪造种子。
- 规划步骤的输入使用同一合同。每个生成步骤保存独立名称、数量、当前类别规则及真实草稿/运行回执；前一交付审核和固定确认后，才继续下一交付。新交付的分类按字段更新、要求清单完整替换，省略保持通用要求；不能沿用上一类别的专属限制。当前目标取当前步骤数量，整体目标独立显示。生成步骤自行建立幂等草稿，方案禁止再单列建立草稿。
- 规划检查模型配置与当前会话可读背景；执行前冻结已读取的真实页段、文档哈希/提取版本及当前要求，再创建或复用同一幂等草稿。缺少背景、实际阅读依据、模型或明确数量时，不创建草稿/处理任务。
- 新运行使用 `source:{kind:"background",id:当前私人会话ID,recordIds:[]}` 与 `operation:"generate"`，仅接受受服务端助手 fence 保护的内部创建调用。旧记录处理来源仍必须有非空记录，不能使用新来源进行清洗/改写/旧扩充。公开处理接口不增加任意空输入生成入口；已存在生成任务的显式“补齐未完成部分”复用服务端冻结配置及真实缺额，调用者不能另传生成要求或数量。
- `processing-v8` 仅用于从零生成；旧 v1–v7 的冻结恢复保持原义。v8 沿用 v7 的队列、租约、批次、最多三次模型调用与 60 秒批次总时限、40 KB 请求、8192 输出 token、取消和成功结果保留；新生成温度为 0.7，旧配方温度不变。模型只输出三字段，服务端分配稳定身份；继续修改时以真实候选为基线，不编造原始输入或继承不存在的保护字段。分批上下文明确当前缺额、全局位置及已有候选排除样例，不增加独立多样性规划或新的补齐循环。
- 候选来源标明“依据背景文档生成”，只列冻结实际页段；这是运行级依据，不承诺逐题引文。私人原文只对原会话用户可见，采用后的共享记录只保留受权限保护的来源指针。复用现有审核、局部处理、采用和发布确认；不新增表、框架、页面或 RAG。

### OPT-30 生成分配与共享额度（本次实现约定）

- `generate_candidates` 与对应计划输入可带 `scenarios`：1–20个、每个最多200字的不同情境摘要，由已有规划模型按当前要求拟定。旧方案省略时保留兼容的通用情境，不增加策划请求或用户必填项。生成选项和现有 MinIO 输入快照冻结场景、原目标、根运行与服务端位置；仅新生成使用 `processing-v9`，v1–v8按原配方恢复。
- 每次请求只接收本批尚缺位置与对应场景、已用场景计数及有界排除样例；模型仍只返回三字段，服务端按数组位置赋予稳定身份。空值/无效行及完全重复不占成功位置；不同答案的同题保留为待核对碰撞，不引入近似语义去重。场景分配是生成要求，不是语义合格证明。
- 沿同一 processing task 的 v9 生成及补齐累计调用，根目标原批次数×原三次调用为共享上限，首次调用起原批次数×原60秒为总时限；每批自身上限不变。调用前锁定现有任务并持久预留，未知写入、重领、自动回合和显式补齐均不重置；完成/采用/发布不获得新额度。旧记录转换的预算语义保持。
- 补齐以原目标和当前有效成果的位置计算，只请求真实缺额；局部处理沿原始候选位置保留身份，未修改数据不重生成。耗尽后保留候选、原因和缺额，原页面停用无额度的补齐入口；仍用既有组件、确认及权限，无新增表、公开路由或依赖。
- v9在逐行严格校验前，可无损接收三字段记录根数组并归入records，不猜字段或补正文；v1–v8保持原外壳合同。生成位置随任务引用保留，采用后转换也能继续定位；补齐替换旧候选后回存草稿时，对原行执行既有受修订保护的替换范围，维持当前成果数量。分类配额按当前实际保留类别计算，恢复的同批结果只计一次。

### OPT-31 内容核对与局部修复（实现约定）

新生成配方 v10、其他处理配方 v11 在现有 Worker 中执行批量内容核对；旧 v1–v9 冻结行为保持。核对使用冻结要求、已验证定义及真实背景片段，按服务端批次/结果位置绑定身份和内容/要求哈希。内容响应须逐项提供问法、类别、期望行为、原事实四项严格枚举，服务端合并，缺项/错误类型保持待核对，不能用顶层口头通过覆盖任一失败项。结论分为符合、不符合、存疑、待核对；旧运行没有证据时为待核对。当前要求或实际内容变化使旧结论失效，原确认修订保护继续生效。

初检响应可以为明确不符项提出一次替换，服务端再做身份、字段保护、分类值及重复校验；只有被授权的未采用候选可接受替换，存疑与符合项保持原值。随后只对接受替换的项独立复检一次。生成、初检/修复和复检共用原至多三次请求及 60 秒批次总期限，SDK 不自动重试；v10 仍共享根目标预算。额度不足保留候选和待核对原因，不新增循环、审核 Agent、表或依赖。

批次结果 JSON 的可选 `contentReview` 保存已尝试阶段和逐项证据。调用前沿原租约、权限、来源及事务 fence 保存候选/阶段；未知响应不会重做同一阶段。读取、助手汇总和现有结果表复用当前有效集合，区分本轮允许字段差异、同题碰撞、结构有效数、内容核对和真实保存回执；不以标签种数或标点变化证明语义质量。内容问题不增加新的保存/发布质量门槛，固定确认与部分采用合同不变。详细证据见 [OPT-31 记录](../../.scratch/assistant-optimization/opt31-verification.md)。

已授权执行方案的采用准备步骤复用原固定步骤执行器，只为 `request_processing_apply` 准备现有确认卡；原工具仍执行权限、修订、固定范围及幂等检查，准备后立即停止等待人工确认。只规划、暂停及待复核方案不准备卡片，其他 request 工具保持原路径。背景生成的服务端绑定输出草稿不作为虚构输入来源；该例外须所有背景运行的目标草稿与当前已创建草稿完全一致，显式步骤来源、范围和背景要求仍独立校验。

用户精确发送既有“按当前已保存方案执行”或“继续执行已保存方案”控制语句时，且已有非空步骤、没有待答业务问题，直接调用原 `plan_task` 执行切换及固定步骤执行器，不再让模型重写同一方案。该路径不推断新参数、来源或步骤，不越过校验与确认；其他自然语言及有待答问题时保留原模型路径。
