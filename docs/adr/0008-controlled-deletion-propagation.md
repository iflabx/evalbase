# 永久删除的 fail-closed 传播

- Status: Accepted
- Date: 2026-08-18
- Amended: 2026-09-27
- Decision role: Project Owner / Sole Developer

冻结原型中的“永久删除”确认是不可逆内容移除的唯一用户提交边界。确认后的第一笔数据库事务立即阻断受影响内容的读取、下载和新引用；服务端在后台冻结依赖闭包并以 fail-closed 顺序幂等清理 MinIO/数据库载荷，最后提交必要墓碑。该顺序允许内部失败重试，但确认后不可取消，也不会因局部故障重新暴露内容。

共享 blob 只有在不存在未受影响引用时才物理删除。采用增量版本存储后，跨出删除范围的第一层存活后代必须先按 [ADR-0011](./0011-incremental-test-set-version-storage.md#永久删除时切断存储依赖)建立并校验依赖切断 Checkpoint；全部存活分支独立后才允许清理被删祖先的专属内容。Phase 1A 没有系统备份；本决定是永久删除背后的安全机制，不是法律、隐私或合规认证。依赖闭包、preview hash、清理作业和审计仍可作为内部证据，但不得形成独立治理页面、理由字段、第二确认人、外部副本清单或恢复任务页面。

移入回收站只改变日常可见性，内容、父子关系、版本标签和溯源全部保留并可恢复。整套测试集回收会吸收其已经回收的版本分支；恢复整套测试集时，这些可恢复版本与分支条目在同一事务内一并恢复或关闭。永久删除测试集时输入完整名称，永久删除版本/版本分支和中间版本墓碑时输入根版本号；服务端锁定当前对象后精确比较。永久动作不可恢复。中间版本永久删除时保留原标签和父子边作为墓碑，后代不得改挂到祖先版本，版本标签不得复用。

实施细节见 [Phase 1A 架构](../architecture/phase1a-architecture.md#8-删除传播)。
