## 2. 结论

可以进入“修订合同与拆分 Ticket”阶段。新增工作主要是三条链路：真实账号与项目权限、持久共享草稿、实时协作与修改归属。整页编辑是这些能力的用户入口。

现有正式实现仍符合“单人、无登录、不可变版本”的既有合同。新原型的设计冻结没有自动替换 PRD；应先把新行为和兼容决策同步到权威文档。无需把原型分支合并 main；正式实现继续在 frontend-v3 中复用 frontend-v1 的样式和组件。

可复用的基础包括服务端密码哈希和会话、project_member 权限查询、稳定 case/revision、分页版本读取、稀疏发布、Checkpoint、版本图、来源和删除模块。历史草稿接口已经退出正式公共路径，且采用单人租约，不能因仓库中存在相关代码就认定多人草稿已实现。

## 4. 原型显示的权限矩阵

以下提取自 roleFor、canWrite、canManage、actionAllowed；它是下一步合同修订输入，不代表服务端已经实现或验证了全部边界。

## 5. 实施前必须明确的差异和兼容事项

### 5.1 一次性初始化、账号与旧数据归属

现有 bootstrapOwner 每次启动都会按部署配置更新固定 Owner 的密码哈希（E2）。新注册入口需要数据库权威的一次性初始化状态，并保证两个首次访问请求不会分别创建管理员。上线前应明确将现有 user_owner、项目归属与历史操作接到哪个真实账号，避免任何注册用户自动继承旧项目。

建议保留既有业务对象与历史 actor ID，通过受控的账号接管迁移建立邮箱凭据；迁移策略在技术方案中固定。新空库和已有单人数据的升级都要验证。复用 scrypt 与数据库会话，不复制原型的浏览器账号存储或 SHA-256 Mock 密码处理。

用户已明确选择邮箱密码注册、不做邮箱验证；本审计沿用该决定。邮箱按登录标识处理，邀请只能由登录后匹配目标的账号接受，不能信任客户端提交的 userId。SSO、邮箱验证和密码找回页面不是本次冻结自动增加的需求；账号恢复若需要进入本轮，应另写明确行为。

### 5.2 管理员与项目负责人、邀请边界

原型的管理员只是固定 owner 用户，并没有独立系统管理员字段；新建项目根据当前项目的 canManage 判断（E1）。正式 POST /api/projects 目前只做身份与 Origin/CSRF 检查，没有同等的“当前项目负责人”限制（E4）。需要明确谁能新建项目，以及系统管理员是否自动拥有全部项目数据权限。

建议区分系统初始化/项目创建资格与逐项目 owner/editor/viewer；数据访问仍按项目成员关系判断，不因账号标签静默越过项目隔离。具体项目创建资格需要 Owner 决定。

当前 sessionActor 的 projectRole 来自固定 project_demo，且全局 editor/viewer 被 isTestIdentityRole 当作测试身份，关闭测试身份开关后会拒绝这些会话（E2、E4）。真实账号属性与逐项目角色必须分离，不能通过打开 allowTestIdentity 开关交付多人功能。

原型允许对未注册邮箱先发邀请，并保留“体验受邀加入”演示入口；这比“已注册用户在信息中接受”多一条注册分支。应明确是否保留先邀请后注册；演示切换账号按钮与强制过期按钮不进入正式产品。inviteMember 对 status=pending 的邀请直接判重，未排除已经过期的邀请，正式合同必须定义过期后的重新邀请及重复接受结果（E1）。

### 5.3 草稿身份和数量：按父版本独立，传输也必须独立

原型 localStorage 键包含 project、mode、test set、parent version（E9），但 activeEditingSet 和协作消息只使用测试集 ID（E10）。因此同一测试集基于 v1 与 v2 的两个草稿，会落入相同消息匹配范围；request-draft、字段修改、删除草稿和发布通知均可能影响错误的草稿。这是静态控制流发现，尚未执行双标签复现。

新建测试集的存储键固定为该项目的 new，演示实际只有一个新建草稿槽。旧数据库却约束每个 test_set 只允许一个 editing/materializing 草稿，且写入要求唯一 lease holder（E14）。三者不能直接拼接。

建议所有草稿具备稳定 draft ID，并固定 project/test set/parent version；同一测试集同一父版本最多一个活跃共享草稿，不同父版本独立；新建测试集草稿也独立分配身份。需要决定同一项目可同时保留多少个新建草稿，并据此补充发现入口。协作房间、在线位置、保存、删除、发布与幂等都必须使用同一个草稿身份。

### 5.4 多人同步、冲突、保存和退出

原型只在远程 edit 命中当前聚焦字段时记录一个 editConflict；remove 直接删除行，snapshot 可整体替换记录；next 没有基于 editConflict 的发布阻断（E10、E15）。这些 Mock 行为不能作为正式的并发一致性方案。

正式方案需要覆盖不同记录/字段并行修改、同字段冲突保留双方输入、删行与编辑竞争、断线重连、撤权后旧连接和在途操作。Metadata 当前作为整个 metadataEntries 字段同步；是否允许不同 Metadata 项独立合并需要写清，不能承诺逐字光标/CRDT 而没有设计。

saveEditorDraft 失败会显示提示，但 closeModal 仍会退出（E9、E15）；“已保存”必须对应服务端确认，保存失败应保留当前输入并允许重试。在线/正在输入是短期状态，最近修改者是持久事实，二者分别建模。用户要求的实时共同编辑应完整保留，原型阶段未建立共享服务只是演示方式选择。

### 5.5 同一草稿只能发布一次

现有稀疏发布锁定测试集并安全分配标签，幂等键按 project + actor + operation + key 判定（E13）。这可以防止一个请求重试，却不能单独保证两个用户发布同一共享草稿只得到一个正式版本。

建议发布绑定 draft ID 与已确认修订，在事务中固定待发布内容，并原子记录唯一发布结果。第二位发布者或响应丢失重试返回同一版本；发布后的迟到编辑不得进入已经发布的快照。复用既有 sparse publisher、容量检查和 Checkpoint，草稿保存不分配正式版本号。草稿与其父版本的删除/回收竞争也需在相同的服务端状态边界处理。

### 5.6 来源归属、成员移除与删除兼容

原型 fieldEdits / lastEditedBy 来自客户端，Metadata 归属到整个字段；来源页对缺失历史信息明确显示“修改者未记录”等（E12）。现有版本 published_by 只证明谁发布，历史 draft_revision/audit 的 actor 也不能自动还原每个字段作者。

建议由服务端在确认的修改操作上记录 actor、时间和字段，发布时固定归属事实；未记录的旧字段保留“未记录”，不统一补写为迁移管理员。明确新增、移除记录及未变化字段显示谁，并保留成员移除后的历史归属。修改显示名称是否改变历史展示应写入合同，身份仍以稳定 ID 为准。

本次用户要求来源页面显示编辑者，并未明确要求新增 CSV 列。建议先保留既有下载格式；若要导出作者，再单独定义格式兼容与缓存证据。新增草稿及归属数据也应纳入永久删除范围审计，避免已删正文通过草稿、操作记录、缓存或事件重放再次可读，同时保持存活后代和必要来源不受损。

### 5.7 Metadata 空值与文案兼容

原型 inlineMetadataProblem 要求有字段名时 value.trim() 非空，而正式 MetadataEditor 与 normalizeMetadataEntries 允许空字符串值（E11）。已有合法记录可能因此在新草稿中无法发布，即使用户没有修改该 Metadata。

建议保持字段名非空、忽略大小写唯一，并继续允许空值；空占位行如何清理应明确。若确实要禁止空值，必须明确兼容处理，不能静默修改旧数据或让继承旧版本的草稿全部报错。该选择需要在合同修订时确认，本轮未改动冻结文件。

原型仍使用“预测输出”，正式合同明确使用“期望输出”。继续执行这项已批准的文案映射，不回退正式领域名称。

## 9. 后续必要验收场景

1. 空库同时打开两次管理员注册，只能完成一次初始化；已有单人库升级后旧数据归属正确，普通新注册账号不可见旧项目。
2. 邮箱密码注册错误不清空输入；按既定要求不做邮箱验证。登录/登出/过期后，旧页面和项目缓存不泄漏上一账号数据。
3. 邀请接受、重复接受、到期/撤销、重复邀请、未授权邮箱，以及无项目账号的信息入口；直接请求不能越权管理成员。
4. 负责人/编辑者/查看者逐项验证读取、写入、导出和删除；移除/降级后旧页面、下载及实时连接同步失权。
5. 已有草稿入口和最后修改提示；不同父版本草稿隔离；新建草稿按已决定的数量规则独立；刷新及服务重启后恢复，失败保留输入。
6. 两账号改不同字段、改同字段、删行与编辑竞争、Metadata 竞争、断线重连和重复消息；双人发布同一修订只生成一个版本。
7. 跨页选择与取消、筛选变化、资料新增时的全选边界；覆盖 5 资产、10,000 条及既有 byte 上限，超限保留可调整状态。
8. 旧 Metadata 空值、旧版本来源和下载保持兼容；新修改归属可信，未知历史不伪造；发布者与字段编辑者可以不同。
9. 删除草稿不删除已发布版本；父版本或测试集回收/永久删除与草稿协作竞争时，不产生幽灵写入或已删正文重新可读。
10. 对受影响页面核对 frontend-v1 字体、颜色、按钮、表格和布局，以及冻结原型的控件顺序、空态、错误与禁用态。

原型在同一浏览器的两个标签页中把 userId 分别留在内存，可测试两个 Mock 身份；正式 Cookie 会话通常在同一浏览器配置的同源标签页共享。正式双账号验收应使用两个隔离浏览器上下文/配置或普通窗口加隐私窗口，除非产品另行明确标签页独立账号。无需为复刻 Mock 测试方式新增认证架构。
