# 登录与多人协作：Owner 决策记录

日期：2026-09-28。状态：下列四项已由 Project Owner 明确确认，作为下一轮合同修订和 Ticket 的输入。

基于[冻结原型](../prototypes/phase1a-login-multiuser-vnext-freeze.md)与[差异审计](login-multiuser-vnext-delta-audit.md)。本记录优先于原型中与这四项相冲突的演示行为；原型标签继续保存原始设计证据。现行单人 PRD 的整体升级仍需后续同步，不能据此将多人功能视为已经实现。

## D1. 管理员与项目角色

只有账号层面的“管理员”，不设置“项目管理员”或具有等价管理权的项目“负责人”角色。只有管理员能创建项目；普通账号不能通过加入某项目或切换当前项目取得创建项目权限。

原型原有编辑者、查看者仍作为普通账号在项目内的访问角色；它们不升级为管理员。正式合同应清理原型和既有代码中把项目 owner 等同于管理员的规则，并明确处理旧 owner 数据的迁移。

管理员默认可以查看和管理所有项目，包括项目内容、成员邀请、权限调整、回收和永久删除；无需先成为某项目的成员。普通账号仍按各项目的编辑者/查看者成员关系授权。服务端必须明确区分管理员的全局权限与普通账号的项目权限，不能通过客户端隐藏按钮或打开测试身份开关实现。

## D2. 区分版本草稿

派生草稿必须绑定稳定的项目、测试集和父版本身份。同一测试集基于不同父版本的草稿彼此独立；同一父版本的共同编辑者进入同一活跃共享草稿。

每个草稿使用稳定 draft ID。草稿保存、恢复、在线位置、编辑事件、冲突、删除和发布都按该身份隔离，不能只用测试集 ID 或可见版本标签作为协作标识。不同项目/测试集即使版本标签同为 v1，也不能共享草稿或消息。

新建测试集尚无父版本时也分配独立草稿身份；原型中固定的 project:new 存储槽不能代替正式身份设计。新建草稿数量和列表入口在后续规格中明确。

验收必须覆盖同一测试集分别从 v1、v2 编辑：一方修改、删除草稿或发布，均不能覆盖另一草稿的记录和编辑状态。

## D3. 同一草稿只生成一个正式版本

两人同时发布同一草稿、重复点击、响应丢失重试，都只能对应一个正式版本。保证范围是整个草稿，不限于同一操作者或同一个 HTTP 幂等键。

发布固定一个已经确认保存的草稿修订，并原子记录其正式版本结果。后续合法重复请求返回既有版本；修订不匹配的尚未发布请求应保留输入并返回明确冲突，不能自行另发一个版本。已经发布的草稿不再继续写入，迟到编辑不能进入已发布快照。

不同父版本的独立草稿仍可各自发布；正式版本标签由服务端按现有事务规则分配，保存草稿不消耗标签。后台重试和服务重启同样遵守“一草稿一发布结果”。

验收使用两个真实独立账号、不同请求幂等键同时发布相同草稿，并验证只生成一个版本、双方取得同一个 version ID；继续验证响应丢失后的重试。

## D4. Metadata 允许空值

Metadata 项允许 value 为合法空字符串。字段名仍须非空，并在同一记录内忽略大小写唯一；允许空值不等于允许空字段名、重复键或任意 null/缺失结构。

例如“渠道”的值为空可以保存与发布；继承含空值的旧版本也可以继续编辑、发布与下载。保留现有值内容，不因判空而静默裁剪或改写旧数据。

冻结原型 inlineMetadataProblem 对空值的阻断不再作为实施要求。后续界面和服务端遵循同一规则，同时维持现有有序键值结构与旧文本兼容。

验收覆盖新建空值、继承旧空值、共同编辑空值、发布和 CSV 下载，以及空字段名/重复键仍被拒绝。
