## 1. 问题、目标和范围

当前派生版本会将父版本全部记录加载到浏览器，提交完整数组；服务端读取全部父记录并比较，向 MinIO 保存完整 records 对象，再逐条插入整版 `version_member`。未修改的 `case_revision` 已经复用。

目标是减少少量修改时的网络载荷、成员写入和 MinIO 重复正文。继续使用 PostgreSQL、MinIO 和现有 Worker，版本仍为完整不可变逻辑快照。

保留冻结 v5.3 的页面、控件、顺序、三字段编辑、数据核对、来源、CSV 下载、分支和删除行为。前端只改变内部加载和提交方式，不新增草稿管理、行移动、修改理由、冲突工作台、进度管理或后台作业页面。首版创建及大量新增记录本来需要处理全部新内容，不承诺把它们降为常数成本。

不引入 DVC、Dolt、lakeFS、数据湖引擎、Redis、消息代理或自研 Merkle/Prolly Tree。产品目标仍是每版最多 10,000 条及 PRD 既有容量。

## 2. 选定方案与取舍

采用不可变版本节点、记录级稀疏变更、周期完整成员检查点和按需导出缓存。

| 借鉴对象                   | 采用的思想                             | 不照搬的部分                           |
| -------------------------- | -------------------------------------- | -------------------------------------- |
| Langfuse                   | 只为变化记录写入历史修订               | 全局时间有效区间不能直接表达本项目分支 |
| Hudi、Delta Lake           | 增量与周期物化平衡读写成本             | 数据湖引擎、文件格式和运行基础设施     |
| Git、Dolt、Iceberg、lakeFS | 不可变内容复用、快照引用和共享数据保护 | 完整版本引擎与复杂持久树               |

本次借鉴设计思想；未复制第三方源码。后续若选择复制代码，需单独记录准确提交、文件和许可证。项目一手资料与差异见研究文档，不重复扩展调研。

设完整记录数为 N，变化数为 D，检查点后累计变化数为 C。常规提交传输和新变化存储目标为 O(D)，检查点偶尔写 O(N) 个成员指针。版本解析可能处理 O(N+C) 个成员，发布哈希、数据核对与筛选仍可能需要 O(N) 扫描。此方案不承诺所有请求耗时为 O(D)，也不保证读取比完整成员表更快；必须实测读取代价。

## 3. 数据模型

下述为概念结构；正式表、字段和约束已由 ADR-0011 固定。

| 对象                      | 职责及约束                                                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| `test_case`               | 保持稳定身份；不同测试集不得共享或注入身份                                                      |
| `case_revision`           | 保存完整新记录和来源；内容或来源变化才新建，继承 `parent_revision_id`                           |
| `test_set_version`        | 保留父边、标签、顺序、哈希；增加内部存储格式标识，区分 legacy 与 delta                          |
| `version_change`          | `(version_id, case_id)` 唯一；只保存 add/update/delete 的最终净变化，以及前后修订引用和稳定位置 |
| checkpoint header/members | 绑定版本、格式、成员数和校验值；成员为 case/revision/position 指针；完整校验后才可见            |
| export cache              | 可重建派生字节索引，不决定版本存在性或可访问性                                                  |

首个版本保存完整成员检查点；已有 `version_member` 直接视为 legacy 检查点，不改写旧历史。普通子版本仅保存 delta。

每条记录保留内部稳定顺序键。内容更新不改变位置，删除留空位，新增按现有编辑流程的顺序分配位置；页面 ordinal 是解析后连续展示编号，不是记录身份。不为本次优化加入公开 move 操作、分数索引或任意排序。检查点保持顺序键和逻辑顺序，避免重排导致后续 delta 失效。

版本级独立的变更事实和内容引用必须分开考虑：checkpoint 只能加速状态读取，不能抹掉相对直接父版本的修改、新增、移除事实。无内容变化的合法派生仍按现有行为处理，可产生零 delta 版本。

## 4. 前端与提交协议

沿用现有派生版本路由，父版本 ID 以 URL 为准，不重复要求用户选择。编辑响应提供内部 case/revision 身份；前端分页获取记录，以 case ID 保存本地增删改集合，并合并回可见页面。切页、筛选或重新请求不得丢失尚未发布修改。

前端折叠操作：修改后改回原值不发更新；新增后删除不发操作；同一旧记录最终只发一次更新或删除。服务端独立验证这些规则，不信任前端判断。

拟议更新请求示例（幂等键仍在请求头）：

```json
{
  "operations": [
    {
      "op": "update",
      "caseId": "case_5000",
      "expectedRevisionId": "revision_old",
      "record": {
        "question": "修改后的问题",
        "expectedOutput": "期望输出",
        "metadata": []
      }
    }
  ]
}
```

update 提交该记录完整新内容，避免字段级 JSON Patch。delete 携带 case ID 和父修订；add 携带批次内唯一临时 ID、完整记录、必要的来源选择引用及新增顺序，持久 case ID 由服务端分配。来源必须由项目内已确认资产验证并生成，不能由客户端伪造 locator/hash。旧记录的继承来源由父修订获取。

服务端验证父版本可派生、case 属于父版本、expectedRevisionId 与该父版本匹配、操作无重复冲突、Metadata 合法、来源及最终版本容量合法。容量检查覆盖继承记录和全部来源，不仅检查 D 条请求。数据核对继续按整版语义统计，不提高为新发布门槛。

**并行派生不是过期冲突。** 两个标签页从同一不可变 v1 发布两个子版本均合法，按现有分支规则分配标签。expectedRevisionId 校验的是指定父版本中的记录身份，不与全局“最新修订”比较。先前对话中的“另一标签页发布就拒绝旧标签页”表述不适用于本项目。

复用当前路由并最终替换旧全量请求协议；实施期间如需兼容窗口必须有明确退出点，不长期维护两套公共版本 API。

## 5. 统一版本读取

在现有版本模块内收敛内部 Interface：分页查询、单记录读取和流式遍历。列表、编辑、来源、摘要、核对、下载、删除依赖分析均复用它；调用方不需要知道 legacy/delta/checkpoint 格式。避免在每条路由复制递归 SQL。

解析先找到目标版本最近的有效祖先检查点，应用其后沿唯一父链的 delta；每个 case 以最近一次净变化决定状态，delete 排除成员，再按稳定位置排序。应用全部变化后再计算筛选、总数和分页，不能先截断检查点分页再叠加变化。

项目校验和可见性判断先于内容输出。公开读取拒绝已删除节点；内部读取依赖受专门存储引用规则约束，不能成为公开绕过路径。Metadata 的旧文本兼容、字段顺序、CSV 转义和来源事实沿用现行合同。

当前请求按最多 10,000 条先验证 SQL resolver 的可行性，不预置通用缓存。分页响应小不代表数据库只扫描一页，基准须同时记录扫描行数、内存和延迟。

## 6. 原子发布、哈希与 MinIO

发布流程：解析父状态及净操作，验证最终容量和来源，流式计算规范化 payload hash、证据和数据核对；准备增量对象，经 staging/校验/commit marker 完成后，在受锁的发布事务内复检父状态和删除竞态，分配标签并原子写入修订、delta、版本、来源事实和幂等结果。

MinIO 增量 manifest 保存格式版本、父版本 ID、记录数、规范化操作及新修订必要内容、来源证据引用和完整性哈希。D 条变化可在 PG 与对象内重复保存以保持两侧证据职责；不重复保存 N 条未变化正文。格式固定为 ADR-0011 的 `evalbase.test-set-delta-manifest` v1，不能把增量 hash 冒充完整 payload hash。

保留发布时完整 payload hash 及现有规范化规则；允许 O(N) 流式读取计算，不推迟到首次下载。数据核对的整版统计也计入发布成本。哈希定义发生格式演进时必须带内部格式版本并保留 legacy 验证，不重写旧哈希。

数据库提交仍是可见性边界。对象成功而数据库失败只留下可回收孤立对象；数据库提交后响应丢失由同一幂等键返回同一版本。清理器保护进行中的发布引用，不能仅按对象年龄删除。取消与提交竞态复用现有语义，不另加取消成功的虚假承诺。

## 7. 检查点与读取上限

距最近 Checkpoint 20 代，或累计变化达到基准记录数的 20% 时触发后台 Checkpoint；空版本以至少 1 条为分母。任一可见版本的硬上限为 40 代或累计 40% 变化；即将越界时必须随新版本同步物化 Checkpoint，否则发布回滚。

后台任务不足以保证硬上限。触及上限且 Worker 未完成时，发布路径按 ADR-0011 在新版本自身完成必要 Checkpoint 后再使其可见，页面沿用现有等待/可恢复错误状态。Checkpoint 失败不使既有版本不可读，也不允许继续延长链。

Worker 基于不可变版本生成成员指针，完成数量、顺序、内容校验后原子发布检查点 header。重复任务幂等，半成品不参与解析。发布、检查点和删除使用一致锁序与依赖复检，防止任务完成后复活已删除数据。

仅当原有基线与 delta 仍可重建时，检查点才是可丢弃的加速结构。旧版本完整基线，以及删除后用于切断祖先依赖的检查点，是必要存储，不能按缓存策略清理。

## 8. 下载与缓存

保持两个独立 CSV 下载及选中 version ID 绑定。首次请求通过统一解析器流式生成字节，后续可复用 MinIO 缓存；数据与溯源各自校验，不引入 ZIP 或用户可见导出任务。

缓存键包括 version ID、导出类型、序列化格式版本及该导出的证据指纹。provenance 指纹必须覆盖来源和删除可见性依赖，不能仅使用数据 payload hash。若来源改名/移动等会影响现有输出，也必须按现行行为失效；不能通过缓存偷偷冻结原本动态展示的事实。

每次下载（含命中缓存）重新校验项目、版本状态和删除边界；只有完整生成校验后的对象才能登记命中。生成失败清理暂存；与永久删除竞态复用 fail-closed 控制。缓存随关联内容删除而失效，缓存缺失不损害版本真源。

## 9. 删除、墓碑和物理回收

遵守 PRD FR-08 与 ADR-0008，不把“永久删除”改成仅隐藏完整可重建版本。

回收/恢复只改可见性，引用完整保留。整套或整支永久删除先阻断新读取、派生和引用，再清理专属对象，保留仍被未删除版本合法使用的记录内容和必要来源证据。

删除中间版本内容时，其直接保留后代若依赖该版本 delta，必须在内部建立独立完整检查点，校验内容与来源等价后原子切换存储依赖。必要的前值与修改事实按现行溯源/删除规则保留；用户版本父边仍指向原墓碑，不改挂。不能为方便读取而无限保留被删除版本的完整重建链。

随后清理该版本专属 delta、manifest、缓存与无合法引用修订。关系图的父边不等于内容存储引用；GC 按内容、检查点和来源的真实引用计算，而非把所有图祖先正文永远保留。若保护后代步骤失败，删除保持不可访问并可重试，未删除后代内容不丢失。

此处细化了研究文档中的两种候选策略：以独立检查点切断依赖为正式设计方向，不采用单纯隐藏并保留全部祖先正文的捷径。必要共享内容保护不是新增用户能力。

## 10. 验证与实施顺序

1. 在隔离开发数据上建立当前基准，并用技术 Spike 验证 resolver、稀疏写入和检查点；不操作部署目录、现有运行服务或真实数据。
2. 已根据 Spike 结果由 ADR-0011 固定阈值、schema、manifest 和删除依赖切断，并同步 Architecture；下一步同步 Spec 和必要 Test Plan 后拆 Tickets。
3. 以加法迁移引入新表及格式标识，旧版本保持 legacy；接入统一读取，在合成数据上对同一逻辑版本双算比较。
4. 实现稀疏提交、增量对象、检查点、删除依赖切断和下载兼容。上述正确性路径完成后才允许正式写入 delta，不能先切换再补删除/检查点。
5. 前后端同时切换协议；UI 对齐冻结原型，Owner 通过现有创建、派生、来源、下载和删除流程验收。
6. 旧历史压缩或对象清理另作后续维护决定；本次不批量重写或删除旧版本。

回滚分两层：关闭新 delta 写入时，新程序仍必须能读取已存在 delta；直接退回只认识 version_member 的旧程序不安全。若必须降级到旧程序，先在维护窗口将全部新版本物化为旧程序可读取的成员与完整对象，保留 IDs、父边、标签和哈希并验证其全部依赖。未完成兼容物化前采用向前修复，不以开关承诺任意旧二进制回退。

## 11. 必要验证和完成标准

使用同一 10,000 条合成数据、同一硬件与记录长度，记录程序 SHA、冷热缓存、重复次数、请求字节、PG 行/索引/WAL 增长、MinIO 字节、峰值内存、发布时间、分页/筛选/下载延迟。延迟改进不预设虚构倍数；Spike 报告真实对比后确定实施门槛。

| 场景                          | 必须证明                                                              |
| ----------------------------- | --------------------------------------------------------------------- |
| 改 1 条、100 条               | 非检查点发布只传变化记录，新增对应修订/delta，不写 N 个成员或整版对象 |
| 连续小版本及 Worker 停止      | 检查点前后结果相同，触及硬上限时有可靠处理，不无限增加回放深度        |
| 旧父版本的两次并行派生        | 两次均按分支规则成功，父版本不变，幂等重试不重复生成                  |
| 增删改及净零修改              | 内容、顺序、计数、稳定身份和来源与旧实现一致                          |
| Metadata 筛选及两个 CSV       | legacy/delta/checkpoint 的结果、字节规则与现有合同一致                |
| 中间墓碑与整支永久删除        | 后代可读取，父边不改挂，已删内容无公共访问，缓存与共享引用正确        |
| 对象成功/事务失败、提交后断连 | 无可见半版本，孤立对象可回收，重试只得同一结果                        |

这些是持久化架构改变所需的定向证据，不要求每张 Ticket 重跑全仓历史测试。至少做一次受影响冻结 UI 流程的浏览器核对。容量边界、确定性哈希、删除竞态和双格式读取必须覆盖；详细测试归属在后续 Ticket 中集中安排，避免重复。
