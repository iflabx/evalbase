## 1. 背景与问题判断

Project Owner 认为当前 EvalBase 与原始预期存在根本偏差，而不是局部视觉问题：

1. 产品暴露了过多选项、领域状态和技术概念，唯一真实用户难以理解其用途。
2. 当前前端没有充分复用、修改 `frontend-v1/` 已有的应用外壳、页面布局和交互模式，实际结果与此前“借用、复用、修改已有前端”的要求不符。
3. 产品的真实使用模式是 Project Owner / Sole Developer 单人使用、单人维护；登录、项目成员和角色管理不应成为日常流程。
4. 用户真正需要的是两个主要工作区：原始资料管理，以及测试集创建、编辑、迭代和下载。
5. 解析、版本、血缘、审计、容量、作业和交付等复杂度可以保留在系统内部，但不应要求普通页面用户逐项理解和操作。

当前 Web 的主要问题是接口过浅：后端实现中的大量概念被直接投影为页面、表单和选项。正确方向应当是让系统内部保持必要的严谨性，同时以很小的用户界面隐藏实现复杂度。

## 2. Project Owner 的目标产品

### 2.1 总体原则

- 唯一真实用户是 Project Owner / Sole Developer。
- 默认使用单人工作模式；不提供登录、项目成员或角色管理。
- 一级导航只保留“原始资料”和“测试集”。
- 页面使用接近 Windows 文件资源管理器的浏览方式，让用户通过文件名、列表或图块识别对象。
- 默认页面只展示完成当前任务必需的信息；技术证据和高级状态按需展开。
- CSV、JSON 和 JSONL 的原始格式可以不同，但浏览时都通过统一映射后的记录形式展示。
- 系统自动记录可以自动取得的哈希、位置、来源关系、修改和版本事实，不要求用户手工维护技术证据。
- 用户语言以“资料、记录、测试集、版本、来源、下载”为主，不把 Working Draft、Candidate Snapshot、Delivery Record、lease 或内部 Job 状态作为主任务词汇。

### 2.2 原始资料页面

原始资料页面负责浏览、上传、解析确认和查看此前上传的资料。

#### 页面布局

- 使用类似 Windows 文件资源管理器的列表或图块展示已上传资料。
- 默认信息包括文件名、文件格式、大小、上传时间和是否可正常浏览。
- 可在列表与图块之间选择一种最简单、稳定的默认形式；不为了表现形式建立复杂的自定义视图系统。
- 点击一项资料后，进入该资料的浏览界面或详情抽屉。
- 浏览内容采用统一记录表格，不要求用户理解 CSV 行、JSON Pointer 或 JSONL 物理行等内部差异。
- 必要时可以展开原始位置、解析错误和字段映射，但不把它们作为默认页面主体。
- 页面右下角提供唯一醒目的“上传资料”按钮。

#### 上传弹窗

上传操作在同一个弹窗中完成：

```text
选择文件 -> 自动解析和映射 -> 浏览确认 -> 确认上传
```

具体要求：

1. 用户选择一个 CSV、JSON 或 JSONL 文件。
2. 系统上传至临时接收区并执行服务端解析，不在浏览器中整体解析大文件。
3. 同一弹窗展示统一格式的记录预览、自动映射结果和明确的解析错误。
4. 用户可以在确认前纠正必要的字段映射或取消操作。
5. 用户确认内容无误后点击“确认上传”，资料才在日常资料列表中显示为已保存。
6. 用户取消时，临时接收内容必须可清理，不能留下领域可见的半成品。

上传时不要求填写：

- 责任人；
- 使用目的；
- 许可状态；
- 敏感级别。

测试集的使用目的在创建测试集时填写。允许数据范围仍需由经 Project Owner 批准的环境规则保证，但不应把多项治理字段重复放到每次上传表单中。

### 2.3 测试集页面

测试集页面负责浏览、创建、编辑、迭代和下载测试集。

#### 页面布局

- 使用类似 Windows 文件资源管理器的列表或图块展示已创建的测试集。
- 默认信息包括名称、当前版本、记录数、更新时间和可用状态。
- 点击测试集后进入详情页，查看当前版本、历史版本和统一格式的记录内容。
- 每个已创建测试集提供直接、易发现的“下载”操作。
- 页面右下角提供“新建测试集”按钮。

#### 创建第一个版本

新建测试集采用连续但简短的弹窗或全屏编辑流程：

```text
选择原始资料 -> 选择记录 -> 编辑记录 -> 填写名称和用途 -> 创建 v1
```

具体要求：

1. 可以选择一个或多个已上传的原始资料。
2. 可以选择整份资料，也可以只选择其中部分记录。
3. 所选记录进入统一的表格编辑器。
4. 用户可以增加、删除和修改记录。
5. 用户填写测试集名称和使用目的。
6. 用户确认后形成测试集第一个版本 `v1`。

#### 迭代新版本

- 用户可以从任一适用的已有版本开始编辑。
- 编辑体验与创建 `v1` 使用同一套表格和动作。
- 保存或发布后形成新的不可变版本，不覆盖旧版本。
- 用户可以在版本之间切换、查看差异并下载指定版本。
- 页面使用“编辑新版本”“保存版本”“下载”等用户语言，不要求用户操作内部候选、快照或租约对象。

#### 自动溯源

系统自动记录两层来源事实：

1. **资料级来源**：一个测试集版本使用了哪些原始资料。
2. **记录级变化**：每条记录来自哪份原始资料的哪条记录，以及用户对其做过哪些增加、修改或删除。

用户不需要手工填写血缘边。详情页可以通过“查看来源”展示这些事实，但默认编辑页面不应被技术血缘信息占据。

## 3. 目标信息架构

```text
EvalBase
├── 原始资料
│   ├── 资料列表 / 图块
│   ├── 统一记录浏览
│   └── 上传资料弹窗
│       ├── 选择文件
│       ├── 解析与映射
│       ├── 预览
│       └── 确认上传
└── 测试集
    ├── 测试集列表 / 图块
    ├── 测试集详情
    │   ├── 当前版本
    │   ├── 历史版本
    │   ├── 记录表格
    │   ├── 查看来源
    │   └── 下载
    └── 创建 / 编辑版本
        ├── 选择资料与记录
        ├── 表格增删改
        ├── 名称与用途
        └── 保存新版本
```

以下内容不进入一级导航：

- 登录；
- 项目成员与角色；
- Delivery Records；
- 后台作业；
- 审计事件；
- Controlled Deletion；
- Transformation Run；
- 系统设置；
- Phase 1B 或生产能力。

其中确有保留价值的能力作为对象详情中的次要信息、后台自动行为或高级操作存在。

## 4. 建议的工程策略

### 4.1 结论

不建议重写整个项目，也不建议继续在当前 Web 上做布局修补。建议采取：

> 保留后端、数据和领域能力；替换当前前端；增加一个面向单人工作流的小接口。

### 4.2 保留、隐藏与替换矩阵

| 当前能力                       | 决策           | 目标处理                                       |
| ------------------------------ | -------------- | ---------------------------------------------- |
| PostgreSQL 与 MinIO 持久化     | 保留           | 继续作为元数据和不可变字节真源                 |
| 流式上传、大小限制和幂等       | 保留           | 隐藏在上传弹窗背后                             |
| CSV、JSON、JSONL 服务端解析    | 保留           | 统一为资料记录浏览接口                         |
| 原始字节、哈希和定位证据       | 保留           | 默认隐藏，详情按需展示                         |
| 测试集版本与原子发布           | 保留           | 对用户表现为保存不可变新版本                   |
| 记录级和资料级血缘             | 保留           | 自动记录，通过“查看来源”展示                   |
| 下载包和离线校验               | 保留           | 简化为测试集详情中的下载操作                   |
| 后台作业、重试和取消           | 保留           | 自动运行；只有等待或失败时显示简洁状态         |
| 容量和完整性检查               | 保留           | 失败时给出用户可执行的修正提示                 |
| Controlled Deletion            | 后台保留       | 不作为普通主流程；是否保留高级入口需重新决策   |
| Owner/Editor/Viewer 多角色界面 | 移除           | 真实单人模式只显示隐含 Owner                   |
| 登录表单                       | 删除           | 冻结原型没有登录步骤，打开应用直接进入原始资料 |
| 项目成员变更历史               | 从日常界面移除 | 审计事实保留，不与当前成员混排                 |
| 当前超大型 Web 页面            | 替换           | 使用按页面和任务组织的新前端                   |
| 当前后端核心实现               | 不重写         | 只为新工作流补足缺少的接口                     |

### 4.3 单人工作流模块

新前端不直接理解现有全部 HTTP 路由和领域状态。建议在 Web 与现有后端能力之间形成一个小而深的单人工作流模块，其用户可见接口只覆盖：

- 浏览资料；
- 开始上传并取得解析预览；
- 确认或取消上传；
- 浏览测试集和版本；
- 从资料或父版本打开编辑；
- 保存新的不可变版本；
- 下载指定版本。

解析、容量、原子发布、对象存储、作业协调、审计和血缘全部留在模块实现内部。不得建立一层仅改名、不隐藏任何复杂度的转发接口。

## 5. `frontend-v1/` 完整复制方案

既有选择性迁移没有充分兑现复用要求。正式方案改为在首次获授权的前端 Ticket 中记录 donor commit，完整复制 `frontend-v1/` 为 `frontend-v2/`，然后只在副本中“保留外壳、替换内核”。`frontend-v1/` 永久不改，`git diff -- frontend-v1` 必须为空。

| `frontend-v1/` 来源                                           | 重构用途                                     |
| ------------------------------------------------------------- | -------------------------------------------- |
| `src/styles.css`                                              | 作为视觉令牌、密度、圆角、颜色和焦点样式基线 |
| `src/routes/__root.tsx`                                       | 应用外壳、内容区和响应式布局的起点           |
| `src/components/app-sidebar.tsx`                              | 收敛为仅有“原始资料”和“测试集”的导航         |
| `src/components/state-view.tsx`                               | Loading、Empty、Error、PageHeader 等通用状态 |
| `src/routes/datasets.index.tsx`                               | 资料和测试集资源管理器式列表的布局种子       |
| `src/routes/datasets.new.tsx`                                 | 上传、映射、预览和确认流程的视觉种子         |
| `src/routes/datasets.$id.tsx`                                 | 测试集详情、版本和记录浏览的布局种子         |
| 必要的 Button、Dialog、Table、Input、Tabs、Toast 等 primitive | 随目录完整复制，在副本中按实际需要保留       |

完整复制后必须从 `frontend-v2/` 正式运行路径移除：

- Mock store 和旧 service；
- 浏览器内大文件解析；
- 旧 Dataset 领域模型；
- Langfuse、运行、计算器、报告和设置页面；
- 旧 Phase 1B/Phase 2 导航；
- 与两条主流程无关的页面和依赖；未被使用的 primitive 可在副本中清理。

重构目标不是让新页面“看起来有一点像” `frontend-v1/`，而是直接从其真实代码副本出发，保留字体、外壳、页面层级、Dialog、表格和状态表达，再替换领域内容和服务端接口。正式切换后只有 `frontend-v2/` 进入构建和部署，当前 `src/web/` 不再运行。

## 6. 已确认的产品与安全合同

以下事项已由 Project Owner 于 2026-08-31 决定，并已同步权威合同。任何进一步改变仍需重新确认。

### 6.1 无登录步骤的单人模式

正式 Phase 1A 单人产品不提供登录页、登录按钮或凭据输入。Owner 打开已批准的非生产访问地址后直接进入“原始资料”。服务端可以用配置中的唯一 Owner 建立非交互式请求身份，并继续执行 Origin/CSRF、项目范围和跨项目 IDOR 边界；这些是内部安全实现，不得转化为用户步骤或多人能力声明。该决定仅适用于当前受限非生产部署，不构成生产认证方案。

### 6.2 上传来源字段

目标体验取消每次上传时的责任人、用途、许可状态和敏感级别字段。这会改变当前 Source Attribution 和允许数据分类合同。

已决定：

- 哪些来源事实由系统自动记录；
- 测试集用途如何从上传阶段移动到创建测试集阶段；
- 允许数据范围使用环境级一次 Owner 确认，并结合实际可取得的文件/来源事实；
- 既有数据中的来源说明如何继续展示；
- 不能用虚假默认值伪造许可、敏感性或责任事实。

### 6.3 上传确认语义

目标流程要求先解析和预览，再由用户确认资料上传成功。现有实现可能在解析前已经登记 Data Asset，因此需要正式定义临时接收区、取消清理、超时回收和确认后的领域可见性。

### 6.4 测试集表格编辑

目标流程允许用户直接增加、删除和修改记录，并自动形成新版本及变化溯源。需要明确：

- 编辑时的最小正式字段；
- 自动保存和显式保存新版本的区别；
- 新增记录的来源标记；
- 修改记录与父版本修订的关系；
- 删除是从新版本排除记录，还是触发 Controlled Deletion；两者不得混淆。

### 6.5 下载与 Delivery Record

用户直接从所选测试集版本下载 `data.csv`，或下载包含 `data.csv` 与 `provenance.csv` 的数据/溯源包，不需要理解 Delivery Record。标准包、完整溯源包、Langfuse CSV 和 Delivery Record 继续作为后台能力，但不得阻碍普通下载。

- 不启动后续 Ticket。
- 不删除当前代码、数据库、对象存储或 Git 历史。
- 记录当前前端为未获 Project Owner 产品验收的实现。

- 展示桌面宽度和必要的窄屏行为。

原型确认后再修改：

- Implementation Spec；
- Test Plan；
- 系统流程；
- 涉及认证、来源说明、上传确认或版本编辑的 ADR；
- Ticket 18 状态和新的实施 Ticket。

本阶段只同步合同，不授权阶段 3 或阶段 4 的代码实施。

### 阶段 3：最小后端适配

- 盘点现有接口与目标工作流的差距。
- 保留现有解析、版本、血缘和下载实现。
- 只补临时上传确认、直接表格编辑或单人身份所必需的最小能力。
- 不借重构引入新服务、消息代理、缓存平台或 Phase 1B。

### 阶段 4：复制并替换正式前端

- 在固定基线完整复制 `frontend-v1/` 为 `frontend-v2/`，保持 donor 不变。
- 在副本中替换 Mock 业务并实现已确认原型，不在当前超大型页面上继续叠加条件分支。
- 只连接已确认的单人工作流接口。
- 验证通过后把构建/运行入口切换到 `frontend-v2/`，使 `src/web/` 退出运行路径；保持唯一正式前端，不建立第二个长期部署单元。

### 阶段 5：真实单人闭环验收

Project Owner 使用正常浏览器和允许分类的数据完成：

```text
上传资料
  -> 解析并预览
  -> 确认保存
  -> 创建测试集 v1
  -> 修改形成 v2
  -> 查看来源
  -> 下载指定版本
```

只有 Project Owner 明确确认该流程符合预期，简化重构才可视为产品验收通过。

## 8. 原型验收标准

原型阶段优先回答“是否符合人的使用直觉”，不以技术功能数量作为完成标准。

1. 首次打开应用时无需解释即可知道去哪里上传资料、去哪里创建测试集。
2. 页面上不出现登录、成员、角色、Delivery Record、Candidate Snapshot、lease、Job ID 等主流程无关概念。
3. 原始资料页面默认信息不超过识别文件和判断解析状态所需的范围。
4. 上传全过程在一个连续弹窗中完成，用户能在确认前看到实际解析内容。
5. CSV、JSON 和 JSONL 的预览使用同一种记录浏览方式。
6. 创建测试集时可以从一个或多个资料中选择全部或部分记录。
7. 用户能在一个表格中增、删、改，并清楚知道何时形成 `v1` 或新版本。
8. 测试集下载入口直接、明确，不要求经过交付管理页面。
9. 来源信息可查看，但不阻碍编辑主流程。
10. Project Owner 能用自己的语言解释每个可见按钮的用途；无法解释的选项默认删除或隐藏。

## 9. 非目标

- 不重写已经验证的解析、存储、版本、血缘、导出和持久化实现。
- 不为了重构引入第二个前端、第二套领域模型或第二套数据真源。
- 不新增真实多人协作、Phase 1B、生产部署或敏感数据能力。
- 不把内部技术对象简单改名后继续全部暴露给用户。
- 不在原型获批前继续扩充当前 Web。
- 不用自动填写虚假元数据的方式制造表面上的简化。
- 不删除审计、历史版本或现有持久化数据来清理页面。

## 10. 对当前仓库状态的影响

本次批准只改变产品与实施合同：

- PRD、Architecture、相关 ADR、Implementation Spec、Test Plan、系统流程、前端复用说明和 Tickets 18–26 已同步。
- 原 Ticket 18 的三导航合同已被替代；新 Tickets 18–26 按 Owner 的实际操作顺序提供渐进预览，`ready-for-agent` 仍不代表执行授权。
- 当前 Gate、Production Gate、允许数据范围、运行容器、数据库和对象存储不改变。
- 本文不授权代码实现、数据迁移、`frontend-v1/` 复制、部署切换、Git 提交或删除操作。

下一步应先形成原型到现有 API/数据模型的差距清单和有依赖顺序的最小 Tickets，再由 Project Owner 逐张授权。

## 11. 建议结论

EvalBase 不需要整体重写。当前已经实现的后端能力具有保留价值，但当前前端和用户接口不应继续作为产品基础。

推荐方案是：

> 保留后端和数据，放弃当前前端的产品呈现；冻结原型作为交互合同，完整复制 `frontend-v1/` 为只改副本的 `frontend-v2/`，先补最小后端接口，再一次切换并替换正式 Web。

该方案优先恢复 Project Owner 对产品的理解和控制，同时避免丢弃已经验证的存储、解析、版本、血缘和导出能力。
