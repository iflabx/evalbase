# EvalBase 性能与瓶颈测试方案

日期：2026-10-02。状态：**待执行的扩展方案，不是性能通过报告**。

本轮测试规模：**2 人和 3 人同时使用**。使用预期仍为最多 10 人，但本轮不安排 5/10 人负载，也不安排两小时稳定运行、断线和重启恢复测试；本轮结果不能据此证明这些未测场景。产品容量和一致性以 [v2 PRD](PRD-evalbase-v2.md)、[v1 容量合同](PRD-evalbase-v1.md#62-容量)及 [架构不变量](architecture/phase1a-architecture.md#6-数据与版本不变量)为准。本方案补充 [v2 测试计划 §6](test-plan-evalbase-v2.md#6-架构与性能优化验证)，不增加产品功能、公开 API 或部署要求。

## 1. 要回答的问题

1. 2 位和 3 位独立用户浏览、编辑时，页面、保存和同步是否仍及时？
2. 大文件解析、建草稿、发布、导出与存储 Checkpoint 是否阻塞其他用户？
3. 瓶颈主要在浏览器、Web CPU/内存、数据库查询/锁/连接池、Worker，还是对象存储和网络？
4. 数据量、版本回放长度和同时重操作增加后，在哪个条件下开始恶化？
5. 并发操作和延迟时能否保持输入、唯一发布、版本不可变、权限与删除安全？

已有 [优化报告](research/architecture-performance-optimization-2026-10-02.md)使用同条件三次 10,000 条基准和 10 个会话短突发，但会话来自两个账号；不等同于 10 个独立账号持续使用，也没有覆盖最大字节容量。五账号浏览器测试是功能证据，不能替代本方案的延迟分布和资源峰值。

## 2. 环境和可重复条件

- 固定修复后的 Git SHA、镜像 digest、Node 版本、配置、数据库迁移与浏览器版本；运行前验证 `/health`、`/health/ready`，结果附这些值。
- 使用新的任务专属 Compose 项目 `evalbase-performance-validation`，独立 PostgreSQL/MinIO 卷、数据库、桶和网络；Web 只绑定空闲 loopback 端口。不要在正式实例、Owner 验收库或服务器其他项目运行负载、删数据、重启、改配置。
- 负载器、浏览器、Web、Worker、PostgreSQL、MinIO 分别记录 CPU/RAM 限额。执行前查看共享主机空闲资源；有余量时初始参考 Web 2 CPU/3 GiB、Worker 1 CPU/2 GiB、PostgreSQL 2 CPU/2 GiB、MinIO 1 CPU/1 GiB，负载器另计。资源不足则下调或使用独立机器，报告只能代表实际资源组合。
- 基线与复测保持资源限额、数据种子、索引/统计信息、诊断配置和并行度一致。基线为修复后版本；优化对比必须只改变一个待验证因素。可另复跑旧基准，但不把不同条件结果拼成提速比例。
- 服务端测试走隔离 Docker 网络或服务器本机，测服务本身；用户电脑经 SSH 隧道的浏览器测端到端体验。分别报告网络 RTT、服务器耗时和浏览器处理时间，不能把隧道延迟算成 SQL 耗时。
- 3 个独立账号：1 管理员、1 编辑、1 查看。2 人档使用管理员和编辑，3 人档增加查看账号；每个账号独立 cookie/session 与浏览器上下文。保留注册/登录成本和已登录操作两组数据，登录失败重试不能伪装成功。所有账号和夹具只存在于自动化库。
- 复用现有 Node、Playwright、`scripts/benchmark-architecture.ts`、`scripts/architecture-load-client.mjs` 和 Docker/PostgreSQL 工具，按下述范围补负载参数和采样即可。旧脚本不是完整持续负载器；先核对其计时、身份与接口后再扩展，不为本轮引入新的监控平台。

## 3. 合成数据矩阵

固定种子，保存文件 SHA-256、行数、原始 bytes、规范化 bytes、Metadata 项数和版本图形状。数据不用真实业务正文；未获授权不复制正式数据库。

| 维度 | 组合 | 验证重点 |
| --- | --- | --- |
| 记录量 | 100、1,000、10,000 条 | 分页/筛选是否随整版扫描变慢；传输仍有界 |
| 正文/Metadata | 短文本；长文本；多项 Metadata；中文/换行/空值；低/高搜索命中率 | 编码、GC、渲染和筛选成本；有字段名的空值保留 |
| 文件格式 | CSV、JSON、JSONL，各自确定性夹具 | 解析、映射预览、确认耗时；不能只测 CSV |
| 文件/来源边界 | 单文件 50,000,000 bytes/10,000 条；编辑 5 文件、100,000,000 原始 bytes/10,000 条来源 | 各边界分别构造合法组合，不能 5×50 MB 绕过总量限制 |
| 版本容量 | 10,000 条且规范化内容接近/达到 100,000,000 bytes | 大对象编码、首次发布、CSV 和内存峰值 |
| 超限 | 第 50,000,001 byte、第 10,001 条、第 6 文件、总原始/规范化第 100,000,001 byte | 快速明确拒绝，不留下半批资产或正式版本 |
| 列表规模 | 5、25、100 个新建草稿/正式测试集 | 全部/草稿/已发布、搜索空态、统一分页和总数 |
| 版本存储 | legacy、Checkpoint、稀疏 Delta；链和多分支 | 20 代/累计 20% 后台阈值；40 代/40% 回放硬上限；来源和 CSV 一致 |

超大数据、100 个列表对象与多项目隔离夹具只放自动化库，不污染给 Owner 浏览的一个验收项目。Checkpoint 完成后回放深度会变化，必须记录每次实际基点和回放长度；本轮不安排故障注入来制造积压，未到达硬上限时如实标为未覆盖，不能误报为“已测到 40 代普通读取”。

## 4. 测试场景

| 编号 | 场景与负载 | 测什么、定位什么 |
| --- | --- | --- |
| P01 | 空闲 10 分钟；随后入队真实 Checkpoint 任务 | Worker 退避、领取/维护 SQL、空闲 CPU；任务启动等待，不能为节省资源饿死任务 |
| P02 | 单用户分操作，三次热运行；首次请求另记 | 登录、项目/原始数据/测试集列表、翻页、搜索、筛选、来源、记录详情、版本图；建立稳定基线 |
| P03 | 2 → 3 独立用户，逐档持续 20 分钟 | 混合读写与真实思考间隔；吞吐、延迟和错误随并发增长；连接池/SQL/CPU 是否饱和 |
| P04 | 管理员与编辑改同条不同字段、同字段、整体 Metadata；3 人档增加查看账号浏览 | 不同字段均保存；真实同字段冲突保留输入；空白占位不误冲突；快速连续修改、旧响应、删除竞争 |
| P05 | 2/3 用户共同在线；同草稿/不同草稿；同账号多标签；隐藏与恢复窗口 | 轮询、心跳、在线 TTL、同步延迟、请求放大与跨草稿隔离；隐藏页不持续拉事件 |
| P06 | 三格式上传、映射预览/变更、确认；1、2 个并发批次；重复字节和同键重试 | Web 解析/编码、MinIO 读取、数据库批次与锁；确认错误/取消不能产生半批可见资产 |
| P07 | 新建/派生 100/1,000/10,000 条；首次发布、稀疏/高比例改动；1、2 个并发重发布 | 同步发布、串行编码线程、RSS/GC、事务持锁、对象写入；两人同草稿发布只得到同一正式版本 |
| P08 | 页/搜索/Metadata/来源筛选和两种 CSV；首次导出与重复导出 | 版本解析、查询计划、来源聚合、CSV 编码/缓存；浏览器不能为筛选下载整版 |
| P09 | 2/3 用户档内分配轻量浏览与一次 P06/P07/P08，另叠加后台 Checkpoint | 重操作的全时段干扰：启动、中段、提交、回落；前台总账号数保持该档人数，不额外增加负载账号 |
| P10 | 回收/恢复、墓碑切断及存活后代读取，另有读写背景流量 | 删除闭包、共享内容保护、依赖 Checkpoint、锁等待及缓存清理；仅删除预先列明的合成对象 |

本轮场景为 P01–P10；原 P11（两小时稳定运行）和 P12（断线、重启及依赖故障恢复）不执行，不以短档测试替代其结论。

P03 默认工作节奏：每个活动用户读操作间隔 2–5 秒；编辑用户每 5–10 秒离焦保存一个字段。按业务动作计，初始分配 60% 列表/搜索/浏览、25% 字段编辑、10% 来源选择/设置、5% 创建/发布/下载，查看账号只执行允许的只读动作。在线/事件请求按应用实际周期自然产生，单独计数，不能包含在这个比例里伪装业务吞吐。

执行器应区分角色可操作范围；思考时间使用固定种子的随机分布。报告每种业务动作的实际次数/速率，并另做固定到达率的轻量读写探针：在相同 2/3 账号上分别固定 2/3 个动作/秒，记录计划发起时间、排队等待和实际完成时间。探针单独运行，不额外增加账号；达到停止条件即结束该档，避免闭环用户因变慢而自动降低发起率掩盖瓶颈。

P07/P09 先测 10,000 条正常大小，再逐级加大 bytes。2 个并发重发布使用不同草稿；同草稿竞争单独统计唯一结果。资源不足时只做到已执行档位。本轮不增加其他人数档，也不要求把系统压到崩溃。

## 5. 浏览器体验与测量方法

- 使用现有 Playwright 独立上下文验证真实服务端；Computer Use 用于少量可见操作与截图，不用于毫秒级吞吐测量。浏览器负载器自身的 CPU/内存也要采样，饱和时不能推断服务端瓶颈。
- 记录导航开始到关键表格可操作、点击行到编辑区可用、离焦到 HTTP 确认、确认到对方字段显示；同步同时记录实际最大延迟与超过 2 秒的比例。
- 保持一页真实浏览器作为体验探针，其余 API 用户负责可重复负载，总账号数仍为 2/3 人；重点场景改用 2/3 个真实浏览器上下文核对在线、编辑位置及输入，不同时叠加同账号的 API 负载。API 测试不能证明渲染流畅。
- 采集请求数/响应大小、页面长任务（超过 50 ms）、输入响应、JS 错误；对桌面和 960 像素视口检查渲染与可操作性。明确初次资源加载、缓存命中与数据查询时间。
- 退出/切换记录/发布前验证待保存写入完成。刷新确认内容真实持久化，不把前端状态或 HTTP 200 单独当作保存正确性证据；本轮不主动断网或重启服务。

## 6. 分层指标和瓶颈判断

| 层 | 采集指标 | 判断与后续诊断 |
| --- | --- | --- |
| 业务/HTTP | 操作数、请求数、完成/到达速率、p50/p95/p99/max、超时、状态码 | 每个动作独立统计；409 预期冲突、预期权限/容量拒绝与意外失败分开；失败请求延迟也保留 |
| Web/Worker | Docker CPU、RSS、堆、重启/OOM、事件循环延迟、任务领取和阶段耗时 | CPU 与 loop 延迟同步上升才追查编码/解析；RSS 包含编码线程，主线程堆不能替代总内存 |
| PostgreSQL | SQL 总量/错误、连接池等待、等待连接数、活动查询/事务、锁等待、I/O | 当前每进程池 max=10；排队高但 SQL 快，查长事务占连接；SQL 慢，再查过滤/解析查询计划与索引 |
| MinIO/磁盘 | 对象读取/写入次数、字节、耗时、磁盘空间与 I/O | 查询稳定但确认/发布慢，区分对象传输和持锁写入；用客户端阶段计时补已有指标缺口 |
| Worker/队列 | 深度、最老等待、成功/失败/重试、阶段时间、Checkpoint 完成与回放深度 | 增长不回落说明消费不足；区分队列等待与任务执行，不能只看队列数量 |
| 浏览器/网络 | RTT、HTTP 时间、渲染/长任务、输入延迟、同步时间和实际请求大小 | 服务端快而界面慢查渲染/过度失效；本机快而 SSH 慢查链路，避免错误增加服务端资源 |

复用隔离实例 `/metrics` 的 `evalbase_http_duration_seconds`、`evalbase_sql_duration_seconds`、`evalbase_pool_wait_duration_seconds`、`evalbase_pool_waiting_connections`、RSS/heap/event-loop 指标，以及现有任务/健康指标。每 5 秒采样，记录累计值差分及进程重启；标出采样自身的 SQL，不能将它算成业务查询。事件循环当前 mean/max 为进程生命周期统计，既有任务阶段为 count/sum；不能从它们直接声称某窗口 p95。

SQL 指标只给总量/分布，不定位某条 SQL。发现慢场景后才在隔离库用 `pg_stat_activity`/锁快照及代表查询的 `EXPLAIN (ANALYZE, BUFFERS)` 分析；后者会真正执行查询，写语句只在可回滚合成事务中分析。若需查询指纹工具，只在测试库配置。输出只保留模板、指纹、计划和数值，移除正文、参数、邮箱、资源 ID、令牌与对象 URL；不打开共享主机全局日志。

CPU/GC 采样按需单独复测，先证明慢点，再采样对应进程。不能把开启 profiler 的结果与无 profiler 的正常性能结果直接比较。

## 7. 测量规则与评价目标

以下延迟值是本方案的**诊断目标，不是新增产品 SLA**；超过时报告瓶颈并复核用户体验，不以修改容量合同掩盖问题。2 秒同步继续引用既有 COLLAB-07 验证目标。

| 项目 | 初始评价目标 |
| --- | --- |
| 2/3 人正常混合负载的列表/分页/搜索 | 每类服务端请求 p95 ≤ 1 秒；p99 ≤ 2 秒 |
| 字段离焦自动保存 | 服务端确认 p95 ≤ 1 秒；真实竞争仍得到可恢复冲突 |
| 已确认保存到另一活动浏览器 | 核对 2 秒目标，记录 p95/max 和超过 2 秒次数，不用均值隐藏超时 |
| 关键列表/编辑区可用 | 热访问端到端 p95 ≤ 2 秒；初次静态资源和 SSH 链路另列 |
| 10,000 条正常大小首次发布/CSV | 发布暂以 p95 ≤ 15 秒、单份 CSV p95 ≤ 5 秒定位回退；100 MB 边界另列绝对耗时，不套用小数据结果 |
| 重操作叠加时的轻量读写 | p95 ≤ 2 秒且不超过同档无重操作的 2 倍；任一超过均调查 |
| 正常合法操作 | 意外错误/超时比例 < 0.1%；数据损失、错误归属、重复正式版本、越权为 0 |
| 每档运行期间 | 无 OOM/意外重启；队列完成后回落；记录内存/连接趋势，但短档观测不足以判断长期稳定性或排除泄漏 |

每档先预热 2 分钟，再测量；正常档三次独立热运行。快操作每类每轮至少 200 次，不足时延长或标记样本不足；p99 至少 1,000 个样本才作判断，否则只列观测值/max。昂贵发布/导出每组合至少 5 次，样本不足以可靠评价 p95 时明确只报告每次和最大值；不能将三次中位数称为 p95。

应用缓存首次未命中、重复命中与新进程首次请求分别报告；操作系统/数据库/对象存储缓存若未控制，不称为“冷缓存”。不要清除共享主机 page cache。保持两组数据库 ANALYZE 条件一致；性能结果含错误、取消和未完成样本，不能只留下成功请求。

停止条件：仅停止本任务负载，不操作其他服务。健康异常/OOM、意外错误连续 1 分钟 >1%、本任务容器内存持续 1 分钟 >限额 90%、队列持续 5 分钟无进展、磁盘低于预先留存的夹具/清理预算（至少两份最大数据加现有安全余量），或确认影响共享主机其他服务时结束该档并保存证据。记录“容量未完成/停止原因”，不记为通过。

## 8. 执行顺序与交付

1. **正确性前置**：Metadata 误冲突回归、真实不同字段/同字段协作、唯一发布、权限、CSV/版本不变；失败先修，不开始性能比较。
2. **单项基线**：P01/P02，记录主要操作 SQL、阶段与资源；保留每次原始 JSON。
3. **目标负载**：P03–P05，验证 2/3 用户负载及账号隔离。
4. **重操作与容量**：P06–P10，逐组合测试，2/3 人档内的浏览探针贯穿重操作全时段。
5. **定位复测**：按慢点逐层分析，一次只改一个因素；优化后重复原失败组合及直接相关正确性检查，不先做全面重构。

输出到任务专属证据目录，包含环境清单、fixture manifest、逐次请求/阶段/资源数据、聚合表、关键 trace/截图和通过/失败/未执行清单。凭据只在运行时注入，不写结果。一次复测的 SHA 和运行条件可追溯。

最终报告必须给出：瓶颈出现的最小条件；对应 SQL/锁/CPU/内存/网络证据；2/3 人本轮目标能否满足；可优先优化的 3–5 项及收益、成本、风险；未测容量/故障边界。明确 5/10 人负载、两小时稳定运行、断线和重启恢复未测试，不推断其通过。阶段结果不足时写“尚不能判断”，不把没有报错当成全项目性能通过。

结束后先封存证据，再按已核对的本任务资源名回收临时负载器、浏览器、容器、卷、桶和账号夹具。Owner 验收环境及历史验收记录保持原有状态；本方案及性能通过都不授权合并、GitHub 推送或正式部署。
