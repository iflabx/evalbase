## 1. 要回答的问题与最终交付

验证完整组合：Deep Agents TypeScript 的现成 Harness + LangChain 模型/工具适配 + LangGraph 持久检查点 + 当前配置模型 + EvalBase 共用业务操作。不能把新框架只接到假工具，也不能包装旧 executeAssistantTurn。

需要回答：

1. 普通提示能否通过真实工具完成读取、处理、确认、保存？
2. 要求修改、参数反馈、停止、继续、进程恢复是否在同一事实和授权上运行？
3. 已提交业务在检查点丢失或重复通知时会不会重复执行？
4. 框架实际模型适配、禁用默认高权限工具、流式反馈、持久化有什么限制？
5. 分批运行是否保留全局范围和成果，是否把重复候选误计为净新增？
6. 哪些上游代码直接复用、哪些业务接口只需适配；是否又出现一套自研规划/纠错/续步系统？

输出一份结果报告：锁定配置、用例结论、首错与自动纠正、真实回执、资源消耗、复用/适配清单、剩余风险及采用建议。不以截图中一句“已完成”替代数据库事实。

| 验证所需入口 | 复用与最小适配 | 本阶段不做 |

| 修改未执行要求、停止、状态查询、继续 | 新运行时唯一生效目标、持久检查点和宿主控制入口 | 旧计划编译、多层旧参数修复、旧自动续步 |
| 临时验证页面 | 现有 frontend-v3 页面壳和适用组件，提供聊天、附件、状态、停止、确认和真实链接 | 完整工作台改版、全85项工具、伪成功页面 |

### 2.2 隔离资源

- 使用独立 Compose 项目、数据库和对象存储卷；检查点亦位于独立库。不能只改端口却仍连着4217数据库。
- 绑定127.0.0.1，执行前选未占用端口并记入清单；不关闭或占用4217及现有验收环境。不得预写“已运行于某端口”。
- 一个易读测试项目，浏览器使用测试编辑账号；管理员仅准备材料。查看成员、撤权、跨项目对象放在自动测试隔离库。
- 不复制生产库或整份旧验收库。使用本方案材料，旧成果/旧预算原地保留；如果需兼容样本，使用无正文、无凭据的受控夹具。
- 新入口和旧入口有固定运行时归属。禁止新框架失败后回落旧执行器；禁止旧后台消费者接管新任务。
- 当前模型的端点、model ID、配置revision和必要服务端凭据沿用当前实际有效配置，登记非敏感指纹。凭据只经服务端配置传入，不进提示词、截图或提交。
- 应用事件只投影用户可见内容；不把整个框架检查点或内部流状态原样推给浏览器。

### 2.3 锁版本与开跑条件

执行前填写[运行清单模板](../.scratch/assistant-rebuild/validation/manifest.template.json)。空值表示尚未执行，不能用猜测版本填充。没有填写版本与隔离目标时不得启动真实模型阶段。

1. 固定实际代码提交、Node 24.x精确版本、deepagents、langchain、core、LangGraph、模型适配包、持久检查点包的精确版本及lockfile摘要。按实际npm peer依赖选择兼容已发布版本；不得使用浮动 latest 或中途静默升级。
2. 核对所选TypeScript包的实际API和许可证；官网示例仅作导航，不照搬可能属于Python或不同版本的参数。
3. 使用数据库持久检查点；内存检查点不能用于重启用例。无需额外部署LangSmith服务或向外部发送业务追踪。
4. 枚举模型实际收到的工具名与Schema。只开放上述必要业务能力和有证据需要的框架工具；shell、任意网络、真实文件系统和委派能力不能因默认启用混入。
5. 通过本地SDK协议夹具验证流式tool call、中文JSON参数、工具结果关联和完成原因；保留一次有意义的现成工具调用测试，不用“模型只回复hello”代替。
6. 真实探针最多4次外发，包含在总预算内：必要的简单工具调用、带中文/嵌套参数的调用及实际所需响应模式。若现有模型不支持必须协议，记录模型/适配阻断，停止正式CU；不得暗换模型再宣称同模型通过。
7. 参数和正文输出空间先按现有端点支持能力配置并登记。正常小对象已发生截断时先判配置/模型适配问题，不靠连续纠错消耗预算。探针后冻结温度、输出上限、超时与重试设置；调整必须留下新配置版本，并使受影响旧结果失效。

确定性清洗检查：问题去除首尾空白、连续中文问号变为一个中文问号，除此之外内容保持。受保护的expectedOutput和Metadata逐值、逐序比较。原文件字节、原记录、第6条始终不变。

## 4. 额度、执行分段和停止条件

### 4.1 分清四种限制

| 概念 | 本次如何处理 | 不能怎样处理 |
| --- | --- | --- |
| 单次输出/上下文容量 | 锁定模型支持配置；大结果保留引用，必要摘要保留有效目标和保护要求 | 为省token截断合法工具参数；把超出一次上下文当会话报废 |
| 单次执行步数 | 框架保护值与正常结束条件分开登记；受控测试证明跨执行分段后能保留进度 | 把graph步数当模型请求数；到步数后无限重新invoke掩盖循环 |
| 业务任务授权与成本 | 新运行时继续沿同一任务累计；有授权、有进展时可以自动续做 | 普通继续清零；每个分段反复询问开工；会话累计几次后永久失效 |
| 本次验证活动预算 | 使用下表独立总量；它只是试验停止线 | 变成正式产品默认限制；复制、重置或续用已关闭旧预算 |

LangGraph的recursion limit针对单次图执行；检查点持久化也不等同业务事务。[执行步数](https://docs.langchain.com/oss/javascript/langgraph/graph-api#recursion-limit)、[持久化](https://docs.langchain.com/oss/javascript/langgraph/persistence)。本方案验证正确接入这些机制，不承诺框架默认配置已经具备所需业务恢复语义。

正式产品默认额度不在本次定值。正常会话可承载多个明确任务；达到单次执行保护应与费用耗尽、真实业务失败分别呈现。自动续做仍需有效授权、可核对进展和同一预算，不能无限续接。后续全规模参数依据实测再定。

### 4.2 本次建议上限

| 项目 | 上限及统计方式 |
| --- | --- |
| 真实模型外发请求 | 整个campaign最多120次，含最多4次探针及L01/L02；助手、Worker、参数纠正、摘要、传输重试统一计数 |
| 普通CU会话 | 7个：A/B/C各两种表达，D一次；顺序提前固定，不对每个会话再叠加一个很小的永久调用限额 |
| 真实模型纠错会话 | L01/L02各1个，每项至多10次实际HTTP尝试，均在120次总量内，不是额外额度；每项只注入一次预登记错误 |
| 真实处理行次 | 最多50行次；按实际发给处理模型的输入/目标输出数预占，重试也计入；不能用淘汰重复候选返还额度 |
| 从零生成候选 | CU-D最多12条候选目标槽位：先8条，完全重复/无效缺额最多补4条；不是要求返回12条才合格 |
| 正文处理并发 | 单个活动用例；助手和处理Worker各至多1个模型请求在途，总并发不超过2 |
| 模型请求超时 | 单次真实请求180秒，包含响应正文读取；超时后记账和状态核对，不无限等待或追加备用请求 |
| 网络重试 | 每个原始调用的可重试传输错误至多重试1次；同一次失败调用至多2次参数纠正，不限制随后正常调用；不得SDK和宿主各叠加一套重试 |
| 无进展保护 | 连续3次相同对象、参数及结果的重复读取/失败且没有外部状态变化时暂停；正常后台等待不调用模型轮询 |
| 真实阶段活动时长 | 自第一个真实探针起连续墙钟180分钟，包含CU交互及模型/Worker等待；之前的开发和离线夹具不计，途中不暂停或重置计时 |
| 单次用例执行 | 每个预登记样本首次执行一次，不失败后更换措辞救场。CU-C的停止/查询/继续是规定步骤；其他意外中断至多尝试一次普通“继续”以观察恢复，须独立记录，不能冒充自动纠错或抹去首轮失败 |

请求数是费用代理指标，不是精确货币报价。记录供应方返回的输入、输出及可见推理token；超时未返回usage标为未知，仍占已发请求。单请求输出上限必须冻结记录，不能借120次上限发无限长响应。此处180秒仅是本次试验保护，不宣称正式长任务只能运行180秒。

本次只调整尚未执行的方案与空模板：120次请求、50行次和180分钟是补强后的整轮建议上限，不修改任何旧账本。按全部清洗都调用模型保守估算，7次CU中的资料处理合计25行，L02处理3行，CU-D初始8条加最多4条补缺，共40行次，余下10行次用于受限重试；走规则清洗不虚计模型行次。最多4次探针、L01/L02合计最多20次及其余CU共享剩余请求，不保证用完额度前必定完成。

运行前预占请求和行次额度；预占失败不发请求。达到任一总上限后停止新派发，已发请求记账、已提交业务对账并保存检查点；保留结果，不自动补充预算。剩余额度不足一个完整处理批次时不提交该批次。整个campaign只累计，不为后面的用例重新建额度池。12条是提交前的生成请求槽位上限；模型超量返回应标记异常、拒绝超量采用并如实记录原始条数，不能伪称请求限额保证模型绝不多返回。

### 4.3 立即停止与允许继续的区别

- 越权、错误项目写入、未确认采用、重复落库、旧引擎接管、额度漏计、泄露凭据：停止整轮写入验证，保留证据，结论为阻断。
- 重复澄清、参数持续失败、模型不可用：停止当前用例；其他不依赖该故障的用例可在剩余总预算内继续。
- 预算/时间用完：标记未完成及停止原因，不把它写成“业务接口报错”或“框架不适用”。
- 普通澄清只回答真正缺失的业务信息；不得发送字段名、工具调用JSON、要求模型改内部参数等救援提示。
- 修复后只复验受影响项。此方案不授权自动修复和反复重跑；新尝试须保留首轮报告并有明确剩余额度或新授权。

## 5. 第一层：自动验证与真实模型纠错

### 5.1 真实SDK传输链的受控回归

这些用例使用真实Deep Agents/LangGraph和模型客户端序列化、流式解析、工具派发；模型端连接本地可控HTTP响应服务器，业务操作连接真实隔离PostgreSQL/对象存储。不能mock掉工具执行、提交保护、检查点或接收结果的公开入口。外部模型请求为0；离线进程不加载真实模型凭据，模型客户端只允许指向本地响应服务器；故障只在隔离模式启用。

| 用例 | 触发与步骤 | 核验事实 / 通过标准 |
| --- | --- | --- |
| F01 参数链一致 | 回放正常中文、嵌套字段、未知字段、错误类型、分片截断和不支持的引用；无效后提供一次合法纠正响应，再提供持续无效分支 | 同一Schema贯穿声明与执行；非法输入不写入；纠正结果实际进入业务；持续失败有界暂停，不能只看纠错文本正确 |
| F02 权限、范围和修订 | 编辑/查看/已撤权身份调用相同写入口；跨项目引用、已过期选择；准备确认后修改草稿revision及用户要求 | 服务端拒绝非法写入；不扩大范围或偷换最新revision覆盖；确认必须重建；不泄漏不可见正文 |
| F03 保存成功但响应丢失 | 在事务落库后、工具返回或检查点落盘前中断宿主；重启后重放同一操作，再双击确认 | 只创建一个目标草稿、只追加一次；同一操作ID查回执；换参数重用ID拒绝；页面对象、名称、保存链接一致 |
| F04 后台等待恢复 | 提交真实job后重启宿主；终态通知分别丢失和重复；晚到旧执行尝试提交 | 持久绑定能补查终态；不重新生成已完成批次；只推进一次且旧令牌拒绝；没有旧续步消费者参与 |
| F05 执行中停止 | 在模型等待、业务提交前两个位置设置可控栅栏；从真实控制入口停止→查询→继续；另测已提交后才停止 | 停止不被busy拒绝；查询不执行；继续只做剩余且不重置账本；已提交结果保持成功，迟到写入被阻止 |
| F06 分段与预算 | 用受控小步数使需多段的任务跨至少3次执行；保持同一任务、作业和操作身份；另构造额度只够1次请求、请求超时和重复无进展 | 有进展可跨段继续，用户无需每段开工；费用上限仍累计且不能绕过；终止、未知结果、费用耗尽区分；重复循环停止 |
| F07 长上下文与摘要 | 通过正常消息/工具入口构造超过验证压缩阈值的历史，触发真实所选框架摘要路径，再修改数量和保存目标 | 摘要后仍以唯一生效要求、权限和业务回执为准；旧要求不复活，工具正文不被当授权；实际摘要请求被计数 |
| F08 跨批重复与补缺 | 两批响应中注入一条同文问题但不同Metadata、一条仅首尾空白不同问题，以及一对语义接近但场景不同的问题；补缺后重放终态 | 全局比较覆盖前批和同批；确定性重复不计净新增，补缺只补剩余并计费；相似项不因高相似度自动删除；重放不重复累计 |

F06/F07的低阈值是离线机制探针，不能带入真实CU配置。框架若不提供可安全恢复的中断位置，必须先找到经验证的受支持接法；不得声称“捕获GraphRecursionError后重新invoke”天然等价于正确恢复。F08只要求确定性去重和可审计筛查，不引入新向量数据库或逐条LLM复审。

每个子分支保存trace和业务断言结果。首次失败保留；代码修复产生新attempt并只重测受影响分支。安全与一致性分支未通过时不进入真实模型阶段；此时结论是适配未就绪，不消耗模型额度。

### 5.2 真实模型纠错：L01/L02

F01的纠正响应由夹具预先给出，只能证明参数传输与执行链一致，不能证明当前真实模型会纠错。因此完成受控安全门槛和最多4次真实探针后，再执行以下两个真实模型用例；模型、工具、业务库和版本与随后CU相同。

| 用例 | 普通需求与一次性错误 | 末端通过标准 |
| --- | --- | --- |
| L01 类型错误后正确读取 | “查看验收资料前3条。”在首次对应选取/读取调用中，将已登记的数量参数改成明确非法的非数值；如真实接口只接受记录ID集合，则预先登记将该集合改为非法类型，不能临时添加测试专用业务参数 | 错误进入真实SDK及校验反馈；当前真实模型重新给出合法参数；实际只读取r01～r03，范围未扩大、无写入；不能只看模型声称已纠正 |
| L02 截断后完成清洗保存 | “把验收资料前3条清洗一下，去掉首尾空格和重复问号，期望输出和Metadata保留，保存为‘纠错保存样例’草稿。”在首次处理提交调用的参数JSON中制造一次未闭合截断 | 非法调用未提交job；模型根据正常错误反馈补全合法调用，实际处理3条；经页面确认保存唯一草稿，刷新及回执核对正确；无技术提示词救援 |

执行约束：

- 开跑前按冻结的真实Schema登记工具名、参数位置、改动方式和触发次数。只在隔离模型传输边界、真实SDK解析之前改变该次工具参数；保留原始响应和注入后响应，不改变工具名、调用ID、身份、用户需求或已知对象事实。工具执行、反馈、持久化和确认仍走正常入口。
- 后续纠正响应必须来自真实供应方请求。不能提供预制正确响应、直接修补业务入参、注入正确答案或另写绕过框架的纠错循环。使用正常工具Schema和结构化校验反馈；不把expected.json发送给模型。
- 若预登记工具先自然发生了同类错误，则记录为自然触发，不再叠加该次注入；其他自然错误也必须保留。若错误被无损归一直接消除，记为“归一化通过”，不能记成“真实模型纠错通过”；该项纠错能力仍未验证，不追加注入试到过。
- 每项独立新会话，至多10次真实HTTP尝试，同一失败调用至多2次参数纠正，均消耗同一campaign预算。预登记触发点未到达时记未覆盖及原因，不能挑另一条响应临时换题。
- L01只读，L02的普通提示和最终确认由验证页面完成；故障注入由隔离测试层完成。不得用SQL或手工业务API代替保存。报告明确标注“真实模型 + 受控参数故障”，不混入普通CU首轮错误率。
- 纠正成功须串联错误反馈、真实纠正响应、SDK解析结果、实际业务入参和末端回执。安全拒绝后暂停或纠正次数耗尽，属于安全保护有效、业务纠错失败；不能据此通过这一层。

这两项验证已知、可由原需求和真实引用纠正的错误。身份越权、对象不存在或含糊范围仍应安全拒绝/业务澄清，不要求模型猜测。自然模型行为的有限复现性由下面预登记的7次普通CU补充观察，不承诺所有输入永不出错。

## 8. 通过门槛、采用判断与复用清单

### 8.1 用例状态与双重判定

- 未执行、执行中、通过、失败、阻断、未完成六种状态。安全结果和业务结果分别给出，最终通过必须满足该项完整目标。
- F02等负向分支按“正确拒绝且无副作用”通过保护机制；这个结论不能替代L01/L02或普通CU的业务完成。
- L01/L02和普通CU须核对正确对象、范围、字段保护、确认及末端回执；保存用例还须打开真实链接并刷新。参数错误被安全拦截但任务仍停住，记业务失败；仅有正确纠错文本、最终总结或一张成功截图均不够。
- 普通CU通过方式为直接完成 / 自动恢复 / 正常业务澄清；首错保留。自动恢复指无需用户补内部参数、催促重试或换会话，系统在原配置与限额内纠正并完成。CU-C规定的停止和继续属于正常控制步骤，不是失败救援。
- 技术提示词、手工业务API补步骤、改库、临时换模型才完成：记失败，附干预。意外技术失败后靠用户“继续”才完成，只能另记恢复能力，不能改记首轮自动纠正通过。
- 安全失败立即阻断；未发生既有业务失败而先遇额度/时间耗尽，记未完成。预算耗尽不能覆盖此前已发生的错误。7次样本只提供有限的表达复现证据，不能估算全量稳定率。

### 8.2 决策规则

1. F01～F08所有规定分支通过、L01/L02均有真实模型纠正并完成业务的证据、7次普通CU分别完成业务闭环、无P0/P1且未依赖旧编排：可建议正式采用该固定组合并拆下一阶段开发票。不能用“安全停止”“另一个表达通过”或旧测试成功替代任何一项。
2. 仅CU-D内容多样性不足：独立记录数据生成业务风险；不能据此直接否定框架，也不能把生成效果写为通过。报告区分“运行时适配结论”与“生成业务/质量结论”；需业务闭环证据不足时只能给有条件建议。
3. 现有模型不支持必要协议、核心持久恢复不可靠、无法关闭越权默认工具，或必须重新实现大套规划纠错才能工作：暂不定案，说明需调整模型适配/框架候选的具体证据。不得悄悄回落旧执行器。
4. 任一必需普通表达卡在参数/恢复、L01/L02未覆盖真实模型纠错、仅部分用例通过、预算结束或环境阻断：不得判定正式采用门槛已通过；保留所有样本及原因，提出只补缺口的下一次验证，不自动重跑。通过也只代表冻结组合在这些场景下达标，不保证未来所有输入永不报错。
