## 3. 共同实施边界

- 沿用 AI SDK、现有业务工具、PostgreSQL/Worker/MinIO、处理运行和稳定候选身份；不换框架，不加多智能体、通用 DAG、向量库、第二套结果存储或通用质量评测平台。
- 依据 [ADR-0014](adr/0014-project-agent-and-processing-runtime.md)，背景文档属于私人会话资料；它提供生成依据，不冒充原始数据资产。服务端核实权限、引用、固定输入和回执，文档中的文字不获得工具授权。
- 已授权执行无需反复询问开工；结果采用和正式发布保留现有固定确认。停用、撤权、修订冲突、未知写入对账、字段保护及容量限制保持。
- 同一用户目标的预算跨自动续做、格式纠正和补齐累计，不能靠换运行或重试重置。新一轮明确授权的工作与原故障重试区分；达到上限保留成果并说明未完成部分。
- 只修本次行为链。工具合同尽量复用现有 schema 和领域服务；若现有存储足够，不为计划、场景和统计各建一张新表。确需持久字段时做最小兼容增补，旧运行按原冻结配方恢复。
- UI 严格复用 frontend-v1 的字体、token、图标、间距、密度和适用组件，正式改动在 frontend-v3。沿用独立助手页面、处理结果组件和确认卡，不增设第二个工作台或面向用户的 API 参数编辑器；冻结原型保持只读。
- 保留同一 4217 的项目、账号、文档、失败会话、候选与验收数据；定向测试使用隔离夹具，不改写旧会话来伪造成功。旧 Ticket 的 Owner 状态不由本轮代签。

## 4. 具体用户流程

用户在一个新会话上传背景文档后，可直接说：

> 根据这份文档，为 A.1 的 8 个小类各建一个 50 条的测试集。问题要像用户正常提问、语义完整，不用现有原始数据。先给方案。

助手读取有权访问的文档，核对八个分类定义、每类 50 条和生成能力，给出简短业务方案；此时不创建草稿、不入队、不写候选。用户说“按方案执行，逐个创建”后，逐类生成和审核；每类当前目标为 50 条，整体交付为 8 个测试集、合计 400 条。范围清楚时不要求用户选择内部字段或手动提供种子。

已生成成果支持“把这批问题改得更自然”“只改我选中的两条”“继续下一类”。先处理完当前需要审核/确认的成果，再按已有授权推进下一类；不悄悄采用或发布，不把确认按钮之外的口头总结当作真实写入。沿用已有确认粒度，不新增每个模型批次的确认。

用户改口“先停下，只解释方案”，助手保存当前进度并停止新增业务动作。恢复时以最新明确要求和真实回执继续，不重建已存在的草稿或重复生成已完成的类别。

GB 分类仅为这次验收数据，产品仍支持通用测试集；不内置八类、50 条、拒答要求或安全标签作为所有任务的默认值。内容不满足文档或用户要求时报告具体差额，不承诺模型永远不报错。

## 5. 验证与完成口径

各 Ticket 的验收表是对应断言的唯一详细清单；[测试计划](test-plan-data-selection-and-assistant.md#515-opt-2631-执行与生成修复) 仅作索引。

1. 第一批用现有可控模型和隔离持久化回归本次错误：错误字段、最新意图、跨批 20+28+2 集合、50/30/2 数量。已有未变权限与确认用例直接复用，不重新运行全库流程。
2. 第二批先做 5–10 条真实文档生成样例，再完成第一类 50 条小闭环；检查无原始数据输入、无人工种子、刷新恢复及真实保存回执。能力通过与内容质量分别记录。
3. OPT-32/33 前置定向验证通过后，由 OPT-31 在固定代码/模型配置下，用一个新会话完成一次八类各 50 条的集成验收，作为本轮唯一大批生成。使用上述普通短提示词；允许业务澄清和既有确认，不允许靠用户提供工具名、参数修正、内部 ID、手动种子或绕过页面 API 来完成。
4. 400 条全部进行结构检查；每类内容按自然问法、语义完整、分类一致和期望行为进行逐条审核。若只抽查，必须注明范围，不能据此标记 400 条全部可用。明确区分模型原生合格、自动恢复后合格和人工修改后合格。
5. 记录各类实际数量、重复与未变化数量、模型调用/重试次数、失败类别、耗时和技术纠错提示次数；技术纠错提示目标为 0。预算耗尽保留进度，不能隐藏失败或反复重跑直到成功。一次通过不证明任意模型和输入零失败。
6. 最终汇总原六张及 OPT-32/33 的相关验证证据，复用同一 4217 供一次集中人工验收。只构建受影响服务，不新增 5/10 人压测、两小时稳定试验或服务器重启测试；不自动合并、推送或正式部署。
